对象：聚合根-子实体-值对象，业务完整性约束，有统一的入口。如订单+订单明细属于同一个聚合；订单与客户之间属于独立聚合，通过客户id关联。

行为：业务语义，如点击确认；只关联一个或多个概念（聚合根-子实体），行为的前置/后置判定（可以调用规则做复杂计算），事件产生（执行成功后可以产生什么事件，通知其他对象）。
注意：行为分为查询和写入；写入行为有前置判定和后置判定；查询行为要与统计分析做对应，查询行为无前后置条件。

规则：取值范围、类型和非空判定；复杂的验证和推理：如金额风险判定。把决策解耦调。校验-推理两大类规则。仅做判定，不修改数据。规则采用函数进行计算。
注意1：规则层面，检查只针对对象自身字段，必填required/类型/取值范围/枚举/模式；检查涉及跨对象字段，则需要额外行为补充。
注意2：规则由函数组合构建

函数：一系列功能函数，服务于执行决策。包括 格式转换、属性计算、属性衍生、逻辑判断和机器学习等，仅聚焦于当前本体。

事件驱动：将对象行为进行了解耦。需要定义发布对象和订阅对象。通过事件发布，通过事件模型（事理图谱），可以告知大语言模型，在某个事件发生后，接下该往哪里执行或推理。ps：事件信息可以作为上下文给到大模型。规则可以定于事件。

场景模型：端到端的【业务协同流】（如下单到发货，采购到入库等流程，将一件事情顺利推进走完）。任何业务问题看作为一个场景，该场景由【跨对象的行为和规则来编排】执行的，决定了本体如何用。可以看作为一个流程：规则-行为-事件-规则-行为-。。。。任何一个场景，都是行为-规则-对象的灵活拼装。

主体模型：参与者权限。actor-role-permission-action-content，一个人员可以有不同角色，每个角色可以分配多个权限，每个权限对应一个行为，一个行为可以返回限定范围的内容（如行限制）。role-permission权限角色矩阵。

查询统计模型：定义复杂的统计查询和分析。只能与对象和行为发生直接关系（behaviorType=query），查询行为与查询统计对象一对一严格绑定。不要将规则、流程等糅合到查询里，两者应该解耦。

对象数据表映射：聚合根-主表，子实体-从表，值对象-主表字段，复合对象-一对多映射。

接口：架构本体暴露为MCP服务，以及与外部系统对接（外部MCP服务），需要定义相关输入和输出参数格式。

6 OWL问题
1）OWL无法溯因推理。经典OWL推理主要解决形式化知识下的逻辑蕴涵、分类和一致性问题，并不自带一套通用的因果分析机制。
2）单纯依靠OWL建立的模型，往往更偏向静态语义描述。这不是OWL设计得不好，而是它本来就不是一个完整的业务应用运行平台。SWRL可以扩展规则表达，SHACL可以检查数据图是否符合指定结构和约束，但两者的定位也不一样，不能把它们都当成同一种推理规则。

7 大模型的问题
1）OWL有明确的形式化语义，而大模型本身并没有与之对应的一套世界假设。它既不会因为知识库没有记录就严格判断事实不存在，也不会像封闭世界数据库那样，把未查到的信息直接视为否定。
2）大模型更像是在已有上下文和训练所得模式的基础上，生成一个它认为合适的回答。回答完整，不代表事实完整；表达肯定，也不代表证据充分。我们可以通过Token概率、多个样本的一致性或专门的置信度评估来观察不确定性，但这些指标不能直接等同于逻辑真值。

8 LLM + OWL 核心观点提炼：
1. TBox 是大模型的业务语义锚点，不只服务于传统公理推理。
2. ABox 可按当前问题按需提取，不必每次整体装载，也不必都转成知识图谱。
3. 计算引擎算准数字，语义模型讲清概念口径，大模型负责理解、关联、假设和组织分析，三者灵活组合。
4. 大模型结论要拆成业务断言回查证据：可证明性、一致性、SHACL 校验各答不同问题，不能把通过/失败当成对现实的最终判断。
5. 高风险场景结论必须可追溯，重要操作需权限、审批和人工确认，企业要的是可复核的决策链。
6. 本体的角色变了：从逻辑推理的知识基础，扩展为大模型理解业务的语义基础。
7. 不是大模型取代经典推理，而是确定性部分守好，开放性问题交给大模型探索，再用数据、规则和证据落地结论。
8. 企业 AI 应是连接业务知识、数据、计算、分析和执行的体系，而非万能问答模型。
9. 判断本体是否必要，关键看两点：业务语义是否说清，大模型关键结论能否回到数据和规则中验证。

9 LLM+OWL的执行逻辑
1）问题+TBOX+SWRL+SHACL+LLM（表格+元数据+大模型）
2）输出规划
3）拉取子图数据
4）LLM输出结论
5）符号校验（hermit一致性+逻辑蕴含）


一个建议：
源系统的数据经实时同步或增量 ETL 落到 Foundry Dataset 层，带版本和血缘。然后通过语义映射挂到 Ontology 对象层上，对象实例化、Link 建关系、Function 实时算分。对象状态一变，事件就推给 Jev。判断出来按置信度分流，高的走 Action，低的走大模型，大模型的输出再过校验层挑刺。最后统一落到执行和回写，结果回流更新本体对象状态。

三个容易做错的地方。一是本体层不独立存数据。它只存「对象定义 + 指向 Dataset 的映射关系」，查询的时候底下读的还是 Dataset，也就是虚拟视图。加了本体，不等于多出一份数据要同步。二是别让 Jev 直接读原始数据表。让它订阅本体事件流，好处是判断用的语义和系统其他地方完全一致。三是执行结果必须回写。不回写，本体里的对象状态就是旧的，下一次判断用的还是过期状态，闭环就断了。

jev检测事件流，实现状态快速感知和决策。是否可以进行规划的校验呢？

本体建模贵。 Palantir 那套是要工程师驻场把业务一点一点建模进去的，前期投入不小。可行的做法是先用最小可行本体（MVO）：挑一个高价值痛点域，跑通最小闭环，验证 ROI 再横向铺开。别一上来就想建全公司的本体。Jev 只吃文本。 图纸、设备声纹、监控画面这些都进不去，得先有一层把状态转成文字。这个转换层本身也是成本，而且它转得准不准，会直接限制后面的判断质量。调度层会变成复杂度中心。 系统里有 Jev、大模型、本体推理引擎、Action 执行器，编排逻辑就是核心复杂度所在。老老实实上工作流引擎，别自己手搓。可解释性要求。 金融、医疗这类行业光有概率输出不够，要本体推理层给出形式化证明树，把完整的决策依据链条记下来。最要小心的错误，是把业务规则塞进提示词。 规则一旦进了提示词，就既不可审计也不可测试，以后想改还得重新调模型。规则留在本体和代码里，模型只填判断题的答案。
