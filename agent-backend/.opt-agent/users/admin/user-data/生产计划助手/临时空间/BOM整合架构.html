总BOM整合架构

1 个前置阶段（人机结合定标准） + 1 个自动化主流程（机器执行与把关） + 1 条反馈回路（问题回流修标准/修数据）

阶段 0：映射设计（前置 · 人机结合 · 一次性 + 按需迭代）

人机目标：先定"方言 → 普通话"的翻译规则，再谈自动化
人工抽样各类子BOM文件
   ↓
机器辅助: 扫描各文件表头列名、版式差异(单列 / 双语 / 脏单元格)
   ↓
人工确认: 每个原始列名 ↔ 总BOM标准字段 的对应关系
   ↓
固化产物① 子BOM字段映射.json  —— 每族一个字典 + 标题行特征 (适配层, 可迭代)
固化产物② 总BOM标准字段.json  —— 字段定义 / schema / 列序 (标准锚点, 不再变)
为什么必须人在环里：列名含义、双语列取舍、脏数据识别，机器只能建议，人来拍板。
为什么分两个产物：总BOM字段是唯一标准锚点，定稿不动；子BOM映射是适配层，随数据问题迭代完善。
副产品：映射表沉淀了对该类装备BOM版式的全部认知，本身即是交付物。

主流程：自动生成总BOM（全自动）

S1加载 load_all
读 BOM/ 全部文件，完整文件名建索引、不截断——版本后缀问题留给匹配阶段显式处理，不悄悄丢弃信息。
▼
预检①S1.2 族识别 precheck_families
文件名必须归入族字典（VCPM / WCXXX / WCCMT / WCCUN），否则报出并停止。理由：不放行的文件=被静默忽略的文件，它不会进入后续任何检查。
▼
预检②S1.5 表头 1:1 映射 precheck_headers
每文件三查：①找得到标题行 ②必需字段集齐（schema 中 source=子BOM映射 的全部字段）③无不认识的列。理由：双向卡死——缺字段是"少"，陌生列是"多"，两者都意味着数据会被静默丢。
▼
S2归一化 normalize
逐行抽取 → 统一为标准字段的明细 items。预检②已保证可翻译，此步纯翻译、零判断。
▼
预检③S2.4 整行重复 precheck_duplicates
同一文件内完全重复的明细行 → 报出并停止。理由：重复行会让数量翻倍，且是源文件缺陷的强信号（实战：ER5ZE 重复紧固件块）。
▼
预检④S2.5 编码认领 build_resolver
从根节点逐层：编码 → 唯一文件（精确 / 前缀匹配）。候选 ≥2 个（版本冲突）→ 报出并停止。理由：选错版本整棵树都是错的，而且错得隐蔽；绝不按排序默默选一个（实战：备份副本混入被拦）。
▼
S4递归展开 expand
DFS 先序：有文件 → 组件下钻；无文件 → 叶子；循环引用截断；level=1 标记 UNIT → 拍平的多级树。与 S2 分离：翻译和拼装解耦；与 S5 分离：结构和算量解耦。
▼
S5用量计算 calc_total_qty
total_qty = qty × 父件 total_qty，单趟栈算法沿树连乘（×订单台数）。
▼
S6输出 export
Excel 列序 / 每列填不填 全由 schema 的 source 属性驱动：子BOM映射+计算生成 → 填值，人工维护/到料join → 留空。层级缩进、组件加粗、warnings 附表。
▼
S7回归对账（可选）validate
与人工维护的参考总表 difflib 对齐，比对 posiz / qty / total_qty。注意：参考表只做"标准答案"校验，绝不参与生成。

反馈回路：问题回流（关键闭环）

主流程任何一步报错停止，不是失败，是设计动作——错误报告直接指出该修哪里；修完重跑，直到全流程通过：
报错类型回流到
族不识别阶段0：补新族的映射字典
表头缺字段 / 陌生列阶段0：改 子BOM字段映射.json
脏单元格 / 重复行数据源：清理子BOM源文件
版本冲突数据源：每个编码只保留一版
缺子BOM文件数据源：补文件（或确认确实没有）
对账差异人工归因：版本演进(可解释) / 程序bug(修代码)
效果：映射表随迭代越来越完备，同族新文件进来基本零成本。

机器与人的职责划分

机器：翻译、拼装、算量，以及"宁可错杀不可放过"的预检——输入有歧义就停机，不猜。
人：定义映射标准、清理脏数据、裁决版本——所有需要业务知识的判断。
一句话架构：人机结合定标准（阶段0）→ 机器严格执行 + 严格把关（S1~S7）→ 把关发现的问题回流给人修标准或修数据（反馈回路）。
