## Core Principles

### I. 中文文档优先

所有项目文档——包括功能规范（spec）、技术设计（design/plan）、任务拆分（tasks）、
接口文档与治理文档——必须全部使用简体中文编写。代码注释中的业务说明同样使用中文；
标识符（变量、函数、类名）保持英文并遵循语言惯用命名。

**理由**：团队沟通语言为中文，文档统一可避免歧义，降低维护与评审成本。

### II. 代码质量与分层架构

- 遵循所用语言/框架官方推荐的代码风格（如 Python 遵循 PEP 8、Go 遵循 Effective Go），
  并通过自动化工具（linter/formatter）在 CI 中强制检查。
- 必须采用分层架构：**接口层 → 业务层 → 数据访问层**。每一层职责单一，
  禁止跨层调用（例如接口层不得直接访问数据访问层）。
- 单个文件/模块不得超过 500 行；超出时必须按职责拆分。

**理由**：分层隔离使各层可独立测试与替换，限制文件规模保证代码可读、可评审。

### III. 测试覆盖（不可协商）

- 每个功能模块必须有对应的单元测试。
- 核心业务逻辑的测试覆盖率不得低于 80%。
- 测试必须覆盖三类场景：正常流程、异常流程、边界条件。
- 测试随功能代码一同提交，缺少测试的代码不得合入。

**理由**：覆盖率与场景完整性是回归质量的底线，不可事后补齐。

### IV. 性能标准

- 所有接口的 P95 响应时间不得超过 200ms。
- 涉及数据库查询的功能必须进行索引优化（高频查询字段必须有索引，并验证执行计划）。
- 禁止 N+1 查询：关联数据必须使用批量加载（如 join、批量查询、预加载）。

**理由**：响应时间直接影响 agent 服务的交互体验；N+1 是后端性能退化最常见根因。

### V. 数据一致性与事务

所有涉及状态变更的操作必须使用数据库事务；事务内任何一步失败必须整体回滚，
禁止部分提交。跨多个写操作的流程必须明确事务边界并在代码评审中核验。

**理由**：部分提交会产生不可恢复的脏数据，在 agent 服务中会导致会话/任务状态错乱。

### VI. 依赖治理

引入任何新的第三方依赖必须说明选型理由：包括候选方案对比、许可证、社区活跃度、
维护状态与引入范围。理由记录在设计文档或 PR 描述中。

**理由**：控制依赖面可降低供应链风险与长期维护成本。

### VII. 接口设计规范

- 所有接口遵循 RESTful 规范：资源命名、HTTP 方法语义、状态码使用必须规范。
- 统一错误响应格式（如统一的 `code` / `message` / `details` 结构），
  禁止各接口自定义错误体。
- 所有接口必须有接口文档（OpenAPI 或等价物），文档随代码同步更新。
- 接口契约必须与前端共享并保持一致；契约变更必须先更新文档并通知前端，
  再实施后端的破坏性变更。

**理由**：统一契约是前后端协作与接口可演化的前提。

## 技术与架构约束

- 分层架构（接口层 / 业务层 / 数据访问层）为强制约束，目录结构应体现该分层。
- 数据库访问必须经数据访问层，使用参数化查询，禁止拼接 SQL。
- 高频查询路径必须有索引支撑；新增表/查询必须评审索引设计。
- 对外接口必须具备可观测性：关键路径需有结构化日志与必要的指标埋点，
  以支撑 P95 指标的持续度量。

## 开发流程与质量门禁

- 所有变更通过代码评审合入；评审必须核验本章程各原则（分层、测试、事务、接口文档）。
- CI 门禁：linter/formatter 检查、单元测试通过、核心覆盖率 ≥ 80%。
- 接口变更必须先更新接口文档并与前端确认契约，再合入实现。
- 涉及数据库变更（表结构、索引）必须在 PR 中说明影响与回滚方案。

## Governance

- 本章程效力高于团队其他开发惯例；与本章程冲突的实践必须修订或废止。
- 章程修订需：提交修订说明（含变更原因与影响）、经团队评审通过、同步更新版本号。
- 版本号遵循语义化版本：MAJOR = 原则移除或不兼容重定义；MINOR = 新增原则/章节
  或实质性扩充；PATCH = 措辞澄清与非语义修订。
- 每次代码评审与功能规划时检查章程合规性；发现违规必须在合入前整改。
