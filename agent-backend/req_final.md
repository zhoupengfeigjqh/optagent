## 〇、用户与认证

- 系统为**多用户**设计，用户数据按用户隔离，目录结构含用户维度。
- 目标认证形态：账号密码登录 + JWT 无状态认证。
- **本期不实现认证**：所有请求默认归属内置 `admin` 用户；接口与数据访问层
  按"当前用户"抽象编写，后续接入 JWT 时不改动业务逻辑。

## 一、文件管理模块

### 1.1 用户文件空间

**路径**：`.opt-agent/users/{user_id}/user-data/`（本期 user_id 固定为 admin）

**目录结构**（共8个文件夹）：

| 文件夹        | 用途             | 权限（Agent）                     |
| ------------- | ---------------- | --------------------------------- |
| `生产计划/`   | 存储生产计划文件 | **只读**                          |
| `产线信息/`   | 产线配置与参数   | **只读**                          |
| `切换时间/`   | 切换时间记录     | **只读**                          |
| `求解时间/`   | 求解时间数据     | **只读**                          |
| `产线电价/`   | 电价配置         | **只读**                          |
| `目标优先级/` | 优先级配置       | **只读**                          |
| `使用规则/`   | 业务规则文件     | **只读**                          |
| `tmp/`        | 临时工作空间     | **读写**（Agent输出唯一可写目录） |

**功能要求**：

- 用户可上传到 **7 个业务目录 + `shared/`**；`tmp/` 为 Agent 专用，用户不直接上传。
- 系统自动在文件名后追加时间戳（格式：`_YYYYMMDD_HHMMSS`），避免覆盖。
- 文件大小限制：单文件 ≤ 50MB，格式限制为 `.csv`, `.xlsx`, `.txt`, `.json`, `.pdf`。
- `tmp` 目录内文件自动按 `{thread_id}_{timestamp}_{filename}` 命名，防止多对话冲突。
- `tmp/` 定期清理：**7 天未访问的文件自动清除**。

---

### 1.2 用户共享资料

**路径**：`.opt-agent/users/{user_id}/user-data/shared/`

- 用于存放跨对话、跨数字人共享的资料文件（如企业统一规则书）。
- Agent 具有**只读**权限；用户可通过前端上传或管理员统一部署。

---

### 1.3 用户对话管理

**路径**：`.opt-agent/users/{user_id}/user-data/threads/{thread_id}/`

- 每个 `thread_id` 对应一次独立对话，**thread_id 由后端生成（UUID）**。
- 目录下包含：
  - `history.jsonl`：对话历史，**JSONL 格式**（每行一条消息，追加写 O(1)、
    崩溃最多损失最后一行）。**不分片**，每 thread 一个文件。
  - `summary.json`：滚动摘要（派生物，见 2.3），含摘要文本 + 已覆盖消息序号。

**history.jsonl 存储内容**：

- 仅保存 `role: user` 和 `role: assistant` 的消息。
- **不保存**：thinking 内容、tool 调用日志、system prompt、中间过程。

**存储格式示例**（每行一个 JSON 对象）：

```jsonl
{"role": "user", "content": "今天生产计划是什么？"}
{"role": "assistant", "content": "根据当前产线信息，建议..."}
```

**Thread 生命周期接口**：创建、列表（按更新时间倒序，标题取首条 user 消息
前 20 字）、重命名、删除。删除 thread 时**连带删除** history/summary 及
`tmp/` 下该 thread_id 前缀的全部文件。

---

### 1.4 用户数字人信息

**路径**：`.opt-agent/users/{user_id}/agents/{agent_name}/`

每个数字人包含以下核心配置文件（由数字人设计平台预配下发）：

| 文件                            | 作用                                                        |
| ------------------------------- | ----------------------------------------------------------- |
| `SOUL.md`                       | 定义数字人人格、语气、角色设定，内容追加到 System Prompt    |
| `MCP.json`                      | 声明数字人可调用的 MCP 服务（如数据库、API）                |
| `TOOL.json`                     | 声明内置工具（从本期 6 个内置工具中选取启用）               |
| `/skills/{skill_name}/SKILL.md` | 技能文件，**YAML frontmatter 头部信息**追加到 System Prompt |

**加载机制**：

- Agent 初始化时读取上述文件。
- `SOUL.md` 全文与 `SKILL.md` 的 frontmatter 头部加入 System Prompt。
- `MCP.json` 和 `TOOL.json` 用于注册可调用能力，不进入 Prompt。

**本期后端对数字人配置只读**：仅提供数字人列表/详情查询接口；
创建、编辑、下发由数字人设计平台负责（直接写目录）。

## 二、Agent核心功能

### 2.1 Agent生命周期管理

**核心模型**：Agent 实例 key = **(user_id, agent_name)**。实例只固化数字人配置
（System Prompt、已注册工具、MCP 连接、LLM 客户端配置），**不持有对话历史**；
每轮请求由业务层按 `thread_id` 拼装历史与摘要注入。

**初始化**：

- 用户选择数字人进入对话后，首次发送消息时触发 Agent 实例创建。
- 实例创建后驻留内存，供该用户该数字人下的多个 thread 复用。

**活跃关系**：**1 用户 : 1 数字人 : 最多 3 个并发 thread**。

- 用户选定一个数字人进入对话，最多同时开启 3 个并行对话（类似新建对话）。
- 切换数字人必须先**退出**当前数字人再重新选择，不存在同时与多个数字人对话。
- "退出"仅清除用户当前选中的数字人状态，**后端实例不销毁**，由 LRU + 空闲超时
  自然回收；重新选回同一数字人时直接复用实例。

**内存管理（LRU 淘汰策略）**：

- 全局最多同时驻留 **5 个** Agent 实例（可配置）。
- 空闲超时统一为 **10 分钟**（可配置），超时自动销毁。
- **LRU 仅淘汰空闲实例**（无进行中推理），不淘汰正在对话的实例。
- 超出限制（池满且无空闲实例可淘汰）时，**拒绝请求并返回友好提示**
  （如"系统繁忙，请稍后重试"），不排队、不淘汰在用实例。

**监控**：

- `GET /api/monitor/agents`：存活实例数 + 每实例明细（user、agent_name、
  活跃 thread 数、空闲时长、降级状态如不可用 MCP 列表）。
- `GET /api/monitor/health`：进程存活、内存 RSS、`.opt-agent` 磁盘可用空间。
- 均为只读 JSON，本期无认证、供运维内网调用，不接 Prometheus。

---

### 2.2 Agent初始化流程

当Agent首次被创建时，按以下顺序加载能力：

1. **读取 SOUL.md** → 将内容追加到 System Prompt。
2. **读取各 SKILL.md 的 YAML frontmatter 头部** → 追加到 System Prompt
   （仅技能描述，不加载技能实现）。
3. **注册 TOOL.json** → 将内置工具函数绑定到Agent运行时。
4. **注册 MCP.json** → 建立与外部MCP服务的连接。

**MCP 策略**：超时统一 **30 秒**（建连与运行期调用相同），重试 1 次。
建连失败**不阻断** Agent 启动：实例降级就绪、标记该 MCP 不可用；
调用到不可用 MCP 时回复"当前服务不可用，请稍后尝试"，并记录告警日志。

初始化完成后，Agent 进入"就绪"状态，等待用户输入。

---

### 2.3 对话与历史管理

**历史加载**：

- 每次对话请求时，业务层加载当前 `thread_id` 的 `history.jsonl` 与 `summary.json`，
  拼装后注入该轮推理（实例本身不持有历史）。

**滑动窗口 + 滚动摘要策略**：

| 层级           | 处理方式                                                                 |
| -------------- | ------------------------------------------------------------------------ |
| 最近 20 条消息 | 完整保留，全部注入上下文                                                 |
| 更早的全部消息 | 并入滚动摘要（**不设 100 条上限**），摘要作为 System Prompt 的一部分注入 |

**摘要再生成**：

- 窗口外每新增满 **20 条**，异步触发一次增量重写
  （旧摘要 + 新归档的 20 条 → 新摘要，更新 `summary.json`）。
- 摘要生成失败**不阻塞对话**，本轮使用旧摘要。

**历史保存**：

- 每一轮对话结束后，**异步**将 `user` 和 `assistant` 消息追加写入 `history.jsonl`。
- 不等待写盘完成即返回响应，确保响应速度。

---

### 2.4 对话输出与思考模式

**输出方式**：

- 采用 **SSE（Server-Sent Events）** 流式输出，事件分四类：
  - `thinking`：推理流（前端折叠渲染，**不落盘**、不进 history.jsonl）
  - `content`：正式回复流
  - `done`：本轮结束
  - `error`：错误信息
- **不输出**：tool 调用日志、中间推理链（thinking 除外）、MCP 请求日志。

**思考模式（Thinking Mode）**：

- 用户可在前端开启/关闭 `thinking` 模式，每轮请求可携带 `thinking` 开关。
- 默认模型 `deepseek-v4-flash-vision-exp`。

---

### 2.5 文件读写权限控制（核心安全策略）

| 目录        | 读取    | 写入    | 说明                        |
| ----------- | ------- | ------- | --------------------------- |
| 7个业务目录 | ✅ 允许 | ❌ 禁止 | Agent可读取文件内容用于回答 |
| `tmp/`      | ✅ 允许 | ✅ 允许 | Agent输出文件唯一可写位置   |
| `shared/`   | ✅ 允许 | ❌ 禁止 | 共享资料只读                |

**强制措施**：

- 通过显式**文件访问代理层**实现（不使用 monkey-patch `os.open`）：
  Agent 的全部文件读写经同一代理，内部做路径规范化 + 白名单校验，
  写操作仅限 `tmp/` 且必须带 `thread_id` 前缀，违规抛 `PermissionError`。
- MCP 服务若自身有写能力，在 MCP.json 注册配置中声明权限边界。

**内置工具（本期 6 个）**：

| 工具         | 说明                                                                                      |
| ------------ | ----------------------------------------------------------------------------------------- |
| `read_file`  | 读 7 业务目录 + shared，经权限代理；单文件读取截断到可配上限（默认 32KB），超出提示分段读 |
| `write_file` | 写 `tmp/`，强制 thread_id 前缀                                                            |
| `list_dir`   | 列目录，便于 Agent 发现文件                                                               |
| `grep_files` | 文件内容搜索，限 Agent 可读目录，经同一权限代理                                           |
| `calculator` | 安全表达式求值                                                                            |
| ~~联网搜索~~ | 本期不做（涉及外部 API 依赖与计费，另行立项）                                             |

---

### 2.6 异步与中断控制

**异步持久化**：

- 对话记录写入、文件保存等 I/O 操作均采用**异步**方式。
- **切换页面、新建对话、关闭浏览器均不影响**正在进行的输出和历史保存。

**断连语义**（客户端断开 ≠ 停止）：

- 正在输出的那条 assistant 消息**继续完成并落盘**；
- 若 agentic loop 还有后续步骤（再调工具/再推理），则就此收尾，不开启新步骤；
- 用户重连后从 `history.jsonl` 看到完整回复。

**中断机制**：

- 前端可发送 `stop` 信号（基于 `thread_id`）。
- 后端**中断该 thread 的 SSE 流与推理**，丢弃本轮未保存的消息；
  **不销毁 Agent 实例**（实例回收统一交给 LRU + 空闲超时）。
- 已保存的历史记录不受影响。

---

### 2.7 Token用量统计

**必要性**：监控 Token 消耗用于成本控制或用户计费。

**存储**：引入 **SQLite** 作为用量存储。

> 选型理由：单文件、零部署，契合单机部署形态；按 thread/agent/时间范围的
> 多维汇总查询由 SQL 天然支持。对比候选：纯日志文件（聚合查询需全量扫描，
> 不可行）、Redis（易失，不适合计费数据）、MySQL（运维过重）。

**统计内容**：

- 每轮对话记录一条：`user_id`、`thread_id`、`agent_name`、
  `input_tokens`、`output_tokens`、时间戳。
- 提供汇总查询接口，按 `thread_id`、`agent_name`、时间范围过滤。
- 按日切分的日志文件保留为**审计备份**，不作为查询数据源。

**默认模型**：`deepseek-v4-flash-vision-exp`（2026-09-09 由 `deepseek-v4-flash` 修订）

| 模式       | 模型                                            | 适用场景               |

## 三、异常处理与容灾

### 3.1 文件读写异常

- 若 Agent 尝试写入 7 个业务目录，文件访问代理层抛出 `PermissionError` 并记录日志，
  但**不影响对话流程**（仅提示用户）。
- `tmp` 目录写入失败时，返回友好错误信息（如"临时空间不足，请稍后重试"）。

### 3.2 MCP服务超时

- 全局超时 30 秒（重试 1 次），超时返回 `timeout` 错误，
  Agent 使用"当前服务不可用，请稍后尝试"回应用户。

### 3.3 历史记录损坏

- 若 `history.jsonl` 存在无法解析的行，跳过损坏行加载；
  文件整体损坏时自动**重建**（清空历史），并记录告警日志。

### 3.4 Agent崩溃恢复

- Agent 因未知异常崩溃时，自动销毁该实例，并记录崩溃日志。
- 用户下次发送消息时重新初始化 Agent，保证服务可用。

### 3.5 容量超限

- 实例池满（5 个且无空闲可淘汰）、单用户 thread 并发超 3 时，
  拒绝请求并返回友好提示，不排队。

## 四、非功能需求

| 项目         | 要求                                                                                                                        |
| ------------ | --------------------------------------------------------------------------------------------------------------------------- |
| **容量**     | 单机最多驻留 5 个 Agent 实例；1 用户 : 1 数字人 : 最多 3 并发 thread                                                        |
| **响应延迟** | 非 LLM 接口 P95 ≤ 200ms；对话接口首字延迟 < 5s（收到请求 → 首个 SSE 事件，模型自身推理时间不计）                            |
| **可用性**   | 99.9%（核心对话服务）                                                                                                       |
| **可扩展性** | 本期单机部署，不引入 Redis；"实例池"与"会话状态"收敛为接口后可替换组件，为日后分布式（Redis 会话索引 + 粘性路由）预留扩展点 |
| **日志记录** | 所有操作（文件读写、Agent 初始化、MCP 调用、错误）均记录结构化日志                                                          |

## 五、相对 v1.0 的关键修订

1. ✅ **明确多用户模型**，目录含用户维度；本期默认 admin、不做认证，预留 JWT。
2. ✅ **Agent 实例与对话历史解耦**：实例 key = (user_id, agent_name)，不持有历史，
   历史按 thread_id 注入；`stop`/退出/断连均不销毁实例，回收交给 LRU。
3. ✅ **容量模型修正**：1 用户 : 1 数字人 : 3 并发 thread；池上限 5、空闲超时
   统一 10 分钟；超限拒绝不排队（取代"50 并发"与"30 分钟"的矛盾表述）。
4. ✅ **历史改 JSONL 不分片**；**滚动摘要**（窗口 20 条，异步增量重写，失败降级）。
5. ✅ **权限控制改用显式代理层**，取代 monkey-patch `os.open`。
6. ✅ **MCP 超时统一 30 秒**，建连失败降级就绪。
7. ✅ **SSE 事件分类**（thinking/content/done/error），thinking 可推送但不落盘。
8. ✅ **Token 统计引入 SQLite**（含选型理由），日志文件仅作审计。
9. ✅ **补充 Thread 生命周期接口**与 tmp 清理策略（删 thread 连带清理 + 7 天定期清理）。
10. ✅ **数字人配置本期只读**；`SOUL.md` 为准，SKILL.md 头部用 YAML frontmatter。
11. ✅ **性能口径分层**：非 LLM 接口 P95 ≤ 200ms，对话接口首字延迟 < 5s。
