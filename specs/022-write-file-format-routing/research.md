# 技术调研：PDF 生成方案与中文字体

- **特性**：`022-write-file-format-routing`
- **日期**：2026-11-16
- **宪章条目**：⑥ 依赖治理（新增依赖必须在本文件留痕）

## 问题

`.pdf` 输出必须满足两个硬条件，缺一不可：

1. 生成**合法 PDF 容器**（浏览器内置阅读器能 iframe 打开）；
2. **中文可显示**——项目场景全是中文（BOM、工艺、排程、月报），英文测试完全测不出这个问题。

## 候选方案

| 方案 | 中文 | 依赖 | 结论 |
|---|---|---|---|
| A. `pdfkit` + 嵌入 TTF | ✓ 嵌入真字形 | `pdfkit`（含 `fontkit`） | **采用** |
| B. `pdf-lib` + `@pdf-lib/fontkit` + TTF | ✓ | 两个包，且无内置排版（需自己实现换行/分页/表格） | 淘汰：排版代码量翻倍 |
| C. 手写 PDF + 非嵌入 CID 字体（`STSong-Light` + `UniGB-UCS2-H`） | △ 依赖阅读器替换 | 零依赖 | 淘汰：浏览器 PDFium 上不可靠，等于把"能不能看"交给用户机器的字体，违反交付确定性 |
| D. 生成 PDF 时把文字转成矢量路径 | ✓ | 仍需字体轮廓数据 | 淘汰：无额外收益，体积更大且不可搜索/复制 |
| E. 不做 PDF，改出 `.md`/`.csv` | — | 零 | 淘汰：不满足需求 |

## 为什么字体必须嵌入

PDF 的"标准 14 字体"（Helvetica 等）**只有拉丁字形**，中文会被渲染成方块或空白。
非嵌入的 CJK CID 方案（方案 C）虽然能让 Acrobat 走系统字体替换，但在浏览器内置阅读器
（PDFium）上表现不一致，而我们的预览正是 iframe 内嵌浏览器阅读器。
因此"嵌入 TrueType 子集"是唯一能给出确定结果的路径。

## 字体选型

| 候选 | 许可 | 体积 | 结论 |
|---|---|---|---|
| Noto Sans SC（`@expo-google-fonts/noto-sans-sc`） | SIL OFL 1.1 | 单字重 ~10.5MB | **采用**（400 Regular + 700 Bold） |
| 思源黑体 / Source Han Sans | SIL OFL 1.1 | 同量级 | 等价，未选（包结构不如前者规整） |
| 系统字体（`msyh.ttc` / `simhei.ttf`） | 商业许可，禁止随产品分发 | — | 淘汰：许可风险，且 Linux 部署无此文件 |

字体以 **npm 依赖**形式引入（而非把 TTF 提交进仓库），好处是：许可随包分发、版本可锁、
部署走 `npm install` 即可，不需要额外的资产同步步骤。

## 性能与内存

- 单字重 ~10.5MB，`registerFont` 时由 fontkit 解析并**按需子集化**（只嵌入用到的字形），
  因此产出的 PDF 只有几十 KB，而不是 10MB。
- 字体字节**进程级缓存**（`encoders/pdf.ts` 的 `fontCache`），
  避免每份 PDF 都从磁盘重读 10MB；常驻上限 = 两份字重 ≈ 21MB。
- 实测：单份两页中文 PDF 生成耗时 ~100–150ms（含首次字体解析，之后显著更快）。

## 新增依赖清单

| 包 | 类型 | 用途 | 许可 |
|---|---|---|---|
| `pdfkit` | dependency | PDF 排版与产出（内含 `fontkit` 做字体子集） | MIT |
| `@types/pdfkit` | devDependency | 类型定义 | MIT |
| `@expo-google-fonts/noto-sans-sc` | dependency | 中文字体（400/700 两个 TTF） | SIL OFL 1.1 |

`.xlsx` **未新增依赖**：复用已有 `xlsx`（SheetJS 0.18.5）。

## 未走通的替代路线（留痕）

- 用 `pdfjs-dist` 生成 PDF：它是**只读**解析器，无写入 API。
- 用 `sharp`/`canvas` 先把文字画成图片再塞进 PDF：中文渲染仍需字体文件，且产出不可搜索、
  体积大，属于"多绕一步还更差"。
