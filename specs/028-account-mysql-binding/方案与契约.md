## 2. 设计口径与关键决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | **JWT `sub` 恒为 `user_id`，不是手机号** | `agent-backend` 用 `sub` 作 `.opt-agent/users/{uid}/` 目录名，53 处 `getCurrentUser()` 零改动；手机号只作登录标识与唯一索引 |
| D2 | 注册用户 `user_id` 由服务端生成：`u_` + 12 位小写十六进制 | 通过 `isSafeName()`（无路径分隔符/`..`），不与存量 `admin` 等冲突 |
| D3 | 存量无手机号用户 `phone = NULL`，仍可用 `user_id` 登录 | 唯一索引允许多 NULL；不破坏 024 与现有 4 个存量用户 |
| D4 | **只迁账号域**；`meta.json` revision、agents/skills/MCP/本体 仍留 `.platform-data` | 避免双权威源；`PlatformStore.withRevision()` 继续作配置写入唯一乐观锁；`Deployer` 的 `assertRevision` 语义不变 |
| D5 | `STORAGE_DRIVER=file\|mysql` 开关，默认 `file` | 与 024「未配 `AUTH_SECRET` 即回退 legacy」同口径；可灰度、可回滚，现有 45 个接口行为不变 |
| D6 | 授权状态用单表 `user_agent_grants` 三态表达，不另建申请表 | 原型中「申请中」就是 `auth[rid]='pending'`，一张表覆盖申请/审批/关闭 |
| D7 | 注册**不自动登录** | 与原型一致（注册成功切到登录表单），也避免绕过 024 的单会话登记 |
| D8 | 管理台全局鉴权**开关化、后置到阶段 4** | 分支 `ncc-1124` 的 `admin-frontend` 仍只有 5 个功能区、**无登录页、无路由守卫**；直接加全局钩子会让后台全挂 |
| D9 | 绑定与部署**解耦** | 授权只决定「能否使用」，部署仍由 `users.agents[]` 驱动。二者衔接方式见 §6 |

### 2.1 数字人服务基本信息的最小字段

用户要求「编码 + 名称就可以」。为让授权能真正落到运行端，最小必需为**三列**：

| 列 | 用途 |
|---|---|
| `code` | 数字人编码，如 `DH-BOM001`；注册链接携带、对外展示。**2026-11-27 起可由平台生成**（`POST` 省略即生成 `DH-` + 5 位去混淆 Base32，见 §17），创建后不可改 |
| `name` | 展示名 |
| `platform_agent_name` | **绑定落点** = `.platform-data/agents/{name}.json` 的 `name`。缺了它，授权记录无法在部署时物化成 `agents/{数字人}`，绑定就是空转 |

原型 5 个数字人与平台文件的映射（迁移脚本按此初始化）：

| `code` | `name` = `platform_agent_name` | 原型内部 id |
|---|---|---|
| `DH-KKB0M7` | 柯昆BOM数字人 | `kekun-bom` |
| `DH-SCHED2` | 生产调度测试 | `sched-test` |
| `DH-PLAN5` | 生产计划助手 | `plan-helper` |
| `DH-FRESH9` | 生鲜识别辅助 | `fresh-rec` |
| `DH-BOM001` | BOM数字人 | `bom` |

> 当前 `.platform-data/agents/` 下正好是这 5 个同名文件，迁移可直接对齐。

## 3. 数据模型

DDL 见同目录 `schema.sql`（MySQL 8.0+ / utf8mb4，可直接执行，可重复执行）。

| 表 | 作用 | 主键 / 唯一键 |
|---|---|---|
| `agent_services` | 数字人服务基本信息 | `code` 唯一 |
| `users` | 账号（含角色、密码摘要、注册来源） | `user_id` 唯一、`phone` 唯一（可空） |
| `register_links` | 专属注册链接（高熵 token、过期、撤销、计数） | `token` 唯一 |
| `user_agent_grants` | **用户 × 数字人服务绑定/授权**（三态） | `(user_id, agent_code)` 唯一 |
| `sessions` | 单会话登记 | `user_id` 主键 |

关系：`users.user_id ← user_agent_grants.user_id`；`agent_services.code ← user_agent_grants.agent_code / register_links.agent_code`；删除用户级联删 grants 与 sessions。

### 3.1 原型 → 后端字段映射

| 原型（`localStorage.dh_reg_proto_v1`） | 后端 |
|---|---|
| `users[phone].name` | `users.display_name` |
| `users[phone].pwd`（**明文**） | `users.password`（scrypt 摘要，绝不明文；2026-11-28 由 `password_record` 更名，与文件模式字段同名） |
| `users[phone].phone`（对象 key） | `users.phone` |
| —（新增） | `users.user_id`（JWT sub / 运行目录名） |
| `users[phone].robot` | `users.source_agent_code` + `user_agent_grants(source=register_link, status=approved)` |
| `users[phone].auth[rid]` = `approved`/`pending`/`none` | `user_agent_grants.status` = `approved`/`pending`/`revoked`（`none` 用行不存在表达） |
| `users[phone].regAt` | `users.created_at` |
| `ROBOTS[].code / name / id` | `agent_services.code / name`（`id` 不入库，统一用 `code`） |
| `ADMIN_ACCOUNTS.admin` | `users(role='admin')`，走同一套 024 登录 |

## 4. 接口契约

**通用约定**：沿用 `specs/001` §0 —— 基址 `/api/admin/`、`application/json`、字段下划线、错误体 `{ error: { code, message, details? } }`。账号域写接口**不用** `revision` 乐观锁（由 MySQL 事务保证）；设计态写接口的乐观锁口径不变。

**权限标记**：`公开` = 免登录；`登录` = 需有效 Cookie；`本人` = 只能操作自己的资源；`管理员` = 需 `role='admin'`（阶段 4 起强制）。

### 4.1 注册与登录（扩展 024）

#### `POST /api/admin/auth/register` · 公开 · 新增

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `link_token` | string | ✅ | 高熵串；须存在、未过期、未撤销、对应服务 `enabled` |
| `phone` | string | ✅ | 11 位手机号（原型校验规则） |
| `display_name` | string | ✅ | ≥2 字符 |
| `password` | string | ✅ | 6~128 字符（复用 `password.ts` 同一约束） |

- **事务**：校验链接 → 手机号未占用 → `INSERT users(role='user', source_agent_code=<link.agent_code>)` → `INSERT user_agent_grants(status='approved', source='register_link')` → `register_links.use_count + 1`。任一步失败整体回滚。
- **201**：`{ "user_id": "u_…", "phone": "…", "display_name": "…", "granted_agent": { "code": "DH-BOM001", "name": "BOM数字人" } }`
- **错误**：`VALIDATION_FAILED`(400)、`ADM_INVALID_LINK`(400)、`ADM_PHONE_TAKEN`(409)、`ADM_AGENT_SERVICE_NOT_FOUND`(404)
- 不下发 Cookie（注册不自动登录，D7）；密码明文不进响应、不进日志。

#### `GET /api/admin/auth/register-links/:token` · 公开 · 新增

注册页渲染用（展示「专属注册链接 · 注册成功即自动获得权限」）。

- **200**：`{ "agent": { "code", "name" }, "expired": false }`
- **错误**：`ADM_INVALID_LINK`（无效 / 过期 / 已撤销 / 服务已停用，统一同一码，不枚举）

#### `POST /api/admin/auth/login` · 公开 · **扩展（不改路径）**

- 请求体由 `{ user_id, password }` 扩展为 `{ user_id?, phone?, password }`，二者至少其一；`phone` 命中后解析为 `user_id` 再验密码。
- 失败仍是**统一** `ADM_INVALID_CREDENTIALS`（账号不存在 / 密码错误 / 无密码 / 账号 disabled，不枚举，024 `FR-011`）。
- **200** 与 024 逐字一致：`{ "user_id": "…" }` + `Set-Cookie: optagent_auth=<jwt>; HttpOnly; Path=/; SameSite=Lax; Max-Age=<ttl>`。

#### `GET /api/admin/auth/me` · 登录 · **扩展响应**

保留 `user_id` 字段（前端兼容），新增：`{ "user_id", "phone", "display_name", "role" }`。错误码 `ADM_UNAUTHENTICATED`(401) 不变。

#### `GET /api/admin/auth/session/valid` · 公开 · 不变

`agent-backend` 内省端点，query `{ user_id, session_id }` → `{ valid }`。**不得改动**：运行侧 `createIntrospector()` 按此契约调用。

#### `POST /api/admin/auth/logout` · 登录 · 不变

### 4.2 授权（绑定关联）

#### `GET /api/admin/auth/my-agents` · 登录 · 新增

当前登录用户**已授权**的数字人服务列表，供对话工作台「切换数字人」渲染。

- **200**：`{ "items": [ { "code", "name", "status": "approved" } ], "pending": [ { "code", "name" } ] }`
- 只返回 `approved` 与 `pending`，`revoked` 不下发。

#### `POST /api/admin/grants/apply` · 本人 · 新增

对话界面「切换数字人 → 申请」。`user_id` **取自会话，不放请求体**（防越权）。

- 请求体：`{ "agent_code": "DH-FRESH9" }`
- 已 `approved` → 200 幂等；无记录或 `revoked` → 置 `pending`（`source='apply'`）；`pending` → 200 幂等。
- **错误**：`ADM_AGENT_SERVICE_NOT_FOUND`(404)、`ADM_UNAUTHENTICATED`(401)

#### `GET /api/admin/grants` · 管理员 · 新增

授权总账 / 审批队列（对应原型「授权审批」与「账户管理 → 授权详情」）。

- query：`status`（`pending|approved|revoked`）、`agent_code`、`phone`、`page`
- **200**：`{ "items": [ { "user_id", "phone", "display_name", "agent_code", "agent_name", "status", "source", "created_at", "reviewed_at" } ], "total", "page" }`

#### `POST /api/admin/grants/approve` · 管理员 · 新增

- 请求体：`{ "user_id", "agent_code" }`
- `pending|revoked` → `approved`，写 `reviewed_by` / `reviewed_at`；记录不存在 → `ADM_GRANT_NOT_FOUND`(404)。

#### `POST /api/admin/grants/revoke` · 管理员 · 新增

- 请求体：`{ "user_id", "agent_code" }`
- `approved|pending` → `revoked`。**不删行**，保留审计轨迹；重建授权走 `approve`。

### 4.3 专属注册链接（管理员）

| 接口 | 权限 | 说明 |
|---|---|---|
| `GET /api/admin/register-links` | 管理员 | 列表，可按 `agent_code` 过滤；带 `use_count`、`expires_at`、`revoked_at` |
| `POST /api/admin/register-links` | 管理员 | body `{ "agent_code", "expires_in_seconds?": 604800 }` → **201** `{ "token", "url", "expires_at" }`；`token` 用 `randomBytes(24).toString('base64url')` |
| `DELETE /api/admin/register-links/:token` | 管理员 | 置 `revoked_at`（软撤销），**204** |

错误：`ADM_AGENT_SERVICE_NOT_FOUND`(404)、`VALIDATION_FAILED`(400)。

### 4.4 数字人服务基本信息

| 接口 | 权限 | 说明 |

| 接口 | 变更 |

## 5. 错误码登记（原则七：四处同步）

新增码需同步：`admin-backend/src/domain/error-codes.ts`、`admin-frontend/src/constants/error-messages.ts`、`specs/001…/contracts/admin-api.md` §0.4、本文件；并通过 `npm run check:contract`。

| 码 | HTTP | 含义 |
|---|---|---|
| `ADM_PHONE_TAKEN` | 409 | 手机号已注册 |
| `ADM_INVALID_LINK` | 400 | 注册链接无效 / 过期 / 已撤销 / 服务停用（不枚举） |
| `ADM_AGENT_SERVICE_NOT_FOUND` | 404 | 数字人服务编码不存在 |
| `ADM_AGENT_SERVICE_IN_USE` | 409 | 服务已被授权或生成链接，禁止删除 |

## 6. 授权模型与部署关联的关系（必须区分）

> **本节已被 §16 取代（2026-11-27）**：双源模型废止——「授权 = 关联」，`users.agents[]` 是唯一
> 真相源，`user_agent_grants` 表/文件与迁移脚本均已删除。以下内容仅作原始设计记录保留。

| | 部署关联 `users.agents[]` | 使用授权 `user_agent_grants` |
|---|---|---|
| 语义 | 决定部署时把哪些数字人配置物化到 `.opt-agent/users/{uid}/agents/` | 决定用户**能不能看到 / 使用**某个数字人服务 |
| 权威源 | `.platform-data/accounts/users/*.json`（阶段 1 起由 MySQL 投影） | MySQL `user_agent_grants`（唯一） |
| 消费者 | `Deployer.resolveTargets()`、`references.ts`、`UnifiedCatalog` | 前端「切换数字人」、`my-agents`、阶段 4 服务端强校验 |
| 是否等同 | **否** | **否** |

**衔接规则**：注册成功只写 `user_agent_grants(approved)`，**不自动写** `users.agents[]`；管理员仍需按现有流程部署该用户，运行端才有对应数字人目录。

若要做「授权通过即自动部署」，按当前分支语义只需调用一次单用户部署：

```
deployer.deploy([user_id], store.revision())
```

- 部署已无预检、无「整批零写入」；该用户失败只落在 `users[].error`，**不影响其他用户**（`Deployer.deploy()` 逐用户 try/catch）。
- 仍需 `revision` 乐观锁，且该用户必须已有 `users.agents[]` 记录——所以联动本身还要决定「是否同时把 `platform_agent_name` 合并进 `agents[]`」。
- **此项默认不做**，待确认（见 §10）。

## 13. 账号维护入口收敛（2026-11-27，已落地）

**背景**：合并后管理员有两条入口能改同一批用户——部署区 `UserCardList`（建号 / 改关联 /
重置密码 / 删除）与用户管理 `UsersArea`（同一批能力 + 手机号、角色、来源、授权审批）。
两处调用同一组 `/api/admin/users*` 接口与同一个编辑弹窗，属于重复入口；两页同时编辑
还会因 `revision` 乐观锁互打 409。

**决策**：账号域只保留**一个**维护入口，部署区回归"部署谁"。

| 能力 | 收敛前 | 收敛后 |
|---|---|---|
| 建号 / 改关联 / 重置密码 / 删除 | 部署区 + 用户管理 | **仅用户管理** |
| 勾选部署对象 / 部署 / 撤回 / 部署状态 | 部署区 | 部署区（不变） |
| 授权审批 / 撤销 | 用户管理 | 用户管理（不变） |

## 14. 账号域目录结构收敛（2026-11-27，已落地）

**背景**：阶段 2/3 把三份集合放进 `.platform-data/accounts/`，而账号主档与会话登记

├── sessions/{uid}.json           ← 迁移前 .platform-data/sessions/{uid}.json
├── agent-services.json           （不变）
└── register-links.json           （不变）

> 见 §16；文件、路径常量 `USER_AGENT_GRANTS_FILE`、迁移模块与 `migrate:grants-to-agents`
> 脚本同批移除，未保留历史副本）。

**迁移**：`npm run migrate:accounts-layout`（`scripts/migrate-accounts-layout.ts` +
`src/infra/accounts-layout-migration.ts`）。

| 项 | 口径 |
|---|---|
| 语义 | **复制而非移动**，旧目录原样保留，删不删由人工决定 |

## 17. 数字人服务编码由平台生成（2026-11-27，已落地）

**问题**：`POST /api/admin/agent-services` 原本**强制调用方传 `code`**——`normalizeAgentCode`
拿到 `undefined` 即空串 → 400。界面上又没有"新建服务"入口，编码实际全靠脚本/curl 手写，
既有 5 条（`DH-KKB0M7`、`DH-SCHED2`、`DH-PLAN5`、`DH-FRESH9`、`DH-BOM001`）就是一次性批量灌入。

**决策**：**平台是编码的唯一生成者**。`code` 改为可选：省略或空串 → 后端生成、响应回显；
显式提供仍按原规则校验（导入历史数据、指定可读语义码时使用）。

**形态**：`DH-` + 5 位 Crockford Base32，字符集 `23456789ABCDEFGHJKMNPQRSTVWXYZ`
（刻意去掉 `I/L/O/U/0/1`——编码会被贴进注册链接、口头传达、手工输入），共 30^5 ≈ 2430 万组合。

**为什么不是别的方案**：

| 方案 | 否决理由 |
|---|---|
| 前端生成 | 多客户端会撞码、离线脚本仍要自己生成，规则出现第二份真相源（平台不再权威） |
| 序号 `DH-0001` | file 驱动要多维护 `next_seq`（存量 5 条还要补号），MySQL 侧再同步一份计数器；为零收益引入可变状态 |
| 名称派生（`DH-PLAN5` 风格） | 中文名无法 slug；拼音首字母重复率高（生产计划/生产调度），还得引入拼音依赖 |

**语义边界（MUST）**：

| 概念 | 含义 | 可否生成 |
|---|---|---|
| `code` | 服务对外**不可变标识**（注册链接、审计、用户来源都引用它） | ✅ 平台生成，创建后不可改 |
| `platform_agent_name` | 平台设计态数字人名 = 部署落点 | ❌ 必须由调用方指定并校验存在 |
| `name` | 展示名，可改 | ❌ 无默认值 |

**创建 = 插入，改 = upsert**：mysql 侧原 `saveAgentService` 是
`INSERT ... ON DUPLICATE KEY UPDATE`，若拿它做创建，自动生成编码在极端并发下会**静默覆盖**
别人的服务（名称/落点被改写）。现在端口新增 `insertAgentService`（纯 INSERT），撞码抛
`DuplicateAgentCodeError`；生成路径换码重试 3 次，耗尽报 `INTERNAL_ERROR`（平台内部问题，
不是调用方输入错误，故非 400）。

**改动**：

- 新增 `admin-backend/src/domain/account/agent-code.ts`：`randomAgentCode()` / `generateAgentCode()`
  （随机源可注入，默认 `crypto.randomInt`），查重耗尽 → `INTERNAL_ERROR`。
- `account-store.ts` 端口新增 `insertAgentService()` 与 `DuplicateAgentCodeError`；file / mysql
  两实现补齐（mysql 用纯 `INSERT`，命中重复键即抛该错误）。
- `agent-services.ts`：`create({ code?: string, ... })`；省略走 `createWithGeneratedCode()`，
  显式走原校验 + 插入。
- `routes/agent-services.ts`：`code` 为 `undefined/null/''/全空白` → 视为省略，交给平台生成。
- 前端 `AgentServiceCreatePayload.code` 改为可选，并注明"必须以响应值为准，不得本地预生成"；
  `createAgentService()` 补文档（管理台目前仍无建服务界面，只有列表）。
- 测试：新增 `tests/unit/agent-code.spec.ts`（形态/字符集/去混淆/查重重试/耗尽语义）；
  `tests/integration/account.spec.ts` 增 3 条——省略生成（并验证注册链接可直接引用生成码）、
  连续两次生成不同、空串与全空白等同省略。

**验证**：`admin-backend` typecheck 通过；744 tests / 63 files（11 跳过为 MySQL 驱动用例）全绿，
其中 `agent-code` 7 条、账号集成 12 条。契约与规格同步：`contracts/admin-api.md` §13
`agent-services` 行、本章 §2.1 字段说明与 §4.4 端点表。

## 18. 数字人 ⇔ 服务编码 1:1：创建即开通（2026-11-27，已落地）

**现象**：新建/复制的数字人卡片显示「未配置注册服务」，而老数字人（如 `DH-SCHED2`
「生产调度测试」）有编码。原因不是生成器失效，而是**两个实体从未联动**：

| 实体 | 存放 | 由谁创建 |
|---|---|---|
| 数字人（设计态） | `.platform-data/agents/{name}.json` | `POST /api/admin/agents`（新建与「复制」同一接口） |
| 数字人服务（含 `code`） | `.platform-data/accounts/agent-services.json` | 只有 `POST /api/admin/agent-services`，且**管理台无此界面** |

卡片（`AgentCardList.vue`）按 `platform_agent_name` 去服务清单里找编码：老数字人的 5 条服务
是早期一次性灌入的，所以有码；新数字人没有服务记录 → 显示「未配置注册服务」。
实测缺口：`.platform-data/agents/` 有 6 个数字人，服务只有 5 条，缺的正是 `test00711`。

**决策**：**一个数字人 ⇔ 一条服务**（1:1）。`POST /api/admin/agents`（新建与复制）在写入
设计态后 MUST **自动开通**服务：`code` 平台生成（§17）、`name` 与 `platform_agent_name`

**级联与保护**：

| 场景 | 行为 |
|---|---|
| 创建 / 复制数字人 | 自动开通服务（幂等：已存在则原样返回，不改人工改过的名称或启停） |

# 17. 029 对齐修订（2026-11-28）

028 定下的表结构与口径，在 029「账号域切库验证」中被逐项核对，产生四处修订。

## 17.1 配置版本（`revision`）口径修正

028 阶段 MySQL 实现把账号域写操作视为"不占设计态版本"（响应里回只读快照）。这与文件模式不一致：
同一套管理台、同一个旧版本提交，两种存储一个 409 一个成功。

029 修订为与文件模式同一语义：**新建 / 改授权 / 删号推进版本，改密不推进**；
顺序固定为「校验 → 写入 → 推进」。版本文件仍由 `PlatformStore`（`meta.json`）持有，不进数据库。

## 17.2 去掉两条外键

`fk_users_source`（`users.source_agent_code` → `agent_services.code`）与
`fk_register_links_agent`（`register_links.agent_code` → `agent_services.code`）被删除，
各自索引保留：

- 数字人是**会消失的对象**（改名、下线、删除），外键会把"删除数字人 / 迁移"顶在库层报错，
  而这些场景的语义应由领域层决定（软撤销 + 影响面统计）；
- 历史链接必须能指向已删除的数字人，这是"注册链接台账"的既有行为。

`sessions.user_id → users.user_id` 保留：会话没有独立生命周期。

## 17.3 去掉 `users.status`

文件模式的账号记录没有状态字段，MySQL 侧多一列会造出"库里 disabled、界面照常登录"的假象。
账号状态若将来需要，应作为账号域正式字段两侧同时引入。

## 17.4 升级动作（既有库）

```sql
-- 先查存在性
SELECT CONSTRAINT_NAME FROM information_schema.TABLE_CONSTRAINTS
 WHERE TABLE_SCHEMA = DATABASE()
   AND CONSTRAINT_NAME IN ('fk_users_source','fk_register_links_agent');
-- 存在则执行
ALTER TABLE users DROP FOREIGN KEY fk_users_source, DROP COLUMN status;
ALTER TABLE register_links DROP FOREIGN KEY fk_register_links_agent;
```

新建库无需此步骤（`schema.sql` 已是修订后形态，`npm run db:init` 可重复执行）。
