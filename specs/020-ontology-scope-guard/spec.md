# 功能规格：本体行为权限闸门（工具调用前置授权）

**Feature Branch**: `020-ontology-scope-guard`

**Created**: 2026-11-08

**Status**: 草稿（口径已收敛，待评审）

**Input**: User description: "新增一个权限判断需求，类似在工具调用上做一个 wrap 进行包装：1）调用工具前，判断该工具所属的本体以及行为；2）如果不是本体行为则通过（不阻断执行）。如果是本体行为，则读取对应的 securities.yaml，提取 action_name 以及对应的 scope（即授权的用户名）；3）若 scope 包含 everyone，则通过；如果 scope 包含 disable，则直接报错拒绝执行该工具；4）如果不包含 everyone 和 disable，判断当前数字人的所属【用户名】是否在 scope 里，如果在则表示授权通过，否则直接报错拒绝执行该工具。"

## 1. 背景与目标

本体市场为每个行为提供了安全管控文件 `securities.yaml`（`action_name` / `scope` / `confirm` /
`confirm_content`），平台侧的约定是"**原样存取与下发、不解析语义，安全管控的执行在运行环境**"。
现状是：运行环境把这份文件**原样物化**到数字人目录，但**从未读取**——`scope` 写什么都没人执行，
行为管控形同虚设。

本特性把这半条链路补齐：在工具真正执行**之前**加一道以"本体行为"为粒度的授权闸门。

- 判定对象：本轮模型可调用的**每一个工具**；
- 判定依据：该工具是否对应某个已部署本体的行为，以及该行为 `scope` 是否授权给**当前数字人的归属用户**；
- 判定结果只有两种：**放行**（原样执行）或**拒绝**（不执行、留痕、给模型可读文案）。

闸门只做"能不能执行"，不改变工具本身的入参、返回值与既有安全层（文件沙箱、签名直链、人工确认）。

## 2. 用户场景与测试 *(mandatory)*

### 用户故事 1 - 授权用户能跑，未授权用户被拦 (Priority: P1)

数字人「采购助手」被授权给用户 `admin` 使用。其本体 `原材料采购和库存` 的
`CreatePurchaseRecord`（创建原材料采购单）在 `securities.yaml` 里只登记了 `scope: [admin]`。
`admin` 在聊天里要求"给高强度钢板下一张 50 吨的采购单"，模型调用该工具，工具正常执行、采购单真实落库；
换到同一数字人的另一份部署（归属用户 `zpf`），同样一句要求，模型照样发起调用，系统**当场拒绝**：
工具不执行、不产生任何采购单，卡片标红并写明"该行为未授权给当前用户"，同时留下一条可检索的日志。
`admin` 之外的人不会因为"模型不知道权限"而误改业务数据。

**为何优先级最高**：这是本需求交付的全部价值——把写在 `securities.yaml` 里的授权意图变成真实约束。
没有这一条，`scope` 只是给人看的注释。

**可独立验证**：同一本体行为构造两份部署（scope 含当前用户名 / 只含他人），分别在聊天里触发同一句
要求调用：前者成功且业务数据变化，后者被拒绝、业务数据零变化、卡片标红、日志可查。
不依赖 `disable` 分支与跨本体同名场景。

**验收场景**：

1. **Given** 数字人归属用户名 `admin` 且目标行为 `scope: [admin]`，**When** 模型调用该行为工具，**Then** 工具按原样执行，结果与无闸门时完全一致。
2. **Given** 同一行为 `scope: [admin]` 而当前数字人归属用户为 `zpf`，**When** 模型调用该工具，**Then** 调用被拒绝、工具未执行、无任何业务副作用，返回"未授权"一类原因。
3. **Given** 拒绝已发生，**When** 用户查看会话，**Then** 该工具卡片以失败态呈现（标红），文案说明是哪个行为、哪个本体的授权问题，且**不展示**任何授权用户名清单。
4. **Given** 被拒绝后模型在同一轮或下一轮再次尝试同一工具，**Then** 仍被拒绝（判定与尝试次数无关）。
5. **Given** 工具并非本体行为（内置文件工具、或不属于任何已部署本体的 MCP 工具），**When** 调用，**Then** 直接执行，闸门不产生任何拦截、告警或额外延迟。

---

### 用户故事 2 - 一条 `disable` 立即停用高危行为，`everyone` 全放开 (Priority: P2)

安全事件发生时，管理员在本体侧把高危行为（如 `CancelPurchaseRecord` 取消采购单）的 `scope`
改成 `disable`，重新部署到运行环境。下一次任何用户要求取消采购单，模型再怎么劝都调不动这个工具：
拒绝文案明确写"该行为已停用"，日志留下记录。反过来，把某个查询类行为的 `scope` 改成 `everyone`，
所有用户无需逐个授权即可使用。整个过程不改代码、不重启服务，重新部署后的下一次调用即按新口径执行。

**为何优先级次之**：没有 `disable`，紧急关停只能靠下线数字人或改代码；没有 `everyone`，公共查询行为
要挨个点名授权，运维成本高。两者都是 P1 授权模型的自然延伸。

**可独立验证**：把同一行为依次改成 `everyone` → `disable` → `[admin]`，每次部署后用固定一句要求触发调用，
观察三次判定结果与文案是否与配置一致；全程不重启服务。

**验收场景**：

1. **Given** 行为 `scope: [everyone]`，**When** 任意归属用户的数字人调用，**Then** 放行。
2. **Given** 行为 `scope: [disable]`，**When** 任意用户调用，**Then** 拒绝，原因分类为"已停用"，文案写明该行为已被停用。
3. **Given** 行为 `scope: [everyone, disable]`，**When** 调用，**Then** 拒绝（停用优先于放行）。
4. **Given** 行为 `scope` 从 `[admin]` 改为 `[zpf]` 并重新部署，**When** `admin` 的数字人在同一会话中再次调用，**Then** 按新配置拒绝；无需重启、无需新建会话。
5. **Given** 行为已 `disable`，**When** 该行为在本轮被并行批次调用，**Then** 每个调用各自被拒绝，无一漏网。

### 用户故事 3 - 拒绝可追溯，配置异常不被静默吞掉 (Priority: P3)

管理员事后要能回答"谁、在什么时候、想调哪个行为、为什么被拦"。每条拒绝都留下结构化记录
（用户、数字人、会话、工具、本体、行为、原因分类），可按用户或行为检索。若某个本体行为在
`securities.yaml` 里**找不到条目**、文件损坏或结构非法，系统不会假装"没配置就是放行"，而是同样拒绝
并打出告警级记录——问题暴露在日志里，而不是变成一次悄悄放过的越权调用。未部署任何本体的数字人
则完全不受影响，日志里不会因此多出噪声。

**为何优先级第三**：判定正确之后，"为什么被拦"决定了这套机制能否被运维与用户信任；没有可观测性，
一次误拒会被当成"系统坏了"，一次漏拒则无人知晓。

**可独立验证**：制造三类情形（正常拒绝 / `disable` 拒绝 / 缺条目），确认每类都有一行带上述字段的日志、
且文案与原因分类一一对应；对一个没有部署任何本体的数字人跑一轮工具调用，确认零拒绝、零告警。

**验收场景**：

1. **Given** 一次未授权拒绝，**When** 查看运行日志，**Then** 有且仅有一条对应记录，含用户、数字人、会话、工具名、本体名、行为名与原因分类。
2. **Given** 本体行为在 `securities.yaml` 中无对应 `action_name` 条目，**When** 调用，**Then** 拒绝并给出"管控配置不可用"一类原因，日志为告警级且指明缺条目的本体与行为。
3. **Given** `securities.yaml` 缺失、无法解析或 `scope` 不是字符串数组，**When** 调用该本体的任意行为，**Then** 一律拒绝并告警，**MUST NOT** 因文件问题放行。
4. **Given** 数字人所属用户的数字人目录下没有任何本体，**When** 正常对话并调用工具，**Then** 全部放行，无拒绝记录、无告警。
5. **Given** 一次拒绝，**When** 查看会话历史与统计，**Then** 该次调用不计入实际发生的 MCP 调用次数（它从未真正发出）。

### 边界情况

- **MCP 工具名带服务前缀**：运行环境暴露给模型的 MCP 工具名形如 `{服务名}__{工具名}`，但"工具名本身就是行为名"的 MCP 服务同样存在。归属识别 MUST 同时尝试**完整工具名**与**去掉首个 `__` 前缀之后的名字**（口径见 `FR-003`），任一形态命中即视为本体行为；两种形态都匹配不到时才按"非本体行为"放行。
- **同名行为出现在多个已部署本体**：同一行为名被两个本体同时声明时，判定**拒绝优先**（任一本体判定拒绝即拒绝），并记一条 warning 指出冲突，避免"靠运气放行"。
- **大小写或首尾空白差异**：行为名、`action_name`、`scope` 元素、当前用户名一律去首尾空白后按**大小写不敏感**比较，避免同一行为因书写差异绕过管控。
- **`scope` 为空数组**：视为"未授权任何人"，拒绝。
- **`scope` 含无法识别的标记**（如 `root`、拼错的名字）：不猜测语义，按普通用户名参与比较；当前用户名不在其中即拒绝。
- **`scope` 元素不是字符串**（数字、对象、空值）：该元素忽略；若过滤后为空则按空 `scope` 处理（拒绝）。
- **当前数字人归属用户未知或为空**：无法完成判定 → 拒绝并告警，**MUST NOT** 以"空用户名等于某个 scope 元素"的形式放行。
- **同一轮并行调用多个工具**：逐个独立判定；一个被拒不影响同批其他工具的判定与执行。
- **拒绝与人工确认的先后**：授权判定在人工确认**之前**完成；已判定拒绝的调用 MUST NOT 向用户弹出确认框。
- **工具名匹配不到任何行为**：按"非本体行为"放行（不进入 `securities.yaml` 读取）。
- **本体目录或 `ontology.yaml` 损坏/不可读**：行为清单无法解析，无法认定工具是否属于本体行为 → 按"非本体行为"放行，并记一条 warning（不因目录残缺拒绝整轮对话）。注意：这是"识别不出行为"的放行，与 `FR-022`"已识别行为但管控不可用"的拒绝是两种不同情形，不可混用。
- **同一数字人存在多份同名本体文件**：以物化目录中的本体为单位分别判定；出现冲突时按"同名多本体"口径处理。
- **部署更新与读取并发**：部署按数字人整体覆盖，判定方 MUST 读到完整文件（任一次判定不得读到半更新内容）；更新后下一次调用即按新值判定。
- **数字人切换**：判定始终以**当前请求的归属用户 + 当前选中数字人**为准，切换数字人后不会沿用另一个数字人的判定结果。
- **拒绝后模型自行改写参数重试**：仍按行为粒度拒绝（判定不看参数）。
- **工具本身执行失败**（非权限问题）：错误分类与权限拒绝不同，不得混为一谈（用户与日志都能区分）。
- **读屏与视觉**：拒绝仅以"失败卡片 + 文案"表达，颜色不是唯一线索（沿用既有工具失败态）。

## 需求 *(mandatory)*

### 功能需求

**判定入口与归属识别**

- **FR-001**：本轮暴露给模型的**每一个**工具，在真实执行前 MUST 经过授权判定（内置工具与 MCP 工具一视同仁）；该闸门 MUST NOT 提供"按数字人关闭"或"按服务关闭"的旁路开关。
- **FR-002**：授权判定 MUST 早于人工确认（HITL）；已判定拒绝的调用 MUST NOT 进入确认流程，也 MUST NOT 向用户弹出确认界面。
- **FR-003**：归属识别 MUST 以**工具原始名**为键，且 MUST 同时尝试两种形态——**完整工具名**，以及去掉 MCP 服务前缀 `{服务名}__` 之后的名字；任一形态与已部署本体的 `behaviors[].name` 匹配即视为本体行为（两种都命中按 `FR-015` 的多本体口径处理）。比对口径为去首尾空白、大小写不敏感。两种形态都匹配不到时，该工具 MUST 视为"非本体行为"并直接放行。
- **FR-004**：归属本体 MUST 由提供该行为的本体文件给出（场景名 + 本体名），用于模型可见文案与结构化记录；MUST NOT 依据服务名、工具说明或人工维护的映射表反推。
- **FR-005**：判定 MUST 只到**行为**粒度：不得因工具参数内容、调用次数、调用时间或历史结果改变结论。

**授权判定**

- **FR-006**：识别为本体行为后，MUST 读取该行为所属本体的 `securities.yaml`，按 `action_name` 找到对应条目（比对口径同 `FR-003`），取其 `scope`。
- **FR-007**：`scope` 含 `everyone` MUST 放行。
- **FR-008**：`scope` 含 `disable` MUST 拒绝，且该拒绝优先于 `everyone`（两者同时出现时结果为拒绝）。
- **FR-009**：`scope` 既不含 `everyone` 也不含 `disable` 时，当前数字人的归属用户名在 `scope` 中 MUST 放行，否则 MUST 拒绝。
- **FR-010**："当前数字人的归属用户名" MUST 等于该数字人部署所在目录的归属用户标识（`users/{用户名}/`），由服务端在请求上下文中确定；模型、前端与工具入参 MUST NOT 指定或影响该值。
- **FR-011**：`scope` 为空数组、或过滤无效元素后为空 MUST 视为"无任何授权"并拒绝；MUST NOT 把"没有配置"解释成"所有人都可以"。
- **FR-012**：`everyone` / `disable` MUST 作为保留标记识别（去空白、大小写不敏感），MUST NOT 允许某个用户名恰好等于这两个词来表达授权。

**拒绝语义与可观测**

- **FR-013**：拒绝 MUST NOT 执行工具、MUST NOT 产生任何业务副作用（不写文件、不落业务数据、不发出 MCP 请求）。
- **FR-014**：拒绝原因 MUST 按三类区分，并使用三个互不相同的错误码：
  - 未授权（当前用户不在 `scope`）：`ONTOLOGY_SCOPE_DENIED`
  - 行为已停用（`scope` 含 `disable`）：`ONTOLOGY_BEHAVIOR_DISABLED`
  - 管控配置不可用（缺条目 / 文件缺失 / 解析失败 / 结构非法）：`ONTOLOGY_SCOPE_UNAVAILABLE`
  错误码语义 MUST 全局唯一，MUST NOT 与既有工具错误码混用。
- **FR-015**：同名行为出现在多个已部署本体时，判定 MUST 为"拒绝优先"：任一本体判定拒绝即拒绝，全部放行才执行；该情形 MUST 记 warning 指明冲突本体。
- **FR-016**：模型可见文案 MUST 讲清"哪个行为、哪个本体、哪一类原因"，并 MUST NOT 列出 `scope` 中的授权用户名或其他用户的标识。**唯一豁免**：判定内部异常导致行为归属不可知时，可省略本体名与行为名（契约 §4「归属未知」兜底文案），其余情形不得省略。
- **FR-017**：拒绝 MUST 以**工具失败结果**的形式返回（沿用既有失败标记通道：卡片标红、模型收到可读文本），MUST NOT 以抛异常方式中断本轮对话；模型据此可向用户说明并收尾。
- **FR-018**：每次拒绝 MUST 留一条结构化记录，含用户标识、数字人、会话、工具名、本体、行为、原因分类与时间；因管控配置异常而拒绝的记录 MUST 为告警级。
- **FR-019**：被拒绝的调用 MUST NOT 计入实际发生的 MCP 调用次数与调用成功/失败统计（该调用从未真正发出），只进判定日志。

**数据源与生效**

- **FR-020**：判定的唯一数据源 MUST 是部署产物中的 `ontology.yaml` 与 `securities.yaml`；MUST NOT 读取平台侧配置、MUST NOT 新增权限白名单或第二套授权来源。
- **FR-021**：数字人没有部署任何本体时，所有工具都 MUST 按"非本体行为"放行；该路径 MUST NOT 产生拒绝记录，MUST NOT 产生告警噪声。**可验证口径**：该路径下 `scope_guard.*` 日志条数为 0（含加载期 degraded 事件）。
- **FR-022**：行为已从 `ontology.yaml` 识别、但其所属本体缺 `securities.yaml`、文件不可解析、`scope` 结构非法或缺少对应 `action_name` 条目时，MUST 按"管控配置不可用"拒绝并告警（fail-closed）。理由：这类情形下"放行"等同于绕过管控，异常必须暴露而非静默。**判定过程自身的内部异常**（如缓存加载出错）同样 MUST 按本条拒绝并告警，MUST NOT 因异常而放行。
- **FR-023**：重新部署后 MUST 在下一次工具调用即按新配置判定，无需重启服务、无需新建会话；判定结果 MAY 缓存以控制开销，但缓存 MUST 随配置变化失效，且任一次判定 MUST 读到完整文件，MUST NOT 读到半更新内容。
- **FR-024**：判定带来的额外开销 MUST 满足 `SC-004` 的时延阈值；不得因每次调用重读全部本体而拖慢工具执行。
- **FR-025**：管理平台侧 MUST NOT 新增端点、MUST NOT 解析或改写 `scope` 语义；`securities.yaml` 仍由本体市场整包导入与下发（与现状一致）。

### 关键实体 *(include if feature involves data)*

- **本体行为**：一次可被模型调用的能力，来自已部署本体的 `behaviors[]`；关键属性：名称、标题、操作类型（`command` / `query`）、所属本体（场景名 + 本体名）。
- **行为管控条目**：`securities.yaml` 中的一条登记；关键属性：`action_name`、`scope`（授权范围）、`confirm`、`confirm_content`。本特性只读取 `action_name` 与 `scope`。
- **授权范围**：条目上的 `scope` 列表，元素为保留标记（`everyone` 全放开 / `disable` 全停用）或用户名。
- **数字人归属用户**：数字人部署所在目录的用户标识，是"当前用户名"的唯一来源。
- **权限判定结果**：`非本体行为放行` / `放行` / `拒绝`（附原因分类：未授权、已停用、管控配置不可用）。

## 成功标准 *(mandatory)*

### 可度量结果

- **SC-001**：对 `everyone`、`disable`、`含当前用户名`、`仅含他人`、`空 scope`、`缺条目` 六类配置构成的判定矩阵，判定结果与预期**一致率 100%**（矩阵用例全绿）。

## 影响范围与现状核对 *(落点登记)*

- **涉及侧**：**运行环境（`agent-backend`）**——工具装配处的执行包装、本体与管控文件加载、判定与缓存、三类错误码、结构化记录与测试。按宪章原则七，本特性的契约（错误码与拒绝语义）MUST 一次落全，不允许"只有判定没有可观测"。
- **前端（`frontend`）**：**零改动**。拒绝复用既有"工具失败卡片标红 + 文案"通道，无需新字段。
- **管理平台（`admin-backend` / `admin-frontend`）**：**零改动**。`securities.yaml` 现状已随本体整包导入、原样下发、平台不解析语义（`FR-025`）。
- **现状缺口（必须改变项）**：
  1. 运行环境当前**完全不读** `securities.yaml`（全仓检索零命中），`scope` / `confirm` / `confirm_content` 均未被消费。**本特性已补齐**：`scope` 由权限闸门消费；`confirm` / `confirm_content` 仍不消费（人工确认由 MCP 服务配置决定）。
  2. 工具装配处目前只有"人工确认"一层包装，没有授权层；两者需要确定先后（判定在前）。
  3. 暴露给模型的 MCP 工具名带服务前缀，与本体行为名之间没有现成映射，需要一处统一的口径实现（宪章原则二：唯一来源）。
  4. 运行时错误码目前只有人工确认类，缺"权限/停用/管控异常"三类。
  5. 本体文件加载目前只服务意图聚焦（每轮读取），本特性需要面向"每次工具调用"的判定视图与缓存策略。
- **不涉及**：参数级或数据级权限（只判行为）、调用频次限额、按数字人覆盖 `scope`、平台侧编辑 `scope` 的界面、`confirm` / `confirm_content` 的消费（人工确认仍由 MCP 服务配置决定）。

## 口径决策（2026-11-08 本次收敛）

> 本表记录**决策来源与理由**，不构成第二套口径。判定语义以 `FR-001`~`FR-025` 为唯一正本；两者表述冲突时以功能需求为准，并回写本表。

| # | 决策 | 理由 |
|---|---|---|
| 1 | "用户名"取**平台用户标识**（`users/{用户名}/` 的那一段），不是登录账号或显示名 | 平台侧唯一存在的用户身份即用户标识，部署目录、会话归属、用量统计都用它 |
| 2 | 行为名 / `action_name` / `scope` 元素 / 当前用户名一律**去首尾空白 + 大小写不敏感**比较 | 避免同一行为因书写差异被绕过（漏拦比误拦代价更高） |
| 3 | 缺条目、缺文件、文件损坏、结构非法 → **拒绝**并告警（fail-closed） | 放行等于绕过管控；平台保证两文件必需，异常属部署问题，应暴露而非静默 |
| 4 | 数字人**未部署任何本体** → 全部按非本体行为放行 | 没有本体就不存在"本体行为"这一前提，不应对纯工具型数字人制造故障 |
| 5 | 同名行为跨多个本体 → **拒绝优先** + warning | 归属歧义下宁严不宽；warning 让冲突可被治理 |
| 6 | `disable` 优先于 `everyone` | 停用是硬性关停语义，与"放开"并存时应以关停为准 |
| 7 | 空 `scope` → 拒绝 | "配了条目但没写授权对象"最接近"无人授权"，不是"所有人" |
| 8 | 判定先于人工确认，被拒不出确认弹窗 | 让用户为一个必然失败的调用点确认是纯浪费，也容易让用户误以为"确认了就能跑" |
| 9 | 不提供关闭闸门的开关 | 本需求的目的就是让 `scope` 生效；需要放开时由本体侧写 `everyone`，单一来源 |
| 10 | 模型可见文案不含 `scope` 清单，日志可留痕 | 避免把授权配置泄露给终端用户；排障仍可从日志定位 |

## 假设

- **归属关系**：同一数字人可被多个用户各自部署一份，每份按**自己那份部署目录**的归属用户判定；不存在"同一部署被多个用户共用"的情形。
- **命名约定**：MCP 工具名与本体行为名同名（现状成立）；不同名的工具无法被识别为本体行为，按放行处理。这也是本特性唯一的"漏拦"面，已在 `FR-003` 显式登记。
- **数据来源**：`securities.yaml` 由本体市场提供并整包下发，平台不编辑；管理员改 `scope` 的入口在本体侧，改完重新部署即生效。
- **保留标记**：`scope` 的保留词只有 `everyone` 与 `disable`，其余元素一律按用户名解释。
- **判定粒度**：本期只做行为级开关，不做参数级约束（如"金额超过 X 需要审批"）。
- **文案语言**：拒绝文案为中文，面向终端用户可读，不出现内部错误码原文为唯一说明（错误码只进日志与结构化字段）。
- **性能基线**：闸门是同步内存判定，不引入外部依赖、不发起网络请求。
- **测试口径**：用例以本地桩数据构造本体与管控文件，不依赖真实 MCP 服务与真实 LLM。
