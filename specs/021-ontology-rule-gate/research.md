## D1：`rule_design` 的解析口径 —— 固定两层 AND/OR 结构，不是通用表达式树

**决策**：把 `rule_design` 解析成**定长三层**模型（根 → 组 → 条件），求值只做两级布尔合成：

```
RuleDesign { combine: 'and'|'or', groups: RuleConditionGroup[], pass_message?, fail_message? }
RuleConditionGroup { combine: 'and'|'or', conditions: RuleCondition[] }
RuleCondition { function: string, field: string, operator: string, values: string[] }
```

- 根 `combine` 组合各组的布尔结果；组 `combine` 组合组内各条件；
- 只有这两级，**没有 NOT、没有括号嵌套、没有"条件引用条件"**；
- 空串 / 非法 `combine` 按 `and` 处理（读侧归一，与设计期"非法即空串"一致）；
- 结构上限（≤5 组 × 每组 ≤5 条）属于**设计期**约束，运行期**不因超限拒绝**（超限数据照常求值，
  避免"平台写了就对、运行期却拒绝"的口径分叉）。

**理由**：
1. 权威文档明确"结构是固定的两层「组间 + 组内」AND/OR 结构，不是通用表达式树"；
2. 两级组合的求值是**有限、可穷举、可单测**的（没有递归、没有优先级歧义），
   与"不能由 LLM 判断"的硬要求天然契合；
3. 预留"将来把 `conditions` 换成 `children`"的演进空间，本期的解析器不影响后续扩展。

**被否决的替代方案**：
- *通用表达式树（递归节点 / NOT / 任意嵌套）*：权威结构不支持，且会引入"平台产不出的形状怎么算"的
  解释负担；
- *直接 `eval` / 模板表达式*：不可控、不可审计，且无法把"哪个条件不成立"结构化上报；
- *把 `rule_design` 交给模型解读*：用户明确禁止，且不可复现、不可测试。

**扩展位**（本次不实现，只保证不挡路）：`design.ts` 的入口只接受一个"未归一的对象"，
将来若出现 `children` 形态，只需在解析层加一条分支，求值层（`evaluate.ts`）与包装器不变。

## D2：函数执行记录存什么 —— 存**业务数据**，不存工具结果原文

**决策**：记录值为该次调用的**业务数据**：

1. 结果带**统一信封**（同时含 `data`，且含 `success` / `error` / `status` 之一，判据以 `FR-006` 为准）→ 取 `data`；
2. 无信封 → 取结果对象本身（本仓库既有 MCP 服务返回 `{status, message, ...}` 扁平形态，走这条）；
3. 结果为纯文本 → 按合法 JSON 对象解析；
4. 解析不出对象 → 记为空对象（该函数的一切条件都不成立）；
5. 结果为数组 → 记为 `{ count: 长度, items: 原数组 }`。

**理由**：权威文档写明 `field` 是"相对统一信封 `[data]` 的路径，不含信封层"。若把整个信封存进记录，
所有 `field` 都会多一层 `data.` 前缀，规则将**永远取不到值**；而本仓库既有服务又是扁平形态，
故按"有信封取 `data`、无信封取本体"的判据兼容两种现实。

**被否决的替代方案**：
- *只存原始文本*：求值模块要再写一套解析，且"模型看到的文本"与"规则读到的值"会分叉；
- *只认 `{success,data,error}` 信封*：本仓库 `bom-service` / `ocr-service` / `jev-service` 全部返回
  `{status, ...}` 扁平结构，会把它们的结果全判成"无字段"；
- *记录整个 MCP `CallToolResult`*：`content` 块与 base64 会把记录撑爆，且与业务字段无关。

## D3：`field` 路径与类型强制 —— 复用权威语法，不引入 JSONPath / JSON Schema 库

**决策**：

- 路径语法按权威文档实现：`segment := name ['[]']`，分段用 `.`；`items`（数组容器本身）与
  `items[].qty`（元素层字段）都合法，`a[].b[].c` 叠加；
- `[]` 语义：对该层数组**逐元素投影**，缺失元素丢弃；投影结果为空即"字段缺失"；
- 类型强制：`values` 恒为字符串数组，解释时查该函数 `response` 中该字段声明的 `type`
  （`boolean` / `integer` / `number` / `string`）；未声明类型 → 字符串精确比较
  （数值算子除外，转不出数字即不成立）；
- `response` 两种形态都要吃：本体函数是**属性映射**（`{pass: {type: boolean}}`），
  公共函数是 JSON Schema（`{type: 'object', properties: {...}}`）——遇到 `properties` 先解包。

**理由**：语法与类型口径是**平台侧已在用的既有约定**，运行期必须与之一致，否则"平台配得出、
运行期算不出"。手写 30 行的路径解析与类型强制即可覆盖，无需为两种 JSON 形态各引一个库。

**被否决的替代方案**：
- *JSONPath 库（`jsonpath-plus` 等）*：新增依赖（违反原则六），且要额外把 `[]` 语义映射到 JSONPath
  方言，反而更难保证与平台一致；
- *JSON Schema 校验库（`ajv`）*：本需求只需要"读一个字段的声明类型"，不需要校验入参；
- *按值外形猜类型（`"true"` → boolean）*：会与字段声明冲突（`"3"` 到底是数字还是字符串没人说得清），
  权威文档明确"目标类型由字段声明 `type` 决定，而非值的外形"。

**安全边界**：`matches` 的正则由本体数据提供（不可信来源），求值时 MUST 限长（待比较文本 ≤ 4096
字符）并 `try/catch`，失败即"条件不成立"，不得抛异常、不得让一次坏正则拖垮整轮。

## D4：解耦形态 —— 纯领域包 + 单一包装器 + 6 处装配/接线

**决策**：

```
infra/agent-factory.ts（装配 4 行）
   ├─► infra/tool-rule-gate.ts（唯一 AgentTool 包装器，只认端口，不懂 YAML）
   ├─► domain/rule-gate/**（规则解析 / 求值 / 目录 / 文案 / 端口）
   └─► domain/ontology-doc.ts（ontology.yaml 的统一解析与名称归一，被 020 与 021 共用）

domain/run-consume.ts（中止接线 3 行）→ domain/run-impl.ts（新增 1 个字段）
```

硬约束（可用 grep 断言）：

- `domain/rule-gate/**` MUST NOT import：`../infra/**`、`./scope-guard/**`、`./intent-focus/**`、
  `./mcp/**`、`@earendil-works/**`、`fastify`、`pino`、`node:fs`（IO 只经 `ontology-doc`）；
- 求值模块 MUST 是**纯函数**（同样的记录 + 同样的规则设计 → 同样的结果），不读时钟、不读环境、不发网络；
- 包装器 MUST NOT 出现具体工具名、本体名、YAML 字段名（与 020 同一红线）；
- 删除本特性 = 回退 `agent-factory` 4 行 + `run-consume`/`run-impl` 各 1~3 行 + 删除两个新目录。

**理由**：用户明确要求"解耦，方便后续扩展"。规则体系最可能的演进是"新增算子 / 新增规则形态 /
新增介入位置"，把它们关在 `rule-gate` 包里，包装器与装配层就不会跟着改。

**被否决的替代方案**：
- *写进 020 的 `tool-scope-guard.ts`*：权限与规则是两个正交关注点，混在一起后任一方的改动都要重跑
  另一方的全部用例，且 020 的单测会开始依赖规则数据；
- *写进 `agent-factory.runWith`*：装配层会出现 60+ 行判定逻辑，突破"装配只装配"的边界；
- *独立微服务 / 独立进程*：规则数据在本机目录、求值是纯内存计算，引入 IPC 只增加失败面。

## D5：包装顺序 —— 权限闸门（020）在外，规则闸门（021）在内

**决策**：`tools → ruleGateTools(...) → guardTools(...) → loop`。

**理由**：规格 `FR-009` 要求"权限校验通过后"才判规则。外层 020 拒绝时，内层包装器根本不会执行，
天然满足顺序；反过来（021 在外）会在未授权的调用上白跑一次规则求值，甚至可能先中止整轮、
再也没机会告诉用户"这是权限问题"。

**被否决的替代方案**：
- *021 在外 + 重复调用一次 `scopeGuard.check`*：多一次判定、两套顺序维护点，且两处都不再是"单点真相"；
- *合并成一个包装器*：020 已完成、已验收、有 5 个测试文件；合并会让本次改动面翻倍。

## D6：行为识别与名称归一 —— 单一来源 `domain/ontology-doc.ts`

**决策**：把 020 `scope-guard/policy.ts` 的 `normalizeName` / `matchKeys` 与 `catalog.ts` 的
`ontologySignature`、以及 `behaviors[]` 的解析抽到新模块 `domain/ontology-doc.ts`，
020 侧保留**同名再导出**（既有引用与测试不改），021 直接使用。

`ontology-doc.ts` 的产出（一个本体一份）：

```
OntologyDoc {
  scenarioName, ontologyName         // metadata 展示名，缺失回退目录名
  behaviors: { name, title, opType }[]
  rules: unknown[]                   // 原样（由 rule-gate/catalog 归一）
  functions: { name, response, type }[]
  key                                // `{场景}/{本体}`
}
```

**理由**：宪章原则二"同一职责 MUST 只有一处实现"。"什么算一个本体行为"是**安全相关**判据，
如果在 020 与 021 各写一套，一次改动只修好一侧就会造成"权限认它是行为、规则不认"的分叉。
同时，`rules` 与 `functions` 只有本特性消费，放在 `ontology-doc` 里"顺手解析"成本极低。

**被否决的替代方案**：
- *021 自己再读一遍 yaml*：两套 behaviors 解析必然漂移；
- *让 020 的 catalog 暴露 rules*：把 021 的数据需求压进 020 的快照，020 会被动承载无关字段；
- *让 021 依赖 020 的 `policy.ts`*：跨特性横向依赖，删除 020 会连带弄坏 021。

**回归保证**：020 的 `scope-guard-catalog.spec.ts` / `scope-guard-policy.spec.ts` 全绿是本次重构的
验收条件；告警片段（`invalid_yaml` / `not_object` / `not_regular_file`）与行为名归一结果 MUST 逐字不变。

## D7：规则目录的加载与缓存 —— 目录签名 + 惰性加载（与 020 同口径）

**决策**：实例内持有一份快照，键为 `{agentDir}/ontology` 的 `mtimeMs`（缺失为 `missing`）；
每次判定前 `statSync` 一次，签名变了才重读全部本体。部署是**目录级原子改名**，因此"重新部署后
下一次调用即生效"成立。

**理由**：与 020 的既有实现同口径（用户与运维不需要理解两套失效策略）；规则与行为来自同一批文件，
同签名同生命周期最省心。

**被否决的替代方案**：
- *每次调用重读*：`SC-004` 的 ≤5ms 预算会被几十毫秒的 YAML 解析击穿；
- *只在实例创建时读一次*：只换本体（不换数字人配置）的部署要等实例回收才生效，违背 `FR-038`；
- *接入配置指纹（R7）*：已核对指纹不含 `ontology/**`，靠它会漏掉"只换本体"的部署。

## D8：多规则 / 多本体的合成 —— "缺函数优先（暂停）"，其后"任一不成立即拒绝"

**决策**：

1. 收集该行为在**所有**已部署本体中声明的前置规则（多本体同名行为不挑"更相关的"）；
2. 先做缺函数检查：只要**任一**规则缺函数 → 暂停，一次反馈**全部**缺函数的规则；
3. 缺函数检查通过后逐条求值：任一规则 `false` → 拒绝并中止（附全部不成立的规则与失败条件）；
4. 后置规则同理合并，全部追加。

**理由**：`FR-013`/`FR-024` 已定"全部参与、逻辑与"。把"暂停"放在"拒绝"之前，是为了优先走
**可自愈**的那条路：一次中止会把本轮彻底终止，而"还没算"本来只要模型多调几个函数就能过。

**被否决的替代方案**：
- *只取第一条规则*：其余规则形同虚设，且"哪条算第一条"没有业务依据；
- *暂停与拒绝同时报告*：模型会不知道该补函数还是该放弃，体验上等价于直接失败；
- *按本体就近择一*：多本体同名行为本身就是配置问题，猜"更相关"等于掩盖冲突。

## D9：中止整轮怎么落地 —— 复用 `AbortController` + 失败轮收尾，不改事件集合

**决策**：

- `AgentRunRequest` 新增可选回调 `abortRun?(reason: { code, message, details })`；
- `run-consume.ts` 把它接到 `run.ruleAbort = reason; run.stop()`（`stop()` 已是"中断 + 清挂起"的既有入口）；
- 消费事件流时，`error` 分支先看 `run.ruleAbort`：有值则以 `ONTOLOGY_RULE_DENIED` 走
  **失败轮收尾**（`finalizer.error`），不再走 `finalizer.aborted`；
- `HistoryErrorInfo` 增加可选 `details?: string[]`（"有才写"），`toHistoryErrorInfo` 透传它。

**理由**：
1. 中止 = 停止后续模型调用与工具调用，`AbortController` 正是既有机制（用户点"停止"走同一条路）；
2. 但**用户语义不同**：用户主动停止是"丢弃本轮"，规则拒绝是"本轮失败且要看原因"，
   所以必须走 `finalizer.error`（失败轮留痕 + 可见原因），而不是 `finalizer.aborted`；
3. 复用 `error` 事件意味着**不新增 SSE 事件类型**，前端只需补一条错误码映射。

**被否决的替代方案**：
- *在工具里 `throw`*：pi 的 `catch` 会覆盖整个结果，`details` 丢失；且异常与"业务拒绝"混成一条路
  （`domain/tool-error.ts` 已把这条教训写进文件头）；
- *新增 SSE 事件 `rule_denied`*：前端要新增事件分支、历史回放要新增状态，成本远高于复用 `error`；
- *让模型"自觉停止"*：不可靠，且模型仍可能继续调用其他工具。

## D10：成功/失败怎么判 —— 读 `details.toolError`，不看 `isError`

**决策**：包装器在拿到 `execute` 的返回值后，用既有 `readToolError(result.details)` 判定成功与否：
有标记 → 失败（不记录、不追加后置提示）；`execute` 抛异常 → 失败（异常继续上抛，由 loop 兜底）。

**理由**：`isError` 是 `afterToolCall`（loop 内部）才翻的牌，包装器返回时它还不存在；
而 `details.toolError` 是工具层**已经写好**的统一标记（`domain/tool-error.ts`），正是唯一权威判据。

**被否决的替代方案**：*看 `content` 里有没有"失败"字样*：文案会变、会误判；*看状态码*：MCP 结果里没有。

## D11：错误码与文案 —— 中止一个码、暂停一个码，文案单一来源

**决策**：

| 场景 | 码 | 通道 | 用户可见 |
|---|---|---|---|
| 前置规则缺函数（暂停） | `ONTOLOGY_RULE_FUNCTIONS_MISSING` | 工具失败结果（`details.toolError`） | 工具卡片失败态 + 规则原文 |
| 求值不成立 / 规则不可用（中止） | `ONTOLOGY_RULE_DENIED` | SSE `error` + 失败轮落盘 | 失败提示（含逐条原因） |

两个码都全局唯一；文案全部由 `rule-gate/format.ts` 生成（包装器与域层都不拼字）。
`details` 里放 3~6 条中文字符串：本体/行为、规则名、`fail_message` 原文、不成立的条件摘要。

**理由**：暂停是"这次调用没成，但本轮继续"，必须留在工具结果通道；中止是"整轮失败"，
必须走失败轮通道。两者混用会让前端要么误判成功、要么丢掉整轮。

**被否决的替代方案**：*两个场景共用一个码*：前端无法区分"要不要提醒用户重发"。

## D12：记录与求值的资源边界

**决策**：

| 项 | 上限 | 超限行为 |
|---|---|---|
| 单条函数结果 | 256 KB（序列化后） | 丢弃该条 + 告警（该函数本轮视为"未记录"→ 触发暂停，不会静默通过） |
| 记录条目数 | 64 条 | 超出后新函数不再记录 + 告警 |
| `matches` 待比较文本 | 4096 字符 | 该条件判不成立 + 告警 |
| 规则求值条件总数 | 不设额外上限（结构上限 ≤25，设计期保证） | — |

**理由**：`SC-004` 的 ≤5ms 预算与"一轮内存里的记录"都要求有界；而"丢弃即暂停"保证丢弃不会变成
静默放行（与 `FR-007` 一致）。
