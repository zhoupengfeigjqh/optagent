# 阶段 0 研究：账号域 MySQL 模式功能对齐

**输入**：[spec.md](./spec.md)　**日期**：2026-11-28
**结论**：本特性的全部未知项已在下面 R1–R13 收敛，无 `NEEDS CLARIFICATION` 残留。

## R1 数据搬运的范围

- **Decision**：搬运 `账号`、`会话登记`、`数字人服务`、`注册链接` 四类数据的**全部业务字段**；按 `服务 → 账号 → 链接 → 会话` 顺序写入；全部采用"存在即更新、缺失即插入".
- **Rationale**：现有搬运只覆盖账号的 3 个字段与会话，导致角色/手机号丢失（管理员进不去）、服务与链接整体消失。四类实体存在引用关系，顺序错了会先出现悬空引用。
- **Alternatives considered**：
  - 只迁核心字段（当前实现）→ 已被现网验证为不可用（管理员权限丢失、链接全丢）。
  - 先迁账号再迁服务 → 账号的来源数字人在目标端暂时无对应记录，语义上先悬空。
  - 移动语义（迁完删源）→ 失去回滚能力，否决。

## R2 会话是否必须搬运

- **Decision**：搬运。
- **Rationale**：规格 FR-004 要求"当前唯一有效登录会话"保留；不搬会让所有人被踢下线，属可观测的行为差异（切换窗口内管理员可能正在操作）。
- **Alternatives considered**：不搬、要求所有人重新登录 → 可接受但属额外行为变化，与"功能对齐"目标冲突。

## R3 配置版本（乐观锁）在两种存储下的语义

- **Decision**：完全一致。新建账号（未携带版本）成功后推进版本；携带版本时先校验（不符即拒绝）再写入再推进；修改授权同样"校验 → 写入 → 推进"；重置密码**不**推进；删除账号推进会。
- **Rationale**：规格 FR-010/FR-011/FR-012 要求并发保护与 file 一致；前端已按 409 处理，若后端不再抛 409，并发覆盖会静默发生（违反宪章"并发写入必须有控制且被测试覆盖"）。版本文件仍在文件系统，本身就是设计态快照的一部分，账号写入推进它与 file 同构。
- **Alternatives considered**：
  - 账号写不推进版本（028 现状）→ 前端 409 分支永不触发，并发覆盖无感知，功能不对齐。
  - 把版本也放入数据库 → 越出 028 D4 边界（设计态仍留文件），且需同时改部署链路。

## R4 引用完整性的落点

- **Decision**：数据库层**不**用外键裁决"能否删除服务/数字人"，改为普通索引；引用规则只在领域层判定（删除服务：存在有效链接或用户关联 → 拒绝）。
- **Rationale**：注册链接是**审计记录**，删除服务后记录仍需保留（现网 file 行为）；数据库的 `RESTRICT` 对任何历史链接都拦截，与"只有有效链接才算引用"直接矛盾，且错误被统一翻译成存储不可用（表现为 500）。引用规则留在领域层也符合"同一职责只有一处实现".
- **Alternatives considered**：
  - `ON DELETE CASCADE` → 物理删除审计记录，且删除数字人场景会连带删掉刚软撤销的历史。
  - `ON DELETE SET NULL` → 需把链接的服务编码改为可空，且会改写账号的来源数字人（file 不改）。
  - 保留 `RESTRICT` 并在删除前物理清理历史链接 → 删除数字人时会把全部历史链接删掉，审计丢失。

## R5 会话与账号的级联

- **Decision**：保留"账号删除时会话随删"的数据库级联，同时保留业务上"先注销再删"的顺序。
- **Rationale**：会话是账号的从属数据，不应存在孤立会话；业务的显式注销仍是主路径，数据库级联只作兜底。
- **Alternatives considered**：去掉级联、完全依赖业务顺序 → 任何绕过业务层的删除都会留下可用会话（安全问题）。

## R6 账号状态字段

- **Decision**：删除"启用/禁用"列。
- **Rationale**：file 模式下不存在账号停用概念；保留一个无人读写的列会让两种存储语义分叉（数据库里改了不生效），属"看起来有、实际没有"的陷阱。停用账号是独立需求。
- **Alternatives considered**：实现停用（登录拒绝）→ 属功能扩张，超出"对齐"范围，且需同步前端与契约。

## R7 级联撤销链接的原子性

- **Decision**：下沉为存储端口的一次操作（一条语句 / 一次整份落盘），返回实际撤销条数。
- **Rationale**：现实现是"逐条读-改-写"，N 次写且中途失败留下部分撤销，违反宪章"状态变更必须原子或等价原子替换". 端口方法表达的是领域动作（撤销某批服务的链接），不泄漏实现细节。
- **Alternatives considered**：在领域层循环调用单条保存 → 无法消除中间态；引入跨记录事务 → 需要改端口形态，收益不抵成本。

## R8 注册使用次数的原子性

- **Decision**：改为"自增"语义（数据库自增、file 原地自增），不再回写绝对值。
- **Rationale**：绝对值回写在并发下丢计数（规格 SC-006 要求偏差为 0）。
- **Alternatives considered**：加行锁/乐观锁重试 → 复杂度更高，且 file 侧无锁可用。

## R9 注册链接清单的排序

- **Decision**：两种存储统一按创建时间升序、同刻按链接标识。
- **Rationale**：前端"复用最新一条"依赖列表顺序；两种存储顺序相反会让同一界面在切换后展示不同链接。
- **Alternatives considered**：改为倒序 → 需同步改前端取首条为末条，属无必要的行为变更。

## R10 账号数据的读取方式（内存投影）

- **Decision**：**账号**保留启动期加载的内存投影（读同步），并明确"单实例运行"前提；**会话不投影**，每次回源（file 读文件 / mysql 查 `sessions`）。
- **Rationale**：部署编排、引用统计等同步消费方依赖账号的同步读；改成直读会波及多处。会话则相反——它是安全边界，内存副本会让"别处登录/运维删行"造成的失效看不见，而它只有一个消费方（`introspect`，本就在异步请求上下文里），改直读代价极小。
- **Alternatives considered**：账号也全部改直读（需把同步端口改异步，波及部署器与引用查询）；给会话引入 TTL 缓存或失效广播（新增机制，且仍留一致性窗口）。
- **2026-11-28 补注**：会话侧已按上述结论落地——`SessionPort` 四个方法全部 async、`MysqlSessionStore` 去掉 `rows` 投影并每次查表、`clearSession` 去掉基于投影的提前返回；`AuthService.introspect` 随之改为 async（HTTP 契约不变）。账号投影维持原状。

## R11 跨介质操作（数据库 + 文件系统）

- **Decision**：不追求跨介质事务；固定顺序（撤回部署副本 → 注销会话 → 删除账号）+ 每步幂等 + 失败如实上抛并记录上下文。
- **Rationale**：部署产物、配置版本与清单都在文件系统，无法与数据库同事务。假装有事务比诚实补偿更危险；宪章允许"事务或等价的原子替换"，此处以"顺序 + 幂等 + 可观测失败"作为等价手段，并在 plan 的复杂度跟踪中登记。
- **Alternatives considered**：把部署产物也入库（越出 028 边界）；两阶段提交（无基础设施，成本远超收益）。

## R12 运维工具与健康检查

- **Decision**：运维脚本按当前存储装配（与主程序同一处装配逻辑）；健康检查增加账号存储探测。
- **Rationale**：现状两个脚本硬编码文件路径，切换后会"成功但无效"，属于最危险的静默失败（运维以为改了密码）。健康检查不探库会让故障只能从业务错误里发现。
- **Alternatives considered**：脚本直接连库（各自写一套连接与装配）；健康检查保持现状（依赖业务报错）。

## R13 迁移期的一致性来源

- **Decision**：迁移只读文件、只写数据库，源数据不改；迁移期间停止写入。
- **Rationale**：文件是切换前的唯一权威源；写入交错会让"对账"失去意义。停止写入是内部工具可接受的窗口成本。
- **Alternatives considered**：双写过渡（两套真相源，冲突处理成本高）；在线增量同步（规模不支持，收益低）。

## R14 表列命名规则

- **Decision**：文件模式存在的字段，在表中必须**同名同义**；表**允许额外列**（`id`、`created_at`、`updated_at` 等），但额外列不得表达与文件字段冲突的语义，也不得被当作业务键。据此把 `users.password_record` 更名为 `users.password`。
- **Rationale**：同一份数据在两种存储下两个名字，会在三处持续产生成本——搬运/对账要维护映射表、SQL 与领域记录之间要维护别名、排障时要靠记忆翻译；而且"共享字段都被改名"意味着每加一个字段都要改两遍。允许额外列保留的是"库的物理需要"（聚簇主键、审计时间），禁止的是"语义漂移"。
- **Alternatives considered**：
  - 保留 `password_record` 并在代码里做别名映射（现状）→ 映射点虽有两处，但每个读代码的人都要先翻译一次；一旦某个 SQL 漏改就是运行期错误。
  - 用视图 `SELECT password_record AS password` 兼容 → 多一层视图，写路径仍要别名，且掩盖问题。
  - 把文件也改成 `password_record` → 违反"以文件模式为语义基准"的前提，且会让运行环境既有数据读不到。
