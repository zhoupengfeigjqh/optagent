## 原始输入

> 补充一个上传文件的记录需求，功能具体如下：
> 1 数字人选择或切换后，点击 "+" 上传文件。如果成功且落盘，则在输入区需要 显示 @ 上传文件名（现有功能满足），方便用户开展后续对话，如果失败则不用在输入区显示
> 2 上传成功或失败后，如果关闭（即再点击 + ），此时会清空上传成功或失败的消息，用户再点开时没有成功或失败记录，会重新开始记录
> 3 上传文件改一下自动的后缀模式。即上传成功后，如果上传地址有重名文件，则在新上传文件加"（1）.(2).." 这种数字后缀（自动检测并+1），不重名则原名。注意，在输入区显示的应该是@xxx带后缀的文件

**逐句落点**（避免后续理解漂移）：

| 原话 | 本规格的落点 |
|---|---|
| "数字人选择或切换后，点击 + 上传" | 上传仍以**当前选中的数字人**为数据域（既有归属口径不变）；未选数字人时沿用既有拒绝并展示失败原因（`FR-003` / 假设 1） |
| "如果成功且落盘，则在输入区需要显示 @ 上传文件名" | **成功且后端返回落盘名**才回写，回写内容 = `@落盘名`（`FR-001` / `FR-002`） |
| "（现有功能满足）" | 与现状不符（见现状核对 #5）：现状只有手动 `@` 才插入，本特性要求自动回写；本规格以"成功即回写"为准 |
| "如果失败则不用在输入区显示" | 失败项**零回写**：既不插 `@` 标记，也不登记引用（`FR-003`） |
| "关闭（即再点击 +）……会清空上传成功或失败的消息" | 收起面板即清空**关闭那一刻已成终态**（成功 / 失败）的记录；再展开时这些记录不出现（`FR-010`） |
| "用户再点开时没有成功或失败记录，会重新开始记录" | 清空是**记录窗口**的重置，不是删文件、不是清引用（`FR-011`）；关闭瞬间仍在上传的项不参与清空（Q2 = B，`FR-013`） |
| "重名则加（1）.(2).. 数字后缀（自动检测并+1）" | 冲突时取**最小可用正整数**编号，形态为**半角括号紧贴主名、扩展名保留在末尾**（Q1 = A，如 `报告(1).csv`；`FR-021`） |
| "不重名则原名" | 不再追加时间戳（`FR-020`） |
| "在输入区显示的应该是 @xxx带后缀的文件" | `@` 标记取**落盘名**（含后缀），用户可据此区分 `(1)` / `(2)`（`FR-024`） |

## 用户场景与测试 *(必填)*

### 用户故事 1 - 上传即回写：成功后输入区直接出现 `@落盘名`（优先级：P1）

用户选好数字人，点 `+`、选目录、选文件。上传成功的瞬间，输入区末尾出现 `@报告(1).csv `，同时这份文件成为本轮可提交的引用。
用户接着打字"帮我分析一下这份数据"就能直接发送，**不需要**再手动打 `@` 去翻目录。
上传失败的文件不会出现在输入区（否则用户会把一个不存在的文件发出去），失败原因留在面板里可见、可重试。

**为什么是这个优先级**：这是本需求最直接的可用性收益——"上传完能立刻对话"。同时它是需求 3 的验证面（输入区显示的必须是带后缀的落盘名）。

**独立测试**：在 `useUploads` 上模拟 `files.upload` 返回 `{ filename: '报告(1).csv' }`，再让 `useUploadPanel` 的订阅生效，断言 `mentionComposer.onPickFile` 收到 `{ dir, filename: '报告(1).csv' }` 且草稿追加了 `@报告(1).csv `；模拟抛错，断言 `onPickFile` **零调用**、草稿与引用**均未变化**。

**验收场景**：

1. **Given** 已选中数字人且输入区为空，**When** 向「数据准备/生产计划」上传一个此前不存在的 `报告.csv` 并落盘成功，**Then** 输入区出现 `@报告.csv `（`@` + 落盘名 + 一个分隔空格），光标仍在文本末尾。
2. **Given** 该目录已存在 `报告.csv`，**When** 再上传同名文件成功，**Then** 输入区出现的是 `@报告(1).csv `（**带后缀**），而不是 `@报告.csv`。
3. **Given** 输入区已有文字"帮我分析一下"，**When** 上传成功，**Then** 原文一字不改，`@落盘名` 追加在其后并以空格分隔。
4. **Given** 上传被服务端拒绝（扩展名不在白名单 / 表头不符 / 超限 / 未选数字人），**When** 请求失败，**Then** 输入区**没有任何**变化，记录列表显示失败原因。
5. **Given** 刚上传成功（未手动 `@`），**When** 立刻点发送，**Then** 消息正常发出，**不出现**"引用的文件已不存在"的拦截。
6. **Given** 一次多选 3 个文件且全部成功，**When** 全部落盘完成，**Then** 输入区按完成顺序出现 3 个 `@落盘名`。
7. **Given** 已引用 10 个文件（既有单条上限），**When** 再上传成功一个，**Then** 上传本身成功、记录显示"已完成"，但**不**自动插入第 11 个 `@`，并给出可感知提示（"单条消息最多引用 10 个文件"）。

### 用户故事 2 - 收起面板即清空记录，再展开从零开始（优先级：P1）

用户传完几个文件、关掉面板继续聊天；再点 `+` 时，面板里干干净净——没有上一轮的"已完成"/"上传失败"残影，这次刚开始的列表是空的。
关键点：清掉的是**这段记录**，不是文件、也不是输入区里已经写好的 `@` 引用——那些是给对话用的，不能被顺手抹掉。
例外只有一类（Q2 = B）：关闭面板那一刻**还在传**的文件不参与清空，它继续传完，记录留到下次展开可见——用户不该因为"顺手关掉面板"就失去一条正在进行的上传。

**为什么是这个优先级**：它是需求 2 的全部内容，判据是"关闭 → 再展开不再有成功/失败的残影"，但必须把"清什么、不清什么"划清，否则实现极易顺手删掉文件、引用，或者把正在传的文件一起清掉。

**独立测试**：用 `useUploads` + `useUploadPanel`（**不挂组件**）制造 1 条 success + 1 条 failed + 1 条 uploading → 触发收起 → 断言 `items` 只剩那条 uploading、`files.remove` 零调用、草稿与引用快照不变；再让该条完成，断言它转为成功且草稿新增 `@落盘名`。

**验收场景**：

1. **Given** 面板内有 1 条成功与 1 条失败记录，**When** 再次点击 `+` 收起面板，**Then** 记录被清空；再次点击 `+` 展开时列表为空（无任何"已完成/上传失败"条目）。
2. **Given** 刚清空记录，**When** 观察输入区，**Then** 之前写入的 `@落盘名` 标记与对应引用**仍然存在**，可正常发送。
3. **Given** 刚清空记录，**When** 去文件空间（或目录清单）查看，**Then** 已落盘的文件**仍在**（清空记录不删文件）。
4. **Given** 清空后再次上传同名文件，**When** 该次上传成功，**Then** 新记录从这一条开始出现，输入区再插入一个新的 `@落盘名`（带新的后缀）。
5. **Given** 面板内无任何记录，**When** 展开面板，**Then** 只显示目录树，没有任何残留状态文案或计数。
6. **Given** 关闭面板时其中一个文件仍在上传，**When** 再次展开面板，**Then** 该条记录**仍在**（状态照实显示）；它传完后转为"已完成"并照常把 `@落盘名` 写进输入区，其余已在关闭时成功的记录**仍是空的**（不清回、不复活）。
7. **Given** 关闭面板时那个仍在上传的文件最终失败，**When** 再次展开面板，**Then** 该条展示失败原因与「重试」入口（与未关闭时同口径）。

### 用户故事 3 - 重名文件用数字后缀，名字可读、可区分（优先级：P2）

同一个目录里第三次上传 `报告.csv` 时，用户拿到的是 `报告(1).csv` 与 `报告(2).csv`——原名一眼可读，编号一眼可比。
旧行为是 `报告_20261018_143022.csv`：名字被时间戳撑长，用户分不清哪份是哪份，在输入区里也难一眼对上。

**为什么是这个优先级**：它是需求 3 的主体，但相对 US1/US2 属于"命名体验"改进；不过它是 `FR-024`（输入区显示带后缀名）成立的前提，故仍必须在同一批实现。

**独立测试**：后端 `domain/upload-name.ts` 的 `claimName` 表驱动测试：空目录 → 原名；已有原名 → `(1)`；已有 `(1)` → `(2)`；已有 `(2)` 但 `(1)` 空缺 → `(1)`；`a.tar.gz` → `a.tar(1).gz`；无扩展名 → `name(1)`；隐藏文件 → `.env(1)`。

**验收场景**：

1. **Given** 目录内无同名文件，**When** 上传 `报告.csv`，**Then** 落盘名恰为 `报告.csv`（无时间戳、无后缀）。
2. **Given** 目录内已有 `报告.csv`，**When** 再上传 `报告.csv`，**Then** 落盘名为 `报告(1).csv`；再来一次为 `报告(2).csv`。
3. **Given** 目录内已有 `(2)` 但 `(1)` 已被删除，**When** 上传同名文件，**Then** 取最小可用编号 `(1)`（不复用已存在的编号，也不跳号增长到 `(3)`）。
4. **Given** 一次多选 3 个同名文件（同批并发），**When** 全部完成，**Then** 落盘名互不相同（原名 / `(1)` / `(2)`），**零覆盖**，且响应各自返回自己的落盘名。
5. **Given** 上传 `a.tar.gz` 且已存在同名，**When** 落盘，**Then** 编号插在**最后一个**扩展名前：`a.tar(1).gz`。
6. **Given** 上传无扩展名的 `README` 且已存在，**When** 落盘，**Then** 为 `README(1)`。
7. **Given** 其它目录或其它数字人下有同名文件，**When** 上传，**Then** 不受影响，仍用原名（冲突判定只在目标目录内）。
8. **Given** 目录内存在历史遗留的 `报告_20261001_090000.csv`，**When** 上传 `报告.csv`，**Then** 两者并存，历史文件**不改名**。

### 边界情况

- **上传进行中关闭面板**（Q2 = B）：正在进行的那次上传**不得被取消**（已经落盘才算成功，半途中断只会留下残片）；该条记录**不被清空**，下次展开仍可见并继续流转到终态，成功则照常回写 `@`（`FR-013`）。
- **上传成功后立刻切换数字人**：记录必须清空（旧数字人的目录与文件对当前数字人无意义），`@` 标记与引用的处置沿用既有口径（`FR-014`）。
- **输入区被用户手动删掉 `@` 标记**：引用随之移除（既有不变式）；此后关闭面板清空记录 MUST NOT 把它"恢复"回来。
- **达到引用上限**：见 `FR-006`，上传成功但插入被拒并给出提示。
- **文件名含换行/控制字符或 `/`、`\`**：沿用既有 `basename` + `/\`→`_` 清洗口径，清洗后再判重。
- **文件名为点开头的隐藏文件**：`.env` 视为无扩展名，后缀追加在末尾 → `.env(1)`。
- **文件名长度接近系统上限**：追加后缀可能超限 → 截断主名以容纳后缀；仍失败则该次上传**失败并给出原因**，MUST NOT 静默覆盖或静默改名。
- **大小写不敏感文件系统（Windows/macOS 默认）**：`Report.csv` 与 `report.csv` 视为同名冲突，编号后缀按同名处理（`FR-023`）。
- **零字节或空名文件**：沿用既有上传校验口径，本次不改。
- **刷新页面**：记录列表不持久化（与现状一致：它只是本轮面板内的状态）。

## 需求 *(必填)*

> 每条附「验证方式」，与 `tasks.md` 的测试任务一一对应。

### A. 成功即回写输入区（US1）

- **FR-001**: 上传项从"上传中"转为"已完成"（后端已落盘并返回落盘名）时，系统 MUST 自动向输入区追加一个引用标记 `@<落盘名>`，并把 `{ dir, filename: <落盘名> }` 登记为本轮可提交引用。
  *验证方式*：`useUploads.spec.ts` 断言成功回调后引用集合新增一项、草稿末尾出现 `@落盘名`。
- **FR-002**: 回写所用的文件名 MUST 取自后端响应 `filename`（落盘名），前端 MUST NOT 自行拼接时间戳/后缀。
  *验证方式*：响应 `filename` 与请求原名不同（如 `报告(1).csv`）时，断言草稿与引用用的都是响应值。
- **FR-003**: 失败项（含客户端预校验失败与服务端拒绝）MUST **零回写**：不插入 `@` 标记、不登记引用；失败原因 MUST 仍在记录列表可见（且在面板关闭前可重试）。
  *验证方式*：失败用例断言草稿文本与引用集合均未变化。
- **FR-004**: 自动登记的引用 MUST **立即可发送**：紧接着点发送时，存在性校验 MUST 通过（不得因文件清单未刷新而误判"引用已不存在"）。
  *验证方式*：模拟"清单尚未包含新文件"的状态，断言 `onSend` 未拦截（`workspace.exists` 对新落盘文件为真）。
- **FR-005**: 批量上传时，每个成功项 MUST 各回写一次；插入顺序为**完成顺序**；标记一律**追加到草稿末尾**并以单个空格分隔，MUST NOT 移动光标位置、MUST NOT 改写/删除用户已输入的文本。
  *验证方式*：3 文件用例断言草稿中 3 个标记、顺序与完成顺序一致、原有文本前后不变。
- **FR-006**: 回写 MUST 复用既有 `@` 引用的唯一入口（登记 + 拼写各只有一处实现）：当已达单条消息引用上限（当前 10）时，上传仍判成功，但 MUST NOT 插入、MUST 给出可感知提示（沿用既有上传/引用提示口径，不新增静默分支）。
  *验证方式*：既有 10 个引用时再上传成功 → 断言引用数不变、提示被推送、记录仍为"已完成"。
- **FR-007**: 回写 MUST NOT 破坏既有"文本与引用必须同步"的不变式：用户删除正文中的 `@` 标记后，对应引用随之移除，且清空记录 MUST NOT 使其复活。
  *验证方式*：插入 → 删除标记 → 断言引用为空；再关闭/展开面板，断言仍为空。

### B. 关闭即清空记录（US2）

- **FR-010**: 点击 `+` **收起**上传面板时，系统 MUST 清空**关闭那一刻**处于终态（成功 / 失败）的记录；下次展开时这些记录 MUST 不出现（仍在上传中的项按 `FR-013` 保留）。
  *验证方式*：`UploadMenu.spec.ts` / 接线层用例：1 成功 + 1 失败 → 关闭 → 再展开，断言列表 0 条；另有 1 条上传中时，断言只清掉前两类。
- **FR-011**: 清空 MUST 只作用于"记录列表"：MUST NOT 删除已落盘文件、MUST NOT 移除输入区的 `@` 标记与引用、MUST NOT 清空输入区文本。
  *验证方式*：断言 `files.remove` 零调用、草稿与引用快照不变、文件清单条数不变。
- **FR-012**: 清空后新一轮上传 MUST 从空的列表开始记录（新条目正常出现、状态正常流转），不继承上一轮的计数或顺序。
  *验证方式*：关闭 → 再上传一次 → 断言列表恰 1 条且 `localId` 与上一轮不同。
- **FR-013**: 关闭面板时仍处于"待上传/上传中"的项（Q2 = B，2026-10-18）MUST **不参与清空**：已发出的上传请求 MUST NOT 被取消，记录 MUST **保留到下一次展开**并继续流转到终态（成功 / 失败）；成功时照常回写 `@落盘名`（`FR-001`），失败时照常展示原因与「重试」。落盘结果 MUST 与后端实际结果一致（不得出现"界面说失败、文件已落盘"或反之）。
  *验证方式*：mock 挂起的上传 → 关闭面板 → 再展开，断言该条仍在且状态未定；释放 Promise 成功后断言状态转"已完成"且草稿新增 `@落盘名`；失败分支断言原因与重试入口可见。
- **FR-014**: 其它收起路径 MUST 与 `+` 收起同口径：面板自带的关闭入口、以及**切换数字人**导致的收起，都 MUST 清空**终态**记录（上传中项沿用 `FR-013` 的保留口径；数字人切换时该条仍指向原数字人的目录，界面上 MUST 能看出它的归属，不得静默改挂到新数字人）。
  *验证方式*：两条用例分别覆盖面板关闭入口与数字人切换，断言终态记录为空、上传中项未被清掉且 `dir` 仍是原值。
- **FR-015**: 清空后的空态 MUST 干净：不出现"已完成 N 个"之类的残留计数、不出现空分组外壳或占位文案。
  *验证方式*：空态渲染快照断言（无 `upload-item` 节点、无计数文本）。

### C. 重名编号命名（US3）

- **FR-020**: 目标目录内**无**同名文件时，落盘名 MUST 等于原始文件名（不再追加时间戳）。
  *验证方式*：后端命名单测 + 集成上传用例，断言响应 `filename === '报告.csv'`。
- **FR-021**: 存在同名文件时，落盘名 MUST 为 `主名(n)扩展名`，形态为**半角括号紧贴主名**（如 `报告(1).csv`，Q1 = A，2026-10-18），其中 `n` 取**当前目录内未被占用的最小正整数**（从 1 起），扩展名保持在末尾，MUST NOT 插入空格或全角括号。
  *验证方式*：表驱动单测覆盖 `(1)`、`(2)`、编号稀疏时取最小可用，并逐字断言 `报告(1).csv` / `报告(2).csv`。
- **FR-022**: 同批并发上传同名文件时，每个文件 MUST 获得**互不相同**的落盘名，MUST NOT 覆盖任何已有文件或互相覆盖（唯一性由落盘侧保证，不能只依赖前端串行）。
  *验证方式*：并发 3 个同名文件（`Promise.all`）→ 断言 3 个不同的 `filename`、目录内 3 个文件、内容互不相同。
- **FR-023**: 冲突判定 MUST 与目标文件系统的实际语义一致：大小写不敏感平台（Windows/macOS）上 `Report.csv` 与 `report.csv` 视为冲突；隐藏文件、多点文件名（`a.tar.gz`）、无扩展名文件按 `FR-021` 的"主名/扩展名"切分规则处理。
  *验证方式*：大小写冲突、`a.tar.gz`、`README`、`.env` 四类用例。
- **FR-024**: 记录列表中的展示名与输入区的 `@` 标记 MUST 都使用**落盘名**（含数字后缀），使同名的多次上传在界面上可区分。
  *验证方式*：两次同名上传后断言两条记录展示名分别为 `报告.csv` / `报告(1).csv`，且输入区对应两个不同的 `@` 标记。
- **FR-025**: 冲突判定 MUST **只在目标目录内**进行：其它目录、其它数字人下的同名文件 MUST NOT 影响本次命名。
  *验证方式*：跨目录、跨数字人的同名上传用例，断言各自使用原名。
- **FR-026**: 既有落盘文件 MUST NOT 被批量改名（历史 `name_YYYYMMDD_HHMMSS.ext` 原样保留），本规则只对**新上传**生效。
  *验证方式*：目录内预置历史时间戳文件 → 上传同名 → 两者并存、历史文件未被触碰。
- **FR-027**: 文件名清洗 MUST 沿用既有口径（取 `basename`、`/` 与 `\` 替换为 `_`、空主名兜底），清洗后再判重与编号。
  *验证方式*：既有清洗相关用例全绿 + 一条"清洗后重名"用例。
- **FR-028**: 追加后缀导致文件名超长时，MUST 截断主名以容纳后缀；若仍无法落盘，该次上传 MUST 失败并返回可理解的原因，MUST NOT 静默覆盖或静默改名。
  *验证方式*：超长名用例断言落盘名长度合规（或返回结构化错误，无静默分支）。

### 关键实体

- **上传记录（`UploadedDocument`）**：面板内的一次上传及其状态（待上传 / 上传中 / 已完成 / 上传失败）、原始名、落盘名、失败原因。生命周期由本特性收紧为"展开期间有效，收起时清空终态、上传中项保留到终态"（`FR-010` / `FR-013`）。
- **落盘名（server filename）**：后端返回的最终文件名，是展示名、`@` 标记与后续引用的**唯一**来源（`FR-002`、`FR-024`）。
- **文件引用（`FileReference`）**：`{ dir, filename }`。上传成功即登记（`FR-001`），失败不登记（`FR-003`），清空记录不影响它（`FR-011`）。
- **引用标记（`@<落盘名>`）**：输入区内的展示文本，与引用一一对应；拼写只有一处实现（`FR-041`）。

## 成功标准 *(必填)*

- **SC-001**: 上传成功后**无需任何额外操作**，输入区即出现带落盘名的 `@` 标记（用户视角：上传完成即"可对话"）。
- **SC-002**: 收起再展开面板，**关闭时已成功或已失败**的记录条数 100% 为 0；同时目录内文件数不减、输入区 `@` 标记数不减。
- **SC-003**: 连续 3 次上传同名文件，得到的文件名恰为 `报告.csv` → `报告(1).csv` → `报告(2).csv`（半角括号），用户一眼能区分，且名字里不含时间戳。
- **SC-004**: 同名 20 连传零覆盖：目录内 20 个文件、文件名互不相同、编号连续无跳号，任何一次上传都没有覆盖前一个。
- **SC-005**: 失败项 100% 不产生输入区标记（不会出现"发了一个不存在的文件"的失败路径）。
- **SC-006**: 达到单条引用上限时，用户能立刻感知原因（有提示），不出现"点了没反应"的静默失败。
- **SC-007**: 门禁全绿：两侧 `npm run lint` / `typecheck` / `test`（含覆盖率阈值）通过；零新增依赖；改动文件 ≤ 500 行；接口**请求/响应结构**零变更（新增的 `409 FILE_NAME_CONFLICT` 属错误码表面增量，已按 `FR-040` 四处同步）。
- **SC-008**: 关闭面板时正在上传的项 100% 不丢失：下次展开仍能看到它，并最终落到成功或失败，界面结论与后端实际落盘一致（不出现"文件在、状态没了"或"状态说成功、文件不在"）。

## 假设

1. **前提：已选中数字人**。未选中时上传沿用既有拒绝口径（失败记录展示原因，不回写输入区），本特性不新增"先选数字人"的引导。
2. **三空间与目录白名单不变**：上传目标仍由用户在 `+` 面板中**点选的目录**决定（数据准备 / 共享空间 / 临时空间），本特性不设默认目录。
3. **"清空记录"的边界**：仅指面板内的上传状态列表；不删除文件、不清空输入区文本、不解除已登记的引用（`FR-011`）。
4. **新上传不再使用时间戳**；历史带时间戳的文件保持原样、不迁移（`FR-026`）。
5. **扩展名切分沿用 `path.extname` 语义**（最后一个点之后为扩展名，点开头且无其它点的文件视为无扩展名）。
6. **逐文件各发一次请求**的既有契约不变（一次只接受一个文件）；多选仍并行发出，故命名唯一性必须由落盘侧保证（`FR-022`）。
7. **记录不持久化**：刷新页面即丢（与现状一致），本特性不引入上传历史。
8. **不动平台单向数据流**：本特性只改文件落盘命名与前台交互，不涉及"平台 → 运行环境"的配置覆盖语义，也不触及文件空间内容的部署口径。
9. **命名形态与进行中项处置已定**（2026-10-18）：重名后缀为**半角括号紧贴主名**（`报告(1).csv`，Q1 = A）；关闭面板时仍在上传的项**继续完成、记录保留到下一次展开**（Q2 = B，`FR-013`）。其余条目不再留待澄清。
