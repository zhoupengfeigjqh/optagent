**功能分支**: `001-digital-human-platform`

**创建日期**: 2026-09-14

**最近修订**: 2026-09-15（管理端固定单一管理员 `zyw_admin`；卡片列表分页每页 8 项；文件空间场景由用户级改为**数字人级**；新增部署前自动校验；**MCP 连接地址按运行形态分别声明、目标形态显式配置**；统一需求编号）

**状态**: 草稿

**输入**: 用户描述："在当前项目基础上，建立一个独立的【数字人管理平台】，该平台包含四大功能：① MCP 服务：卡片展示当前 docker 安装好的 MCP，可启动/关闭 MCP 服务，可查看 MCP 提供的相关工具信息，可测试 MCP 服务，可查看 MCP 服务里的日志运行情况，有汇总统计（每个 MCP 服务的调用次数统计）；② SKILL 设计：卡片展示 skill，可查看和编辑 skill，可新增上传 skill 的 zip 包安装 skill（安装必须按标准 SKILL 格式校验）；③ 数字人设计：卡片展示数字人，可新建和编辑已有数字人，设计包含角色命名与 SOUL 设计、MCP 搭配、工具搭配、SKILL 搭配、文件空间搭配（即 scenario 配置），相当于输出一个 json 配置文件；④ 数字人部署：卡片展示所有用户（如 admin）及其关联的数字人角色名，可新建/编辑用户、增加或删除数字人，点击部署生效后将最新数字人同步到 agent-backend 里的 .opt-agent 对应的用户文件里。所有项目文档用中文撰写。"

**补充说明（修订时由用户追加）**：管理平台集中管理所有的 tool/skill/mcp/数字人配置信息；部署时，将数字人分发到对应用户。数据严格单向导入到运行环境用户目录（单向导入即直接覆盖）。文件空间的内容不覆盖，既有保留。部署点击时自动检查数字人配置，有错误或不存在的引用则阻止部署。文件空间场景（scenario）随数字人存放于其配置目录下，使同一用户的不同数字人可以看到不同的文件空间。

## 用户场景与测试 *(必填)*

### 用户故事 1 - 数字人设计与配置产出 (优先级：P1)

平台管理员（同时也是数字人的作者）在平台上以卡片方式浏览现有数字人，新建一个数字人或编辑已有的数字人：为它命名、撰写 SOUL（人格设定全文）、从平台统一清单中挑选要搭配的 MCP 服务、挑选要启用的内置工具、挑选要搭配的 SKILL、配置文件空间场景（scenario）。保存后平台产出一份完整的数字人配置（JSON 形式），五类配置齐全，且**只记录所选对象的名称引用**，不复制其内容。

**为什么是这个优先级**：数字人是本平台的核心对象；没有设计能力，其余三个模块（SKILL 归属、MCP 搭配、部署分发）都没有服务对象。只实现本故事即可得到有价值的最小可用产品——把数字人配置从"手工编辑运行环境文件"变成"可视化编辑 + 结构化产出"。

**独立测试**：只实现本故事即可端到端验证——"新建一个数字人 → 填写五类配置 → 保存 → 重新打开该数字人，五类配置完整回显"。

**验收场景**：

1. **给定** 平台已有若干数字人，**当** 管理员打开数字人列表，**则** 每个数字人以卡片展示（至少含名称与用途描述），配置损坏的数字人以可辨识的异常态卡片呈现且不影响其余卡片。
2. **给定** 管理员新建数字人，**当** 只填写名称与 SOUL、未配置 MCP／工具／SKILL，**则** 允许保存，且产出配置中对应三个集合为空集合而非缺字段。
3. **给定** 管理员编辑数字人，**当** 修改 SOUL 文本并保存，**则** 重新打开时 SOUL 全文与保存前完全一致（含换行与标点）。
4. **给定** 名称为空或与已有数字人重名，**当** 管理员保存，**则** 拒绝保存并提示具体原因，已有配置不受影响。
5. **给定** 管理员正在编辑，**当** 从 MCP 服务／内置工具／SKILL 三个选择器中选中若干项，**则** 选中集合被完整记录进产出配置，未选项不出现，且不允许出现清单外的不存在引用。
6. **给定** 两个数字人搭配了同一个 MCP 服务，**当** 管理员修改该服务的连接地址，**则** 两个数字人均自动指向新地址，无需逐个修改（证明配置集中存放、数字人只持引用）。
7. **给定** 管理员打开某数字人的内置工具选择器，**则** 每个工具展示名称、用途说明与入参说明，且说明中依赖具体用户/会话的部分以**占位符**呈现（不出现某个用户的具体目录名）。
8. **给定** 运行环境下线了一个内置工具，而某数字人此前引用了它，**当** 管理员浏览数字人列表，**则** 该数字人标为异常并指明失效的工具名，不能被静默部署。
9. **给定** 运行环境新增了一个内置工具，**当** 管理员重新打开内置工具选择器，**则** 无需平台侧任何改动即可看到该工具。
10. **给定** 管理员配置文件空间场景，**当** 填写场景名并至少添加一个"数据准备"二级目录后保存，**则** 产出配置的场景段包含场景名与该目录清单。
11. **给定** 管理员输入了空目录名、重复目录名或含路径分隔符／`..` 的非法目录名，**当** 保存，**则** 该非法值被拒绝并提示原因，其余合法配置不受影响。
12. **给定** 平台已有 20 个数字人，**当** 管理员打开数字人列表，**则** 每页只呈现 8 张卡片（4 列 × 2 行）并显示总条数与当前页码，翻页后呈现其余卡片。

### 用户故事 2 - 数字人分发与部署生效 (优先级：P2)

平台以卡片展示所有用户（如 admin）及其已关联的数字人角色名。管理员可以新建/编辑用户、为用户增加或移除数字人。点击"部署生效"后，平台**先自动校验**将被分发的全部数字人配置，校验通过才把该用户关联的数字人**分发**到运行环境对应用户的数据目录下，并给出部署结果明细。

**为什么是这个优先级**：平台是配置中心，运行环境是落地形态；只有分发下去才产生业务价值。本故事是"设计 → 生效"的最后一公里，是平台的交付终点。

**独立测试**：只实现本故事即可端到端验证——"给 admin 关联一个数字人 → 点击部署生效 → 运行环境该用户目录下出现对应的数字人配置"。

**验收场景**：

1. **给定** 平台已有用户与数字人，**当** 管理员打开部署页，**则** 以卡片展示全部用户及其关联的数字人角色名清单，且卡片可展开查看每个数字人的搭配摘要与异常标记。
2. **给定** 管理员为用户新增一个关联数字人，**当** 点击部署生效，**则** 运行环境该用户目录下出现该数字人的完整配置，其搭配的 SKILL 被物化到该数字人的技能目录、其搭配的 MCP 配置被物化进该数字人的 MCP 配置文件，部署结果显示成功。
3. **给定** 管理员从用户处移除某数字人关联（该数字人此前由平台部署过），**当** 点击部署生效，**则** 该数字人在运行环境对应用户下被移除，该用户其余数字人不受影响。
4. **给定** 运行环境中存在不由平台部署、由人工创建的数字人目录，**当** 管理员执行部署，**则** 该目录不被删除也不被改写。
5. **给定** 某用户关联的某个数字人所引用的内置工具已下线、或所引用的 SKILL 已从库中删除，**当** 管理员点击部署生效，**则** 部署被**阻止**，运行环境**不产生任何写入**，并一次列出全部错误项（指明是哪个用户、哪个数字人、哪一类配置）。
6. **给定** 某用户关联了两个数字人且各自配置了不同的文件空间场景，**当** 管理员点击部署生效，**则** 两个数字人各自带上自己的场景配置落盘，各自的可见目录清单互不影响、不互相覆盖。
7. **给定** 部署过程中某用户的某个数字人配置不合法，**当** 点击部署生效，**则** 该用户整体不生效（不出现部分写入），并明确指出失败项与原因。
8. **给定** 管理员新建用户，**当** 保存并部署，**则** 运行环境新增该用户的完整数据骨架（文件空间与数字人目录），且用户卡片出现。
9. **给定** 部署已完成，**当** 管理员在无任何改动的情况下再次点击部署，**则** 结果保持稳定（幂等），不产生重复或损坏。
10. **给定** 某用户正在进行一轮回答，**当** 管理员完成一次部署，**则** 该轮回答不被打断，其后的新对话使用新配置。
11. **给定** 某内置工具已被下线，**当** 管理员打开全局异常项汇总，**则** 一次列出所有引用了该工具的数字人及其所属用户，并可跳转到对应编辑位置。
12. **给定** 某 MCP 服务已分别为"容器编排内网"与"宿主机本地"两种运行形态声明了连接地址，**当** 管理员把目标运行形态配置为"宿主机本地"并点击部署生效，**则** 落盘的 MCP 配置中连接地址取"宿主机本地"的取值；把目标形态切换为"容器编排内网"再部署一次后，地址相应变为内网形态的取值——**两次切换都无需修改宿主机的 hosts 文件，也无需手工编辑数字人配置文件**。
13. **给定** 某 MCP 服务只声明了"容器编排内网"形态的地址、尚未声明"宿主机本地"形态的地址，**当** 目标形态为"宿主机本地"时管理员点击部署生效，**则** 部署被**阻止**、运行环境不产生任何写入，并指明是"哪个服务缺哪个形态的地址"；平台 MUST NOT 静默改用另一形态的地址把配置写下去。
14. **给定** 管理员浏览任一处界面，**当** 需要确认当前配置将按哪种运行形态产出，**则** 界面常驻可见当前目标运行形态；修改该配置时**则** 提示"既有部署产物将按新形态重新物化"并要求二次确认。

### 用户故事 3 - SKILL 管理与安装 (优先级：P3)

平台维护一份全平台共享的 SKILL 库。管理员在平台上以卡片浏览库中全部 SKILL，查看某个 SKILL 的元数据与正文全文，直接编辑正文并保存；也可以通过上传 ZIP 压缩包安装新的 SKILL。安装时必须按标准 SKILL 格式校验，不合格的包被拒绝并说明具体原因。一个 SKILL 可被多个数字人以名称引用，部署时再物化到各数字人的技能目录。

**为什么是这个优先级**：SKILL 是数字人的可复用能力资产，是 P1 中"SKILL 搭配"的选材来源；但其自身可在 P1 之外独立交付价值，因此排在数字人设计之后。

**独立测试**：只实现本故事即可端到端验证——"上传一个合规 ZIP → 卡片列表出现该 SKILL → 编辑正文并保存 → 内容原样回显"。

**验收场景**：

1. **给定** 平台已有 SKILL，**当** 管理员打开 SKILL 列表，**则** 每个 SKILL 以卡片展示技能名与描述。
2. **给定** 管理员上传一个含标准结构的 ZIP（含根级 `SKILL.md`，且元数据含非空的 `name` 与 `description`），**当** 提交安装，**则** 安装成功并在卡片列表出现该 SKILL，其名称与描述与包内声明一致。
3. **给定** 管理员上传缺少 `SKILL.md`、或元数据缺 `name`/`description`、或目录层级不合规的 ZIP，**当** 提交安装，**则** 拒绝安装并明确指出不合格的原因，平台已有 SKILL 不受影响。
4. **给定** 上传的 ZIP 内含试图越出目标目录的路径（绝对路径、`..` 穿越、符号链接），**当** 提交安装，**则** 拒绝安装并提示安全原因。
5. **给定** 上传的 SKILL 名称与库中已有 SKILL 冲突，**当** 提交安装，**则** 提示冲突并要求管理员显式选择"覆盖"或"取消"；选择覆盖时以新包整体替换，且引用它的数字人在下次部署后使用新内容。
6. **给定** 管理员编辑某 SKILL 正文并保存，**当** 重新打开，**则** 正文内容与保存前完全一致。
7. **给定** 某 SKILL 正被一个或多个数字人引用，**当** 管理员尝试删除它，**则** 被拒绝或给出显式的影响提示。

### 用户故事 4 - MCP 服务管理 (优先级：P4)

管理员在平台上以卡片浏览运行环境中已安装的 MCP 服务（清单来源为容器编排文件中的声明），查看每个服务提供的工具清单，为每个服务配置其调用与适配信息（连接地址、是否可写、权限边界、文件参数映射），启动/关闭服务，对服务发起测试，查看服务的运行日志，并查看每个服务累计调用次数的汇总统计。

**为什么是这个优先级**：本模块是运维支撑能力，让管理员看清并掌控数字人可调用的外部能力；它不阻塞数字人"设计 → 部署"的价值闭环，因此优先级最低。

**独立测试**：只实现本故事即可端到端验证——"列出 MCP 服务 → 配置其调用信息 → 查看工具清单 → 启停该服务 → 查看日志与调用次数统计"。

**验收场景**：

1. **给定** 运行环境已安装若干 MCP 服务，**当** 管理员打开 MCP 列表，**则** 每个服务以卡片展示名称、传输方式与当前状态（运行中／已停止／异常／未知）。
2. **给定** 某服务运行中，**当** 管理员打开其详情，**则** 展示该服务提供的全部工具及每个工具的用途说明与入参说明。
3. **给定** 管理员修改某服务的连接地址或文件参数映射并保存，**当** 之后有新对话发起，**则** 数字人按新配置调用该服务，且无需修改任何数字人。
4. **给定** 某服务已停止，**当** 管理员点击启动，**则** 服务被启动且状态变为运行中；反之点击关闭后状态变为已停止。
5. **给定** 某服务处于异常状态，**当** 管理员发起测试，**则** 返回明确的失败原因（超时／连接被拒／协议不匹配等），且不把失败误报为成功。
6. **给定** 管理员查看某服务的日志，**当** 页面加载，**则** 展示按时间倒序的运行日志片段；日志量很大时页面仍能快速返回。
7. **给定** 服务已被数字人调用过若干次，**当** 管理员查看汇总统计，**则** 每个服务的累计调用次数、成功/失败次数与最近调用时间正确呈现。
8. **给定** 某服务正被数字人引用，**当** 管理员关闭该服务，**则** 提示"将影响哪些数字人"并要求二次确认。
9. **给定** 管理员为某 MCP 服务配置连接地址，**当** 打开该配置，**则** 可分别为"容器编排内网"与"宿主机本地"两种运行形态各声明一份地址，MUST NOT 只允许填一个地址；修改服务级配置后**则** 自动作用于所有引用它的数字人，无需逐个改动。

### 边缘情况

- **数字人配置损坏**（缺少 SOUL/工具/MCP 等必填段、JSON 解析失败）：列表以异常态卡片呈现并给出可读原因，绝不导致整个列表不可用。
- **数字人引用了已不存在的内置工具**：必须标为异常并指明失效工具名；不得沿用"运行期静默忽略"的行为，让管理员以为配置已生效。
- **工具说明中的用户/会话相关取值**：平台必须以占位符模板展示（如 `{数据目录}/{子目录}/示例.csv`、`{会话标识}_文件名`），不得固化某个用户或会话的具体值。
- **运行环境新增或下线内置工具**：平台无需修改代码即可跟随目录变化；下线导致的存量失效引用必须可见。
- **SKILL 元数据合法但正文为空**：视为合法 SKILL 允许安装，但给出提示。
- **上传的 ZIP 体积极大或嵌套层级极深**：必须在解压前按体积／文件数／层级上限拒绝，不得拖垮服务。
- **并发编辑**：两名管理员同时编辑同一数字人／同一 SKILL／同一 MCP 服务配置／同一部署目标时，必须避免"后保存静默覆盖先保存"，须串行化或显式冲突提示。
- **部署目标不可写**：目标目录不存在、无写权限或磁盘写满时，该用户部署整体失败并保持原状，不得留下半成品。
- **场景配置中的二级目录清单被收缩**：运行环境中该二级目录及其中的文件必须保留（仅不再出现在可访问清单里），平台不得借部署之机清理它们；平台应在界面上提示"该目录已从场景中移除，但既有文件仍保留在运行环境"。
- **同一用户的不同数字人看到不同的文件空间**：场景配置随数字人存放，各数字人的可见目录清单互不干扰、互不覆盖；但底层**文件数据**（三个空间下的实际文件）仍是该用户共享的一份，因此同一用户的不同数字人 MAY 配置出部分重叠的可见范围——这是合法状态，不得据此报错或拒绝部署。
- **校验所需信息读取不到**（内置工具目录、共享技能库或容器编排声明暂时不可读）：必须**按校验失败处理并阻止部署**，不得"读不到就跳过"从而放过一份可能失效的配置；错误信息必须说明是哪一项信息获取失败。
- **非本平台管辖的内容**：运行环境中已有的、不由平台部署的数字人／SKILL／用户，平台只读呈现，部署不得清除。
- **既有数字人引用了不在共享技能库中的 SKILL**：平台标记为"技能不在库中"供参考，不得自动导入该技能，也不得因此阻止浏览；如需纳管，由管理员自行上传同名 SKILL 到库中。若该数字人随后被纳入平台并被部署，其运行环境中那份既有技能目录将按**整体覆盖**语义被清除（因平台侧未搭配）；平台必须在部署前的确认与部署结果中明确提示这一变化。
- **MCP 服务清单为空或全部异常**：页面给出空态与引导，不报错。
- **引用冲突**：删除仍被用户关联的数字人、删除仍被数字人引用的 SKILL／MCP 服务配置、删除仍被部署的用户，必须给出引用冲突提示并阻止或要求先解除。
- **编排文件中声明的 MCP 服务容器尚未创建或已被删除**：卡片以"异常／未知"状态呈现并说明原因，不影响其余卡片与平台其余功能。
- **平台侧 MCP 服务配置与容器编排声明不一致**（服务被改名、被移除、端口变化）：卡片标为异常并给出具体差异；引用该服务的数字人部署时必须被校验拦截，绝不静默产出一份指向空地址的坏配置。
- **MCP 连接地址与部署目标运行形态不匹配**：目标形态未声明对应地址时，部署必须被校验拦截，并指明"是哪个服务缺哪个形态的地址"；不得静默回退到另一形态的地址——那会产出一份"某个形态下必然连不上"的配置，且失败只在运行期以 MCP 状态异常的形式暴露，极难定位。平台的运行位置（容器内／宿主机）不构成目标形态的依据。
- **运行环境中已物化的技能副本被手工改动**：平台以共享技能库为准，下次部署覆盖该副本，并在部署结果中如实反映。
- **部署清单与运行环境实际内容不一致**（有人手工删掉了平台部署过的数字人目录）：部署必须以平台为准重新补齐，并如实报告该差异。
- **MCP 服务名或 SKILL 名与运行环境既有项重名**：必须以既有项为准，不得产生同名两份定义。

## 需求 *(必填)*

### 功能需求

#### 平台定位与配置中心

- **FR-001**: 平台 MUST 以四个可独立进入的功能区组织——MCP 服务、SKILL 管理、数字人设计、数字人部署；每个功能区 MUST 能独立完成其核心任务而不被其他功能区阻塞。平台 MUST 以**独立子系统**形态交付：一个独立的管理界面 + 一个独立的管理服务，二者并入运行环境既有的统一入口网关与容器编排；平台 MUST 与运行环境共享同一份用户数据目录，MUST NOT 另建用户数据副本。
- **FR-002**: 平台 MUST 是**全平台唯一的配置中心**：内置工具、MCP 服务、SKILL、数字人这四类配置信息 MUST 集中存放于平台且各有唯一落点；数字人设计 MUST 只按**名称引用**这些配置，MUST NOT 让每个数字人各自携带一份配置副本。
- **FR-003**: 平台持有的 MUST 是这四类的**配置信息**，而非其本体：内置工具的实现代码、MCP 服务的容器本体分别由运行环境的代码与容器编排文件提供。平台 MUST 以只读投影的方式呈现其存在与可用性，在其变化时自动跟随呈现，MUST NOT 声称拥有或擅自改写其本体。
- **FR-004**: 数字人设计中的内置工具／MCP 服务／SKILL 三个选择器 MUST 从平台统一清单取值；同一实体在全平台 MUST 只有一种名称与语义，MUST NOT 出现同一实体两种称呼。
- **FR-005**: 平台与运行环境之间的数据流 MUST **严格单向**——只允许"平台 → 运行环境用户目录"这一个方向。据此：①平台 MUST NOT 从运行环境**反向导入**任何既有内容，共享技能库 MUST 从**空库**开始并由管理员上传建立，平台 MUST NOT 扫描并纳管既有的技能目录；②运行环境 MUST NOT 反向写回平台；③运行环境中既有的数字人目录、技能目录与用户数据 MUST 保持原样（不被修改、不被删除），除非管理员显式将其纳入平台并部署——此时按 FR-026 的**整体覆盖**语义处理。既有数字人 MAY 只读陈列供参考，但平台 MUST NOT 为其自动补齐缺失的技能库条目。**边界（MUST NOT 误读）**：本条约束的是**配置数据流**——即"谁有权改配置"。它 MUST NOT 被解读为"平台不得读取运行环境"：平台对运行环境的**只读消费**（内置工具目录见 `FR-011`／`FR-003` 的"只读投影"、容器编排声明与容器状态见 `FR-043`、MCP 运行日志见 `FR-048`、调用统计见 `FR-049`／`FR-050`）是**设计内的依赖**，平台 MUST NOT 因本条而放弃这些能力。完整判定口径见 `SC-017`。
- **FR-006**: 所有列表 MUST 以卡片形式呈现实体，卡片 MUST 至少包含名称与用途描述；异常实体 MUST 以可辨识的异常态呈现且不影响其余卡片。实体卡片列表 MUST **分页**：每页固定 4 列 × 2 行（**8 项**，末页可少于 8 项），MUST 展示总条数与当前页码并支持翻页；MUST NOT 一次性渲染全部实体。非卡片类的长内容列表（MCP 工具清单、运行日志、部署历史、异常项汇总等）MUST 具备有界返回（分页或条数上限），MUST NOT 无界返回。
- **FR-007**: 平台 MUST 对所有破坏性操作（删除数字人/SKILL/用户/MCP 服务配置、关闭被引用的 MCP 服务、覆盖已存在的 SKILL、部署覆盖）先提示影响范围并要求二次确认。
- **FR-008**: 所有写操作 MUST 具备原子性——要么完整生效要么完全不生效，MUST NOT 出现部分写入的中间状态；并发写同一目标 MUST 有冲突检测或串行化控制，MUST NOT 静默丢失更新。
- **FR-009**: 任何操作失败 MUST 给出可读且可定位的原因（具体的字段/文件/条目），MUST NOT 只返回"操作失败"。
- **FR-010**: 平台全部界面文案与项目文档 MUST 使用简体中文（技术专有名词、协议名、第三方名称保持原文）。

#### 内置工具目录

- **FR-011**: 运行环境 MUST 提供一份**可枚举的内置工具目录**，至少包含每个工具的名称、显示名、用途说明、入参说明与是否具备写能力；平台 MUST 通过该目录取得内置工具的全部信息，MUST NOT 自行硬编码一份工具清单。运行环境新增或下线内置工具后，平台 MUST 无需修改代码即可跟随呈现。
- **FR-012**: 工具目录中的用途说明 MUST 以**带占位符的模板**给出（涉及具体用户场景或会话的部分以占位符表示），MUST NOT 固化某个用户或某个会话的具体取值；平台在列表、选择器与预览中 MUST 保持模板形态呈现。
- **FR-013**: 数字人引用的内置工具若不在工具目录中（例如该工具已被下线），平台 MUST 将该数字人标记为异常并指明失效的工具名，MUST NOT 允许其在没有明显提示的情况下被保存或部署，也 MUST NOT 沿用运行期"静默忽略未知工具"的行为。

#### 数字人设计

- **FR-014**: 管理员 MUST 能浏览数字人卡片列表，并查看单个数字人的全部配置内容。
- **FR-015**: 管理员 MUST 能新建数字人；数字人名称 MUST 唯一且合法（不得含路径分隔符等非法字符），名称冲突或非法 MUST 被拒绝并说明原因。
- **FR-016**: 数字人设计 MUST 完整覆盖以下五类配置：①角色命名与 SOUL（人格设定全文）；②MCP 服务搭配；③内置工具搭配；④SKILL 搭配；⑤文件空间搭配（scenario）。
- **FR-017**: 管理员 MUST 能编辑已有数字人的任意一类配置并保存，保存后 MUST 能原样回显（含换行、标点与条目顺序）。
- **FR-018**: 保存数字人 MUST 产出一份结构化 JSON 配置，五类配置 MUST 齐全——未配置项以空集合表示，MUST NOT 缺字段；其中 MCP 服务与 SKILL 两类 MUST 以**名称引用**形式保存，MUST NOT 内嵌其连接信息、权限边界或技能正文。
- **FR-019**: SOUL MUST 为必填且非空；MCP 服务、内置工具、SKILL 三类 MUST 只能从平台统一清单中选择，MUST NOT 接受清单外的不存在引用。
- **FR-020**: 文件空间搭配 MUST 允许配置一个场景名与一组"数据准备"二级目录名；目录名 MUST 拒绝空值、重复值以及含路径分隔符或 `..` 的非法值。该配置 MUST **随数字人存放**（数字人级，落在该数字人的配置目录内），因此**同一用户的不同数字人 MAY 拥有各自的场景与可见目录清单**，互不干扰、互不覆盖；平台 MUST NOT 要求同一用户的多个数字人使用一致的场景。
- **FR-021**: 数字人已被用户关联时，平台 MUST 阻止其被直接删除，或要求先显式解除关联。
- **FR-022**: 平台 MUST 允许删除未被任何用户关联的数字人（二次确认按 `FR-007` 的统一口径执行，本条不另立口径）。

#### 数字人分发与部署

- **FR-023**: 管理员 MUST 能浏览用户卡片列表，每张卡片 MUST 展示用户名与其已关联的数字人角色名清单；卡片 MUST 可展开查看每个数字人的搭配摘要（引用的 MCP 服务、内置工具、SKILL）及其异常标记，使该页可作为"部署前核对"的总账。
- **FR-024**: 管理员 MUST 能新建与编辑用户；用户标识 MUST 唯一且合法，非法或重复 MUST 被拒绝并说明原因。
- **FR-025**: 管理员 MUST 能为某个用户增加或移除其关联的数字人；可关联的 MUST 是平台内已存在的数字人。
- **FR-026**: 管理员 MUST 能触发"部署生效"，把该用户关联的数字人**分发**到运行环境对应用户的数据目录：写入数字人的五类配置，并把其搭配的 SKILL 从共享技能库物化到该数字人的技能目录、把其搭配的 MCP 服务配置物化进该数字人的 MCP 配置文件，使运行环境无需依赖平台即可独立加载。分发的语义 MUST 为**整体覆盖**——对本次部署涉及的每个数字人，其配置 MUST 以平台侧为唯一内容来源，MUST NOT 与运行环境的既有内容做合并、协商或字段级差异保留；平台侧未搭配的内容 MUST NOT 残留在该数字人的配置中。该整体覆盖语义 MUST NOT 延伸到用户的文件空间数据（见 FR-028）。五类配置 MUST **全部落在该数字人的配置目录内**（含文件空间场景），MUST NOT 依赖任何用户级的共享配置文件。
- **FR-027**: 点击"部署生效"时，平台 MUST 在**任何写入发生之前**自动对本次部署涉及的全部用户与数字人执行一次**完整的部署前校验**，校验 MUST 为只读。校验 MUST 至少覆盖：①**配置完整性**——SOUL 非空、四类配置文件结构合法且可解析、五类配置无缺字段；②**引用有效性**——所引用的内置工具存在于工具目录、所引用的 MCP 服务存在于容器编排声明、所引用的 SKILL 存在于共享技能库；③**命名与路径安全**——数字人名、用户标识、技能目录名不含路径分隔符或 `..`；④**目标位置可写**。任一校验项不通过时，平台 MUST **阻止本次部署**、MUST NOT 产生任何写入，并 MUST **一次性列出全部错误项**（而不是发现一个就停止），每条错误 MUST 可定位到具体的用户、数字人与配置类别。校验所需信息读取不到时，MUST 按校验失败处理，MUST NOT 视为通过。
- **FR-028**: 部署的作用域 MUST 精确限定在用户的**数字人配置目录**（含 SOUL、内置工具、MCP 服务配置、SKILL 与文件空间场景五类），按 FR-026 的整体覆盖语义写入。除此之外，用户文件空间与会话数据的**内容** MUST NOT 被触碰：三个空间（数据准备／共享空间／临时空间）下**既有的文件与二级目录 MUST 全部保留**，MUST NOT 因部署而被覆盖、删除或改写，也 MUST NOT 因某个数字人的场景目录清单收缩而被清理；平台 MAY 为**新建用户**创建空的目录骨架，但 MUST NOT 写入其中任何文件内容。作用范围的边界 MUST 按**"配置 vs 数据"**划分：数字人配置目录属配置（可被覆盖），三个空间里的文件属数据（不被覆盖）。
- **FR-029**: 部署 MUST 以用户为最小生效单位——单个用户部署失败时该用户 MUST 不产生任何部分写入，且其余用户不受影响。
- **FR-030**: 部署 MUST 幂等——相同内容重复部署 MUST 得到稳定结果，MUST NOT 产生重复或损坏。
- **FR-031**: 平台的删除能力 MUST 以**部署清单**为界：平台 MUST 维护一份部署清单，记录它实际分发过的用户与数字人；部署时只有当某数字人"在清单内且本次不再需要"时才允许从运行环境移除，清单之外的内容 MUST NOT 被删除或改写。
- **FR-032**: 部署完成后 MUST 向管理员呈现结果明细：成功的用户与数字人、失败的用户与数字人及其原因；同时 MUST 如实报告与部署清单不一致的差异（如手工删改过的目录）。
- **FR-033**: 平台 MUST 记录可审计的部署历史（时间、涉及用户与数字人、结果）。
- **FR-034**: 部署生效时机 MUST 为：其后的新对话立即使用新配置；正在进行中的回答 MUST NOT 被中断，其在完成当前轮次之后切换到新配置。**责任侧划分（两侧缺一不可）**：①**运行环境侧** MUST 提供"配置变化即失效"机制——**现状缺口**：数字人配置目前**只在实例创建时读取一次**，而实例按 `(用户, 数字人)` 缓存在**实例池**中、仅"空闲超时（默认 10 分钟）"或"池满 LRU"才回收，故池中已有实例时部署后的新对话仍会使用**旧配置**，与本条直接冲突；运行环境 MUST 在取用池中实例前比对**配置指纹**（关键文件的修改时间／内容摘要），不一致即重建实例（沿用 `agent-catalog.ts` 既有的"现扫现解析、配置修复后无需重启即可重现"思路）。②**平台侧** MUST 保证写入过程**对被读取方不可见**：以**目录级原子替换**实现，MUST NOT 原地逐文件改写正在被读取的文件。③"进行中的回答不被打断"：运行环境只在**实例取用**时做失效判定，MUST NOT 中断已在执行的轮次。落地方式见 `plan.md` 的 R7 与 `contracts/runtime-api-delta.md` §8。

#### SKILL 管理

- **FR-035**: 管理员 MUST 能浏览 SKILL 卡片列表，卡片 MUST 展示技能名与描述。
- **FR-036**: 平台 MUST 维护一份**全平台共享**的 SKILL 库，作为 SKILL 的唯一权威来源；管理员 MUST 能查看库中单个 SKILL 的元数据与正文全文，并能编辑正文后保存，保存后原样回显；一个 SKILL MUST 可被任意数量的数字人以名称引用，MUST NOT 要求为每个数字人各存一份。
- **FR-037**: 管理员 MUST 能通过上传 ZIP 压缩包安装 SKILL 到共享技能库。
- **FR-038**: SKILL 安装 MUST 执行标准格式校验，至少包括：压缩包可正常解压；必须存在 `SKILL.md`；`SKILL.md` 必须含元数据块且元数据必须包含非空的 `name` 与 `description`；技能名 MUST 合法可作目录名。安装目标 MUST 是平台共享技能库，MUST NOT 直接写入某个数字人的技能目录。
- **FR-039**: SKILL 安装 MUST 执行安全校验：拒绝含绝对路径、`..` 穿越或符号链接的压缩包，拒绝解压后总大小、文件数、嵌套层级超限的压缩包；MUST NOT 在完成校验前把不可信内容写入目标目录。
- **FR-040**: SKILL 名称与库中已有 SKILL 冲突时，平台 MUST 提示并要求显式选择"覆盖"或"取消"；覆盖 MUST 整体替换为一个原子操作，并使所有引用该 SKILL 的数字人在下次部署时同步获得新内容。
- **FR-041**: SKILL 安装失败 MUST 回滚，MUST NOT 留下半解压的残留内容。
- **FR-042**: 删除被引用的 SKILL 时，平台 MUST 在确认环节列出受影响的数字人清单（该清单 MUST 与数字人配置中的 SKILL 搭配保持一致）并要求二次确认；平台 MUST NOT 为此维护常驻的"被谁引用"浏览视图。

#### MCP 服务管理

- **FR-043**: 管理员 MUST 能浏览 MCP 服务卡片列表，卡片 MUST 展示服务名、用途描述、传输方式与运行状态（运行中／已停止／异常／未知）。**状态判定口径**：`运行中`／`已停止` 取容器的实际状态；`异常` 指"编排声明与实际不一致"或"状态获取失败"；`未知` 指尚无观测结果（属**正常观测态**，MUST NOT 渲染为故障）。**用途描述**的来源为服务级配置（`FR-044`），未填写时以空占位呈现（满足 `FR-006` 对卡片信息的要求）。服务清单 MUST 以运行环境既有**容器编排文件中声明的 MCP 服务**为唯一来源，MUST NOT 要求管理员在平台内二次登记；编排文件中新增 MCP 服务后，平台 MUST 无需修改代码即可识别并展示。位于其他服务器上的 MCP 服务不在本期范围（见假设）。
- **FR-044**: 平台 MUST 为每个 MCP 服务集中维护一份**服务级配置信息**：传输方式与连接地址（或启动命令与参数）、是否具备写能力、权限边界、文件参数映射；数字人 MUST 只以名称引用该配置，MUST NOT 各自复制一份。修改服务级配置 MUST 自动作用于所有引用它的数字人。
- **FR-045**: 管理员 MUST 能查看单个 MCP 服务提供的工具清单，含每个工具的用途说明与入参说明。
- **FR-046**: 管理员 MUST 能启动与关闭 MCP 服务，操作后状态 MUST 反映真实结果；操作失败 MUST 给出原因。
- **FR-047**: 管理员 MUST 能对 MCP 服务发起测试（连通性检查 + 一次实际能力验证），并得到明确的成功/失败结果与失败原因。
- **FR-048**: 管理员 MUST 能查看单个 MCP 服务的运行日志片段；日志展示 MUST NOT 因日志量增长而拖慢页面。
- **FR-049**: 平台 MUST 提供调用次数汇总统计：按服务统计累计调用次数、成功次数、失败次数与最近调用时间。
- **FR-050**: 调用次数统计 MUST 在数字人实际调用该服务后自动更新，MUST NOT 依赖人工录入。
- **FR-051**: 关闭一个正被数字人引用的 MCP 服务时，平台 MUST 提示受影响的数字人并要求二次确认。
- **FR-052**: 服务级配置所指向的服务若在容器编排文件中已不存在或已改名，平台 MUST 将该服务配置标记为异常并给出具体差异，MUST NOT 静默保留一份指向无效目标的配置。

#### 界面结构与全局视图

- **FR-053**: 平台 MUST 以**常驻可见的一级导航**提供四个功能区的入口（MCP 服务、SKILL 管理、数字人设计、数字人部署）；一级导航 MUST 标明当前所在功能区，MUST 可完整键盘操作，且 MUST NOT 因任一功能区的内部状态而被隐藏或禁用。任一功能区内部的导航深度 MUST NOT 超过两级（列表 → 详情/编辑器）；更细的内容 MUST 以功能区内的分区或页签承载，MUST NOT 演变为新的导航层级。
- **FR-054**: 内置工具的只读目录（含每个工具的名称、用途说明与入参说明）MUST 在**数字人设计**功能区内可见，MUST NOT 作为独立功能区存在；该视图 MUST 为只读，管理员 MUST NOT 在其中编辑工具本身，也 MUST NOT 在其中常驻展示"谁引用了该工具"。
- **FR-055**: 平台 MUST 提供一个**全局异常项汇总视图**（位于数字人部署功能区内，作为该功能区内的一个分区或页签，MUST NOT 构成新的导航层级）：一次列出全平台所有引用了失效对象（已下线的内置工具、在容器编排中已被移除或改名的 MCP 服务、已不存在的 SKILL）的数字人及其所属用户，并可跳转到对应编辑位置；MUST NOT 要求管理员逐个数字人翻查。

#### 运行形态与地址下发

- **FR-056**: MCP 服务的连接地址 MUST 按**运行形态**分别声明，作为该服务服务级配置的组成部分（见 FR-044）：至少覆盖①**容器编排内网**（供运行环境各容器之间互访）与②**宿主机本地**（供在宿主机上直接运行的后端访问）。部署物化时，平台 MUST 按**目标运行形态**选取对应地址写入数字人的 MCP 配置文件，MUST NOT 把某一个运行形态的地址固化为唯一值（否则两个形态中必有一个失效）。平台 MUST NOT 要求管理员或开发者通过修改宿主机 hosts 文件、或手工编辑数字人的 MCP 配置文件来切换形态——形态切换 MUST 只经平台配置完成。
- **FR-057**: **目标运行形态 MUST 是平台的显式配置项，MUST NOT 由平台自身的运行位置推断**——用户数据目录在容器部署形态下是挂载进容器的，平台完全可能在容器内为"宿主机本地"形态产出配置。平台 MUST 在界面上常驻可见当前目标运行形态；切换目标形态 MUST 明示其影响（既有部署产物将按新形态重新物化）并按 FR-007 要求二次确认。部署前校验 MUST 把"目标形态缺少连接地址"视为校验不通过（记入 FR-027 的校验清单），MUST NOT 静默回退到另一形态的地址。

### 关键实体

- **配置中心（平台侧）**：集中存放内置工具、MCP 服务、SKILL、数字人四类配置信息的唯一位置；`.opt-agent` 与容器编排是这些配置在运行环境的落地形态。
- **内置工具目录项**：运行环境提供的内置工具描述。关键属性：名称、显示名、用途说明（占位符模板）、入参说明、是否具备写能力。本体由运行环境代码提供，平台只持有其配置信息。
- **MCP 服务（本体）**：可被数字人调用的外部工具服务，来源为运行环境容器编排文件中的声明。关键属性：名称、传输方式、运行状态、提供的工具集合、累计调用次数与最近调用时间。
- **MCP 服务配置（服务级，平台持有）**：数字人调用某个 MCP 服务所需的全部配置信息。关键属性：所属服务、传输方式、**按运行形态分别声明的连接地址**（或启动命令与参数）、是否具备写能力、权限边界、文件参数映射。**同一服务只有一份**；其中连接地址按运行形态各有取值，部署时按目标形态取用（见 FR-056／FR-057）。
- **运行形态（部署目标形态）**：平台产出部署产物时所面向的运行环境形态，决定 MCP 连接地址等"随形态而异"的配置取用哪一份取值。关键属性：形态标识（如"容器编排内网"／"宿主机本地"）。**MUST 显式配置，MUST NOT 由平台自身运行位置推断**（见 FR-057）。
- **MCP 工具**：MCP 服务提供的能力单元。关键属性：名称、用途说明、入参说明、所属服务。
- **SKILL**：平台共享技能库中的可复用能力资产包。关键属性：名称、描述、正文、安装来源、文件清单。
- **引用关系（派生信息，非实体）**：数字人对 MCP 服务／内置工具／SKILL 的引用，由平台按需从数字人配置中推导，MUST NOT 作为独立实体持久化，也 MUST NOT 表现为常驻浏览视图；其呈现时机仅为破坏性操作的确认环节、部署前校验与全局异常项汇总。
- **数字人**：角色化智能体的定义。关键属性：名称、用途描述、SOUL、引用的 MCP 服务、启用的内置工具、引用的 SKILL、文件空间场景。
- **数字人配置（设计产物）**：数字人的结构化 JSON 表示，包含上述五类配置段；其中 MCP、内置工具与 SKILL 均以**名称引用**，MUST NOT 内嵌其内容副本。
- **用户**：数字人的业务使用者（如 admin）。关键属性：用户标识、关联的数字人集合、数据骨架。**注意**：文件空间场景属**数字人级**（见「文件空间场景」），MUST NOT 作为用户的属性。
- **文件空间场景（scenario）**：**数字人级**配置，定义该数字人可见的文件空间范围（"数据准备"下允许哪些二级目录）。关键属性：场景名、"数据准备"二级目录清单。随数字人一并存放于其配置目录内；同一用户的不同数字人 MAY 有各自场景，从而看到不同的文件空间。**注意**：可见范围是数字人级的，但底层文件数据（三个空间下的实际文件）仍是该用户共享的一份。
- **部署清单**：平台记录其实际分发过的用户与数字人，用于界定部署时允许删除的范围。关键属性：用户标识、数字人名称、最近分发时间。
- **部署前校验结果**：一次"部署生效"点击所触发的校验产出。关键属性：涉及的校验项、通过/未通过、每条未通过错误的定位信息（用户、数字人、配置类别、具体原因）。
- **部署记录**：一次"部署生效"的结果。关键属性：时间、涉及用户、涉及数字人、校验结果、执行结果、与部署清单的差异。

## 成功标准 *(必填)*

### 可度量结果

- **SC-001**: 管理员从零新建一个完整数字人（五类配置齐全）并完成部署生效，总耗时不超过 5 分钟。
- **SC-002**: 四个列表页（MCP 服务、SKILL、数字人、用户）在实体数量 ≤ 100 时，从打开页面到卡片可交互的等待时间不超过 1 秒。
- **SC-003**: 100% 的不合规 SKILL 压缩包被拒绝安装，且每条拒绝都能定位到具体原因（缺失文件／缺失字段／越界路径／超限）。
- **SC-004**: 部署失败时，出现"部分写入"（部分数字人生效、部分未生效）到部署目标的次数为 0。
- **SC-005**: 管理员完成一次"配置修改 → 部署生效"的端到端成功率不低于 99%（不含因输入非法被明确拒绝的情况）。**注**：本项为**运行期观测指标**，不在实现阶段验证；实现阶段的对应保证是 `SC-004`（零部分写入）与 `SC-020`（校验不通过即零写入）。
- **SC-006**: 管理员无需登录服务器、无需手工编辑任何配置文件，即可完成"MCP 服务配置 + SKILL 安装 + 数字人设计 + 部署生效"全部四类任务。
- **SC-007**: 平台对既有运行环境数据零破坏——在未显式删除的前提下，平台任何操作后既有数字人/SKILL/用户数量不减少。
- **SC-008**: 100% 的部署操作都可在部署历史中追溯到操作时间、涉及对象与结果。
- **SC-009**: 在共享技能库中修改一个被 N 个数字人引用的 SKILL 并完成部署后，这 N 个数字人实际加载的技能内容 100% 与库中版本一致。
- **SC-010**: 在容器编排文件中新增一个 MCP 服务后，管理员无需任何平台侧配置即可在卡片列表中看到它。
- **SC-011**: 配置信息零副本——全平台任一 MCP 服务的服务级配置、任一 SKILL 的内容、任一内置工具的说明均只有一处来源；修改一处并部署一次，所有引用它的数字人 100% 同步生效。
- **SC-012**: 部署对用户文件空间**数据**产生的改动次数为 0：三个空间下既有的文件与目录数量及内容 100% 不变（某个数字人的场景目录清单收缩时也不例外）；平台仅可为新建用户创建空的目录骨架，在其中写入的文件内容为 0。
- **SC-013**: 运行环境新增或下线一个内置工具后，平台无需修改代码即可反映该变化；被下线工具的存量引用 100% 在平台界面上可见并标记为异常。
- **SC-014**: 平台界面上出现的内置工具说明中，出现某个具体用户目录名或会话标识的次数为 0（一律以占位符呈现）。
- **SC-015**: 从一级导航出发，到达任意一个配置实体的编辑位置所需的点击次数不超过 3 次。
- **SC-016**: 全平台失效引用的排查耗时：管理员通过全局异常项汇总，在一次视图内即可看到全部受影响的数字人，无需逐个打开数字人。
- **SC-017**: **配置的权威源单向**——"运行环境 → 平台"的**配置回写通道**数量为 0：平台任何功能都不会因运行环境中既有配置的存在而改变平台自身的数据；平台在运行环境产生的写入 100% 位于目标用户的数字人配置位置内。**边界（MUST NOT 误读为"平台不得读取运行环境"）**：平台对运行环境的**只读消费**——内置工具目录（`FR-011`／`FR-003` 的"只读投影"）、容器编排声明与容器状态（`FR-043`）、MCP 运行日志（`FR-048`）、调用统计（`FR-049`／`FR-050`）——**不属反向通道**，是设计内的依赖，MUST NOT 被本条排除。
- **SC-018**: 部署后运行环境中该数字人的配置与平台侧定义完全一致：平台侧未搭配却仍残留在运行环境的项数量为 0。
- **SC-019**: 同一用户关联 N 个数字人且各自场景不同时，部署后这 N 个数字人按各自场景加载的可见目录清单 100% 与平台侧配置一致，数字人之间零干扰、零覆盖（改其中一个的场景不影响其余数字人的可见范围）。
- **SC-020**: 存在任一"错误配置或不存在引用"时，部署在运行环境产生的写入次数为 **0**（100% 被阻止）；每次阻止都**一次性列出全部错误项**，管理员无需为每个错误重复点击部署以逐个发现。
- **SC-021**: 部署前校验的耗时：在单用户关联 10 个数字人的规模下，点击部署到给出校验结论的时间不超过 3 秒。
- **SC-022**: 卡片列表每页恰为 **8 项**（4 列 × 2 行，末页可少于 8 项）；翻页操作到新页可交互的等待时间不超过 100 毫秒。
- **SC-023**: 任何卡片列表在实体数量增长到 100 时，单页渲染的卡片数恒为 8，页面元素总数不随实体总量线性增长。
- **SC-024**: 在"容器编排内网"与"宿主机本地"两种运行形态下，同一份平台配置可为两种形态各产出一份可用产物：两种形态下数字人连接其 MCP 服务的成功率均为 100%，产物中的连接地址按形态正确取值（形态串用次数为 0）；完成形态切换所需的人工步骤为 **0 步**——不得要求修改宿主机的 hosts 文件，也不得要求手工编辑数字人的 MCP 配置文件。

## 假设

- **管理端本期不引入登录与多角色权限，默认单一管理员**：管理端的操作者标识固定为 `zyw_admin`，不做登录、不区分角色、不做鉴权。**注意与运行环境的"用户"区分**：`zyw_admin` 是**平台的操作者**（不参与 `users/` 目录划分），而平台的"用户"（如 `admin`）是被分配数字人的**业务使用者**——两者不可混用为同一概念。
- **平台是配置中心，运行环境是落地形态**：内置工具、MCP 服务、SKILL、数字人四类配置信息集中在平台，运行环境只消费其落地结果。
- **平台不拥有本体**：内置工具的实现代码与 MCP 服务的容器本体分别由运行环境代码与容器编排提供；平台只持有并呈现其配置信息。因此"集中管理"对这两类而言是"集中配置 + 只读投影"，而非"重新发明本体"。
- **内置工具目录由运行环境提供**：运行环境需新增一份可枚举的工具目录（名称、显示名、说明模板、入参、是否可写），作为平台呈现内置工具信息的唯一来源；平台不新建自定义工具、也不承载工具代码。
- **平台是四类配置的唯一权威源**：内置工具、MCP 服务、SKILL、数字人这四类配置信息只有在平台上能被定义与修改，运行环境只是消费方；数据流方向的完整约束见 FR-005。
- **文件空间场景是数字人级的，文件空间数据是用户级的**：场景配置随数字人存放于其配置目录内，因此同一用户的不同数字人 MAY 有各自的可见目录清单；而三个空间下的**实际文件数据**仍以用户为单位共享一份。此模型要求运行环境把场景的读取位置由用户级改为数字人级（属"对既有运行环境的改动"，见下条）。
- **对既有运行环境的改动（四处）**：本特性除新增平台侧能力外，还要求运行环境做四处改动——① 提供**可枚举的内置工具目录**（FR-011）；② 把**场景的存放与读取位置**从用户级（`users/{uid}/scenario.json`）改为数字人级（`users/{uid}/agents/{agent}/scenario.json`），并同步调整依赖它的调用链（Agent 侧可见目录清单、文件管理接口的目录校验）；③ 新增**只读**的 MCP 调用统计端点（`FR-049`／`FR-050`——计数点 MUST 落在运行环境，见 `research.md` D6）；④ 为数字人配置提供**"配置变化即失效"**机制（`FR-034`——池中实例 MUST 在配置指纹变化后重建，否则"新对话立即生效"不成立）。四处改动 MUST 在 `plan.md` 中显式登记，未登记即视为违规。改造后，运行环境中**存量的用户级 `scenario.json`** 将不再被读取；其处置方式（保留为孤儿文件、迁移到某个数字人、或清理）属运行环境侧决定，MUST 在 `plan.md` 中给出结论。平台侧 MUST NOT 读取、修改或删除该存量文件（受 FR-005 约束）。
- **对既有接口契约的变更**：场景改为数字人级后，下列**既有接口**的行为随之变化，MUST 在 `specs/**/contracts/*.md` 中登记，并保证前端类型定义与文案同步（宪章原则七）：
  ① `/api/files/*`（`upload`／`list`／`download`／`preview`／`DELETE`／`workspace`）——目录合法性改为按**当前选中数字人**的场景清单判定；**新增** `409 AGENT_NOT_SELECTED`（未选中数字人时无法确定清单，此前不校验数字人）；
  ② `POST /api/threads/:id/messages` 的 `attachments` 校验——同一引用在不同数字人下可能合法/非法，按**本轮数字人**判定；
  ③ `SCENARIO_NOT_CONFIGURED`（503）——**错误码不变**，仅 message 由"用户未设置场景信息，请联系管理员"改为"数字人 {agent} 未设置文件空间场景，请联系管理员（缺少 users/{uid}/agents/{agent}/scenario.json）"。
- **部署是覆盖式而非合并式**：分发以数字人为单位**整体覆盖**，不做字段级合并、不做双向协商，平台侧未搭配的内容不会在运行环境残留；"直接覆盖"是唯一语义。**覆盖范围仅限该数字人的配置目录**（含五类配置），**不含文件空间数据**——三个空间下既有的文件与目录一律保留。
- **部署前校验只面向"可静态判定"的错误**：校验覆盖配置完整性、引用有效性、命名与路径安全、场景一致性、目标可写性；MUST NOT 试图校验运行期才能确定的行为（如 MCP 服务当时是否真的能连上、SOUL 文本的语义质量）。
- **设计态与运行态分离**：平台需要一份设计态存储，"已修改但未部署"是合法状态；部署是"设计态 → 运行态"的显式动作。设计态与运行态的差异以设计态为准。平台侧的**共享技能库**与**服务级 MCP 配置**是唯一权威源，运行环境中的副本是部署物化出的派生物。
- **SKILL 与服务级 MCP 配置只在平台上编辑**：对运行环境中已物化副本的手工修改会在下次部署时被覆盖，因此平台需明确"内容以平台为准"。
- **部署不中断进行中的对话**：部署后的新对话立即生效；正在进行中的回答不被打断，在完成当前轮次后切换配置。
- **平台不改变既有对话工作台**：本平台以独立子系统形态新增，除统一入口的路由配置外，不修改既有对话工作台的行为与接口契约。
- **MCP 服务清单来源＝本机容器编排文件**：本期只纳管运行环境所在机器上、由容器编排文件声明的 MCP 服务；位于**其他服务器**上的 MCP 服务本期不纳入（既不出现在卡片列表，也不能被数字人搭配），留待后续特性处理。
- **MCP 连接地址随运行形态而异，目标形态由平台显式配置**：同一个 MCP 服务的连接地址在不同运行形态下取值不同——容器编排内网用**服务名**（如 `http://ocr:8000/mcp`），宿主机本地用**宿主机可达地址**（如 `http://127.0.0.1:8000/mcp`）。本期至少支持这两种形态；目标形态是平台的显式配置项（FR-057），**MUST NOT 由平台自身运行位置推断**（用户数据目录在容器形态下是挂载进容器的，平台可能在容器内为本地形态产出配置）。该矛盾的既有表现已在运行环境中被实际观察到：本地把后端跑在宿主机时，数字人配置里的服务名地址无法解析，只能靠**手工修改宿主机 hosts 文件**绕开——这一手工步骤正是本特性 MUST 消除的（FR-056、SC-024）。
- **MCP 服务不由平台安装**：平台负责已纳管 MCP 服务的配置、启停、查看、测试与调用统计，不负责从零安装新的 MCP 服务或编写其代码；新增服务仍需修改容器编排文件并重建/重启。
- **运行环境具备容器能力**：平台运行在同一台已具备容器运行环境的机器上，已纳管的 MCP 服务可通过容器方式启动/停止并读取日志。
- **数据量级为百级以内，但列表必须分页**：单机内部平台，无需考虑分布式部署与水平扩容；但卡片列表 MUST 分页（每页 4 列 × 2 行 = 8 项），MUST NOT 一次性渲染全部实体。
- **不反向导入，从空库开始**：平台不从运行环境反向导入既有内容；共享技能库从空库开始，由管理员上传建立。运行环境中既有的数字人、技能目录与用户数据一律不碰（不修改、不删除）；平台首次接管时不做批量改写，也不要求先完成一次性迁移。
- **界面排列顺序与实现优先级相互独立**：一级导航按"MCP 服务 → SKILL 管理 → 数字人设计 → 数字人部署"排列（这是数据流向顺序，符合管理员的心智模型）；实现顺序按 P1 数字人设计 → P2 数字人部署 → P3 SKILL 管理 → P4 MCP 服务。两者不冲突。
- **引用关系不落库**：数字人对 MCP 服务／内置工具／SKILL 的引用由平台按需从数字人配置推导，不作为独立数据保存；平台只在破坏性操作的确认环节与全局异常项汇总中使用它。
- **文档语言**：规格、计划、任务、接口契约等全部项目文档使用简体中文。
