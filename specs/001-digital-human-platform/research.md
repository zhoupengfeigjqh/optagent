# 技术研究：数字人管理平台（Phase 0）

**特性**：`001-digital-human-platform` | **日期**：2026-09-15 | **上游**：[plan.md](./plan.md)、[spec.md](./spec.md)

本文件记录实现前必须落定的技术决策。按宪章原则六，**每一条新增依赖都必须在 D2 登记**（选型理由 + 被否决的替代方案 + 版本锁定）；未登记即视为违规。

## D1 技术栈：与运行环境同构（TypeScript / Node），而非 Java

**决策**：`admin-backend` 采用 TypeScript 6 / Node 20+（镜像 Node 22）/ Fastify 5 / ESM，与 `agent-backend` 完全同构；`admin-frontend` 采用 Vue 3 + Vite + TypeScript，与 `frontend` 完全同构。

**理由**（按强度排序）：

1. **平台的工作就是读写 `agent-backend` 已在读写的那批文件、说它已在说的那个协议。** 平台要读写的文件是 `SOUL.md` / `TOOL.json` / `MCP.json` / `scenario.json` / `skills/**`；而 `agent-backend/src/domain/` 中已有 `loadAgentConfig`（读四类配置）、`loadScenario` / `parseSpaceDir`（场景校验）、`listAgents` / `getAgentDetail`（数字人枚举）。换技术栈＝把这套格式约定**重写第二份**——这是规格 `FR-002/003`「配置零副本」在**代码层的翻版**，且更难发现（两份实现只在边界输入上漂移）。
2. **MCP 客户端已是既有依赖。** `@modelcontextprotocol/sdk@1.30` 已在 `agent-backend/package.json` 中，且运行环境已用它跑通真实连接（实测 `status: connected`）。`FR-045`（工具清单）与 `FR-047`（连通性 + 能力验证）直接复用同一客户端行为，避免"平台测试通过、运行环境连不上"这类**协议口径漂移**。
3. **原则七的「契约四处同步」可由编译器机械保证。** 契约文档、前端类型、后端 schema、测试用例必须同次更新；同栈时前端 `src/api/types.ts` 可与后端 schema **同源**，跨语言只能靠生成器或人工比对——而"人工比对"正是原则七要消灭的对象。
4. **工具链一致性。** 宪章「技术栈与工程约束」要求工具链大版本两侧一致（TypeScript 6 / ESLint 10 / Vitest 5 / Node ≥ 20），原则八要求"每个子项目一条命令跑门禁"。引入 Java 将带来**第 4 套运行时与第 4 套构建/测试工具链**（现有：Vue+TS / TS+Fastify / Python / nginx）。
5. **重量级失配。** 规格假设明写"数据量级百级以内、单机内部平台、无需分布式与水平扩容"；平台的工作是**文件读写 + 调用外部进程/容器**（IO 密集），JVM 的吞吐与事务优势用不上，却要付出更大的镜像、更慢的启动与更高的常驻内存。

**被否决的替代方案**：

| 方案 | 否决理由 |
|---|---|
| Java + Spring Boot | ①格式解析与 MCP 客户端需重写第二份；②新增第 4 套工具链，与原则八"一条命令跑门禁"、"前后端对称"的推广成本高；③规模用不上 JVM 强项。**唯一明显占优处**是 ZIP 安全解压（JDK 自带成熟的 `java.util.zip`），但仅涉 `FR-037~039` 一个功能点，不足以翻盘 |
| Python（复用 `ocr-service` 技术栈） | 与 `agent-backend` 的格式解析代码仍无法共享；且需引入第 3 套 Web 框架与测试框架 |
| 并入 `agent-backend` 进程（不独立服务） | 直接违反 `FR-001`（独立管理服务）；且会把**管理面**（写配置、操作容器）与**数据面**（服务对话）的权限边界混在一起 |

**重新评估的触发条件**（满足任意两条即应重新选型）：①有独立 Java 团队长期维护；②平台演变为服务多个 agent 运行环境的公司级配置中心（多机、多租户、需要事务与审计）；③出现远超"百级数据"的并发/吞吐需求；④公司合规强制特定技术栈。

## D3 宿主资源访问：Docker Engine API over Unix Socket（零依赖）

**决策**：`admin-backend` 通过挂载的 `/var/run/docker.sock`，用 **Node 内置 `node:http` 的 `{ socketPath }`** 直接调用 Docker Engine API，不引入任何 Docker SDK。可访问的操作**限定为**：①容器列表与状态查询（`FR-043`）；②容器日志读取（`FR-048`）；③对**白名单内** MCP 服务容器的 `start` / `stop`（`FR-046`）。其余 API（构建、删除、exec、卷操作）**不得调用**，并在代码中以单一模块收口以便审查。

**理由**：①`FR-043/046/048` 必须从宿主机读取容器状态与日志，这是唯一可行路径；②Node 内置 `http.request` 支持 `socketPath`，因此**零新增依赖**，符合原则六；③`docker-compose.yml` 的**声明式解析**交给 `yaml` 库（只读文件），与 Docker 查询职责分离——文件声明是"应该有什么"，Engine API 是"实际是什么"，两者的差异正是 `FR-052` 要求检测的对象。

**被否决的替代方案**：

| 方案 | 否决理由 |
|---|---|
| 容器内安装 `docker` + `compose` CLI | ①镜像显著变大（CLI + 插件）；②需处理"容器内路径 ↔ 宿主机路径"的映射才能让 compose 找到项目文件，脆弱；③属"引入非必要新基础设施"（原则六） |
| 由 `agent-backend` 代理容器操作 | ①脏化数据面职责（管理面能力塞进对话服务）；②它自身也无 Docker 权限，等于把问题平移后仍需挂 socket |
| `dockerode` 等 SDK | 功能远超声明的三项操作，属"能在原生能力上实现却引库" |

**风险登记（MUST 在实现说明与部署说明中显式标注）**：挂载 Docker socket **等价于授予宿主机 root 权限**。本平台是单机内部管理工具，采用以下约束把暴露面压到最小：①只挂 socket，不挂 `docker` 二进制；②操作白名单收口在 `infra/docker-host.ts` 单一模块；③**不**暴露任何"任意 API 透传"端点，管理界面只能触发上述三类操作；④新增的 `GET /api/admin/platform/health` 明确报告 socket 是否可达，便于排查。

## D4 平台设计态存储：JSON 文档 + 原子替换

**决策**：平台自身的配置（四类配置信息、用户与关联关系、部署清单、部署历史）存放在 `platform-data/`（仓库根，bind mount 进 `admin-backend`），以 JSON 文档组织，写入采用**写临时文件 → `fsync` → 原子 `rename`**。

**理由**：①`FR-001` 要求与运行环境共享用户数据目录、MUST NOT 另建用户数据副本——**设计态不属于用户数据**，故放在独立目录，既满足 FR-001 又不污染 `.opt-agent`；②数据量百级，读取全部在内存处理即可满足 `SC-002`（≤1s）；③JSON 可直接人工检视与 diff，便于"设计态 vs 运行态"的差异排查（`FR-032`）；④零新增依赖（原则六）；⑤原子替换满足原则五"所有涉及状态变更的操作 MUST 使用事务或等价的原子替换"。

**并发控制**：单管理员前提（规格假设）下并发写概率极低，但仍按原则五要求实现"检查 + 占位"：写入前校验文档版本号（单调递增的 `revision`），版本不符即拒绝并提示冲突（`FR-008`、边缘情况「并发编辑」）。

**被否决的替代方案**：`better-sqlite3`（既有依赖、可复用，但为百级数据引入表结构与迁移成本，且人工检视不如 JSON 直观——**若日后平台需服务多个运行环境则重新评估**）；复用 `.opt-agent/`（违反 `FR-005` 单向流与 `FR-028` 的部署作用域边界）。

## D5 前端零第三方库：UI 需求 → Vue 3 原生能力映射

**决策**：管理界面的全部交互用 Vue 3 原生能力 + 平台原生语义元素实现，**不引入 `vue-router`、`pinia` 或任何 UI 组件库**。

| 需求 | 实现方式 | 无障碍落点（原则四） |
|---|---|---|
| 一级导航（4 个功能区） | `<nav>` + `<button>`/`<a>`，当前项加 `aria-current="page"`；状态用 `reactive` | 完整键盘可达；`FR-053` 要求常驻可见、不因内部状态禁用 |
| 功能区内两级导航 | 纯状态切换（列表 ↔ 详情/编辑器），用 `ref` 承载 | 焦点管理：进入详情后焦点移交标题/首字段，返回后回到原触发元素 |
| 路由（可刷新可分享） | 原生 History API + `popstate`，约 60~90 行的小模块 `api/` 之外独立成 `router.ts` 并单测 | 后退/前进键行为正确 |
| 卡片列表（每页 8 项） | `<ul>` + `<li>` + `<article>`，`computed` 切片 | 列表语义 + `aria-label` 说明总数与页码 |
| 分页 | `<button>` + `aria-label="第 N 页"`，当前页 `aria-current="page"` | 键盘可达 |
| 二次确认（破坏性操作） | **原生 `<dialog>`** + `showModal()` | 焦点陷阱、Esc 关闭、`aria-modal` 由浏览器提供；避免自建 Modal |
| 用户卡片展开搭配摘要 | **原生 `<details>` / `<summary>`** | 原生键盘与读屏支持 |
| 功能区内分区/页签 | ARIA Tabs 模式（`role="tablist"/"tab"/"tabpanel"` + 方向键） | `FR-053` 限制导航深度不超过两级，页签承载细分内容 |
| 选择器（内置工具/MCP/SKILL） | 原生 `<select multiple>` 或自建 listbox + 完整 `aria-*` | 复合控件方向键移动、`aria-selected` |
| 全局提示/部署结果 | `aria-live="polite"` 区域 + 文本（不只靠颜色） | `FR-009` 的可读原因 |
| 异常态 | 图标 + 文本双通道（`FR-006`） | 色觉障碍可用（原则四） |
| 动效 | 尊重 `prefers-reduced-motion` | 原则四 |

**理由**：`FR-006/053` 的界面需求（卡片、分页、两级导航、页签）全部落在平台原生元素的能力范围内；自建 Modal/路由库带来的收益不足以抵消新增依赖与升级成本（原则六）。**风险**：自建路由与确认框属"自研基础设施"，故 MUST 各自成模块并**有单元测试**（原则三）。

**被否决的替代方案**：`vue-router`（4 个功能区 + 两级导航不需要嵌套路由与守卫，原生 History API 足够）；`pinia`（平台状态是"当前用户/当前数字人/当前功能区"这类少量共享状态，`provide/inject` + `reactive` 足够）；组件库（会同时引入样式与可访问性口径，与"自有样式 + Scoped CSS"的既有风格冲突）。

## D6 MCP 调用次数统计口径与来源

**决策**：调用统计由**运行环境侧计数**——`agent-backend` 在 MCP 工具调用点累计（按服务名），持久化到既有 `UsageDb`（sqlite），并新增只读端点 `GET /api/mcp-call-stats`；平台经该端点采集（对应 `plan.md` 的 R4）。统计口径明确定义为**MCP 工具调用次数**（每次工具调用计一次，成功/失败按工具调用结果分列），最近调用时间取最后一次调用的时刻。

**理由**：①运行环境是**唯一确切知道"工具被调用"发生的地方**；②与日志格式解耦——各 MCP 服务的日志格式由服务自身决定（OCR 为 uvicorn 格式，其他服务可能不同），解析日志不可靠；③正确放置计数点只需在既有 MCP 工具适配层加一处，改动面小。

**被否决的替代方案**：

| 方案 | 否决理由 |
|---|---|
| 解析 MCP 容器日志统计 | ①日志格式随服务而异，解析脆弱；②一次 streamable-http 会话可能包含 `initialize` / `tools/list` / 多次 `tools/call`，"HTTP 请求数"与"工具调用次数"**不等价**，会给出误导性数字（`FR-049` 要求"成功/失败次数"） |
| 平台作为 MCP 代理（数字人经平台调用 MCP） | ①把平台变成**运行期关键路径**——平台故障将导致数字人无法调用任何工具，违反 `FR-026`"使运行环境无需依赖平台即可独立加载"；②需改动运行环境既有的直连方式，改动面远大于加一个端点 |

**与 `FR-005` / `SC-017` 的关系（MUST 回写规格）**：本决策与 `FR-048`（读容器日志）都要求平台**只读采集运行观测**，而 `SC-017` 现表述为"运行环境 → 平台的反向数据通道数量为 **0**"。二者需澄清：**「严格单向」约束的是配置数据流**（平台不得反向导入配置、运行环境不得回写平台配置），运行观测的只读采集不在其列。处置见 `plan.md` § 已知口径差异，MUST 在实现前补入 `spec.md` 的 `FR-005` / `SC-017`。

## D7 SKILL ZIP 安全解压：引入 `yauzl`（本特性唯一新增依赖）

**决策**：引入 `yauzl`（运行时依赖，零自身依赖）+ `@types/yauzl`（开发依赖），版本在安装时锁定并提交 `package-lock.json`。以 `lazyEntries: true` 逐条读取条目元数据，**先校验、后解压**。

**理由**：①`FR-038/039` 要求标准格式校验 + 安全校验（拒绝绝对路径、`..` 穿越、符号链接；限制解压后总大小、文件数与嵌套层级），且 **MUST NOT 在完成校验前把不可信内容写入目标目录**——`yauzl` 的惰性条目枚举天然支持"逐个条目先看元数据（`fileName`、`uncompressedSize`、`externalFileAttributes` 的符号链接位）再决定是否读取"，与需求结构对齐；②自身零依赖，符合原则六对"必要性"的要求；③纯 JavaScript，无原生模块，不会引入 `better-sqlite3` 那样的平台二进制风险（原则三的平台差异风险）。

**被否决的替代方案**：

| 方案 | 否决理由 |
|---|---|
| 手写 ZIP 解析（Node 内置 `zlib.inflateRawSync`） | Node **标准库不提供 ZIP 归档读取**（只有原始 deflate 流）。手写需正确处理 local file header、central directory、data descriptor、ZIP64 与编码标志，约 300 行**安全敏感**代码——自研解析器是典型的高漏洞面，与 `FR-039` 的安全目标相悖 |
| `fflate` | 更现代且自带类型，但默认把条目解压进内存（zip bomb 需靠 `filter` 钩子额外防护），"先校验后解压"不如 `yauzl` 的惰性模型直接 |
| `adm-zip` | 历史上出现过路径穿越相关漏洞，维护活跃度较低 |
| `unzipper` | 传递依赖较多，违反"非必要不引入" |
| 不用 ZIP，只接受目录上传 | 违反 `FR-037`（上传 ZIP 是明确需求） |

**与原则六的关系**：原则六要求"能用平台或框架原生能力实现的 MUST NOT 引库"——ZIP 归档解析**不是** Node 的原生能力，故本依赖属"必要"；同时按原则六完成登记（选型理由、被否决方案、版本锁定）。

**前端不涉及**：ZIP 由管理界面上传至 `admin-backend`，前端不做解压，故前端仍为零第三方运行时依赖。

## D8 部署物化：临时目录构建 + 目录级原子改名

**决策**：一次"部署生效"对**每个用户**的物化过程为：①在目标用户目录的**同挂载点**下创建临时目录（如 `.deploy-tmp-{revision}`）；②把该用户全部数字人的五类配置（`SOUL.md` / `TOOL.json` / `MCP.json` / `scenario.json` / `skills/{name}/SKILL.md`）完整写入临时目录；③校验写入结果；④以**目录级 `rename`** 原子替换目标目录；⑤清理临时目录。

**理由**：`FR-008` 要求原子性、`FR-029` 要求"以用户为最小生效单位且失败不留部分写入"、`FR-026` 要求整体覆盖——三者合起来只有"构建完整产物 → 一次改名"能满足。`FR-027` 要求校验在**任何写入发生之前**完成，故校验先于①执行（只读）。

**关键实现约束（进入 Complexity Tracking）**：`rename` 的原子性**仅在同一文件系统内成立**。`platform-data/` 与 `.opt-agent/` 是两个 bind mount，可能不同设备。因此实现 MUST：①临时目录**建在目标目录的父目录内**（保证同设备），而非建在 `platform-data/`；②改名失败（`EXDEV`）时**降级**为"逐文件替换 + 失败回滚"，并把该降级路径纳入集成测试。

**被否决的替代方案**：逐文件原地覆盖（中途失败即产生半成品，直接违反 `FR-029`）；先在 `platform-data/` 构建再移动到 `.opt-agent/`（跨设备 `rename` 失败，触发不必要的降级路径）。

## D9 硬门禁「单文件行数」「依赖清单」的自动检查（建议随本特性落地）

**决策**：为两个新子项目各加两条零依赖 npm 脚本，使其成为可执行的硬门禁：

- `check:lines`：遍历 `src/**`、`tests/**` 的 `.ts`/`.vue`/`.js`，任一文件超过 **500 行**即以非零退出码失败（原则二 / 硬门禁三项）。
- `check:deps`：读取本子项目 `package.json` 的 `dependencies` / `devDependencies`，与本文件 D2 的清单比对，出现**未登记依赖**即以非零退出码失败（原则六 / 硬门禁三项）。

两者纳入 `quickstart.md` 记录的门禁命令序列，并与 `lint` / `typecheck` / `test:coverage` / `build` 并列。

**理由**：宪章「开发工作流与质量门禁」把覆盖率、单文件行数、依赖清单列为**硬门禁三项**，并规定"任一项未达标，任务 MUST NOT 标记完成"；而当前**只有覆盖率有自动证据**，行数与依赖清单靠人工核对。本特性新增两个子项目，正是把检查落地的时机。

**范围说明**：该两项**不属本特性功能需求**（不在 `FR-001~057` 内），故登记为 `plan.md` 待办 3，由 `/speckit.tasks` 决定是否纳入本特性的任务清单；若纳入，则同时覆盖既有 `frontend` / `agent-backend` 的**新增文件**（不回溯存量）。

**被否决的替代方案**：引入现成的行数/依赖检查工具（新增依赖，且规则比"≤500 行 + 白名单比对"复杂得多，违反原则六）。

## D10 网关路由与前端 API 基址

**决策**：`admin-frontend` 的静态资源挂在 `/admin/`，`admin-backend` 的接口挂在 `/api/admin/`。

```nginx
# 管理平台接口（最长前缀，优先于 /api/）
location /api/admin/ {
    proxy_pass http://admin-backend:3001;   # 容器内 admin-backend 监听 3001（2026-09-20 起与本地形态统一）
    ...
}
# 管理平台界面（静态资源）
location /admin/ {
    proxy_pass http://admin-frontend:80;
    ...
}
```

**理由**：①宪章「技术栈与工程约束」要求"前端 API 基址 MUST 走同源相对路径（`/api/*`）"——用 `/api/admin/*` 保持**字面一致**，而非另立 `/admin-api/*`；②nginx 前缀匹配取**最长优先**，故 `/api/admin/` 与既有 `/api/` 不冲突；③管理界面走 `/admin/` 与既有 `/`（对话工作台）并存，符合 `FR-001`「独立子系统」与「并入既有统一入口网关」。

**同时必须清理**：`gateway/nginx.conf` 中三段「待接入」注释（`/mcp/`、`/skill/`、`/designer/`）描述的是"三个独立平台"的旧设想，与 `FR-001`（四个功能区合成**一个**平台）不一致，MUST 删除以免误导后续实现。

**被否决的替代方案**：`/admin-api/*`（偏离宪章的 `/api/*` 字面约定）；把管理界面并入既有 `frontend` 的某个路由（违反 `FR-001`「独立管理界面」）。

## D11 平台自身鉴权：不引入

**决策**：管理端**不做**登录、鉴权与多角色权限，操作者标识固定为 `zyw_admin`；该标识只用于审计字段（部署历史、日志），**不参与** `users/` 目录划分。

**理由**：规格假设已定稿（"管理端本期不引入登录与多角色权限，默认单一管理员"），且明确要求与运行环境的"用户"（如 `admin`）区分——前者是**平台操作者**，后者是**被分配数字人的业务使用者**，二者不可混用。

**风险与缓解**：无鉴权意味着 `/api/admin/*` 与 `/admin/` 对能访问网关的任何人是开放的。当前部署形态是单机内部工具（`gateway` 仅映射 `82 → 80`，未对公网暴露），风险可接受；**MUST 在 `quickstart.md` 的部署说明中标注该边界**，并在引入登录能力前不得对公网暴露网关端口。

**被否决的替代方案**：本期就加 JWT/会话（超出规格范围，且 `FR-*` 未定义任何登录流程与权限模型）；用网关 Basic Auth（部署形态相关配置，仍不解决权限模型问题，且需修改既有 gateway 配置口径）。
