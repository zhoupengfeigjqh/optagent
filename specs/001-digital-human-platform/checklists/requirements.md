| 补充 19 | **Docker Engine API 的版本协商** | 平台访问宿主机 Docker **不写死 Engine API 版本**，路径不带版本前缀，由守护进程协商。理由：写死版本会在较新守护进程上直接失败（实测 Engine 29 要求最低 `1.44`，写死 `v1.43` 会回 `400 client version is too old`），而该失败只表现为 `health` 的 `docker.available=false`，与"未挂载 socket／无权限"**无法区分** | FR-043、FR-046、FR-048；来源：实现期真实部署冒烟抓出的缺陷（见 `quickstart.md` §10.3） |
| 补充 20 | **编排内服务的传输方式默认值** | 容器编排里声明的服务**一律按 `http`** 处理（含"不对外暴露端口"的内网服务）。理由：容器网络里的服务对平台而言必然是跨进程网络调用，`stdio` 只对"能在本地直接起一个命令"成立，**只能由服务级配置显式声明**（`FR-044`）。用"是否有 `ports`"判断会把内网 streamable-http 服务标成 `stdio`，即向管理员展示**错误**信息 | FR-043、FR-044、FR-006；来源：实现期真实部署冒烟抓出的缺陷（见 `quickstart.md` §10.3）；权威值仍以服务级配置为准 |

## 备注

- 因新增部署前校验需插入部署章节中间，本版对**功能需求编号做了统一重排**（现为 FR-001～FR-057）；带"补充 N"的决策表已全部指向新编号。
- FR-003 明确了一条边界：平台集中持有的是四类**配置信息**，而内置工具的**实现代码**与 MCP 服务的**容器本体**仍由运行环境代码与容器编排提供。区分"配置信息"与"本体"是为了避免出现一份与编排文件／代码重复的假权威源。
- 本特性共隐含**两处对既有运行环境的改动**，均已在假设「对既有运行环境的改动（两处）」中登记，`plan.md` MUST 显式给出方案：
  1. **提供可枚举的内置工具目录**（FR-011～FR-013），并把当前分散在两处的工具元数据收拢为单一来源——`agent-instance.ts` 的 `BUILTIN_TOOL_NAMES` 与 `builtin-tools.ts` 的元数据目前各自维护、无机制保证一致；
  2. **场景的存放与读取位置由用户级改为数字人级**（`users/{uid}/scenario.json` → `users/{uid}/agents/{agent}/scenario.json`），并同步调整依赖它的调用链：Agent 侧可见目录清单（`agent-factory.ts` 的 `listAvailableDirs`）、文件管理接口的目录校验（`dirs.ts` 的 `parseSpaceDir`）。**该项已实现**：存量用户级 `.opt-agent/users/admin/scenario.json` 已删除；`demo` 与 `demo2` 各自建立了数字人级场景文件。
- 本次改动还引起**既有接口契约变更**（已登记于假设「对既有接口契约的变更」，`contracts/*.md` 阶段必须写入）：`/api/files/*` 与 `POST /api/threads/:id/messages` 的目录合法性改为按当前/本轮数字人的场景判定；`/api/files/*` 新增 `409 AGENT_NOT_SELECTED`；`SCENARIO_NOT_CONFIGURED` 错误码不变、message 改为指名数字人。
- **实现期已完成的验证（原文记于容器内执行；已于 2026-09-15 改由宿主机本地复核，容器内测试的做法已按宪章 2.0.0 废止）**：
  - 后端：`npm run build`（tsc）通过；`npm run test:all` → **3 个测试文件 / 26 个用例全过**（`tests/unit/dirs.spec.ts` 12 例覆盖纯逻辑、`tests/integration/files-scenario.spec.ts` 7 例覆盖端点行为：未选中→409、目录合法性随当前数字人的清单判定、workspace 随选中变化、未配置场景→503）；**上述结果均为 2026-09-15 宿主机本地复核所得**；
  - 前端：`npm run build`（vite build）与 `npm run typecheck`（vue-tsc）通过；**均为 2026-09-15 宿主机本地复核结果**；
  - 前端行为变化：未选中数字人时打开文件空间面板提示"请先选择数字人"；切换数字人后自动重取文件空间（`useAppSession` 的 `onSwitched`）。
- **本需求（补充 17）的来源是一次实际观察到的本地联调故障**（2026-09-15）：后端在宿主机运行、OCR MCP 服务在容器运行时，数字人配置里的 `http://ocr:8000/mcp`（容器编排内的服务名）在宿主机无法解析，MCP 连接状态为 `failed`；连接成功后又暴露出**签名直链的回源地址**同样随运行形态而异（ocr 容器必须经 `host.docker.internal` 才能回源到宿主机后端）。当时的绕开手段是**修改宿主机 hosts 文件**并调整后端的对外基址——这两个手工步骤都不应长期存在，故立此需求。该故障同时验证了一条边界：数字人配置文件是**部署产物**，MUST NOT 被当作本地联调的调节旋钮（与假设「设计态与运行态分离」一致）。
- FR-013 修正了运行环境的既有行为：当前对数字人配置中的未知工具是"warn 后忽略"，平台侧必须改为可见的异常态，不得让"配了等于没配"。
