# 前端组件库 Constitution

## Core Principles

### 原则一：中文文档优先（NON-NEGOTIABLE）

所有项目文档——包括规范（spec）、计划（plan）、任务（tasks）、清单（checklist）、
研究报告（research）以及其他 Spec Kit 产出物——MUST 使用中文编写。

- 文档正文、标题、表格、注释性说明 MUST 为中文；代码标识符、API 名称、专有技术名词
  可保留英文原形。
- 新增或修改文档 MUST 在评审中校验语言一致性，出现非中文正文视为不合规。

理由：统一的文档语言降低跨团队沟通成本，确保规范—计划—任务链条可被完整追溯与评审。

### 原则二：代码质量与风格一致性

- 代码 MUST 遵循所用框架的官方推荐代码风格与官方 lint/格式化规则。
- 组件命名 MUST 遵循 PascalCase 规范（如 `ChatBubble.tsx`、`ChatBubble`）。
- 单个组件文件 MUST NOT 超过 500 行；超出时 MUST 拆分为子组件、自定义 Hook 或
  纯函数工具模块。

理由：统一的风格与文件规模约束提升可读性、可测试性与 AI 可导航性，避免巨型组件带来的
维护与评审负担。

### 原则三：测试完备性（NON-NEGOTIABLE）

- 每个组件 MUST 有对应的单元测试，组件与测试文件一一对应。
- 核心逻辑的代码覆盖率 MUST NOT 低于 80%。
- 测试 MUST 覆盖以下三类场景：属性（props）传递、事件触发、边界条件（空值、
  极值、异常输入、禁用态等）。

理由：组件库的契约稳定性依赖测试保障；仅覆盖正常路径无法防止回归，边界与事件路径
是缺陷高发区。

### 原则四：用户体验与无障碍

- 组件 MUST 支持键盘导航（可获得焦点、可操作、焦点顺序合理、焦点可见）。
- 组件 MUST 遵循 WAI-ARIA 无障碍指南，提供正确的角色、状态与属性标注。
- 所有交互反馈延迟 MUST NOT 超过 100ms；LLM、Agent、大语言模型相关的异步交互除外，
  但此类交互 MUST 提供明确的加载或流式反馈状态。
- Agent 对话相关设计 SHOULD 参考 Ant Design X 的 RICH 范式作为设计框架。

理由：无障碍与低延迟反馈是可访问、可用的组件库底线；对 LLM/Agent 场景区分对待，
避免以同步延迟指标约束本质上长耗时的推理交互。

### 原则五：渲染性能

- 单个组件首次渲染时间 MUST NOT 超过 100ms。
- 渲染函数中 MUST NOT 执行昂贵计算（如大数组排序、复杂派生计算、深层遍历）。
  此类计算 MUST 移至 memo 化、预计算、状态提升或 Web Worker 中执行。

理由：首次渲染性能直接决定感知流畅度；在渲染路径中放置昂贵计算会成倍放大到每次
更新，是性能退化的主要来源。

### 原则六：依赖治理

- MUST NOT 引入非必要的第三方依赖；能由现有依赖或标准能力实现的功能 MUST 自行实现。
- 引入任何新依赖 MUST 说明选型理由，并记录在案（如依赖决策记录 / ADR）。

理由：依赖是长期的维护、安全与体积成本；显式记录选型理由可防止依赖蔓延并支持
后续审计与替换。

## 技术约束与合规标准

- **运行环境**：面向现代浏览器，遵循框架官方推荐的工程与构建实践。
- **无障碍基线**：以 WAI-ARIA Authoring Practices 作为组件交互模式的实现基线。
- **性能度量**：首次渲染以单组件挂载到可见的耗时度量；交互反馈以用户操作到可见
  响应的耗时度量，均以 100ms 为上限。
- **例外范围**：LLM / Agent / 大语言模型相关交互不受 100ms 反馈上限约束，但 MUST
  提供加载、进度或流式输出等状态反馈。
- **依赖登记**：每个新增依赖 MUST 在依赖决策记录中登记选型理由与替代方案评估。

## 开发工作流与质量门禁

- 所有规范、计划、任务等文档 MUST 使用中文，并在评审中校验。
- 提交 MUST 通过 lint、格式化、单元测试与覆盖率门禁（核心逻辑 ≥ 80%）后方可合入。
- 代码评审 MUST 逐项校验本宪章的六项原则；任何违反项 MUST 记录理由或完成整改。
- 组件新增或变更 MUST 同步更新对应单元测试，并完成键盘导航与 WAI-ARIA 验证。
- 引入新依赖的变更 MUST 附带选型理由记录，否则不得合入。

## Governance

- **宪章优先**：本宪章优先于其他所有开发实践；出现冲突时以本宪章为准。
- **修订程序**：修订 MUST 以文档形式提出，说明动机、影响范围与迁移方案，经维护者
  评审批准后方可生效。
- **版本策略**：采用语义化版本 `MAJOR.MINOR.PATCH`。
  - MAJOR：不兼容的治理变更、原则移除或重定义。
  - MINOR：新增原则或章节，或对现有指引作实质性扩展。
  - PATCH：澄清、措辞修正、错别字等非语义性修订。
- **合规审查**：所有 PR / 评审 MUST 校验合规性；任何复杂度或例外 MUST 说明理由。
  运行时开发指引以本宪章为准。
