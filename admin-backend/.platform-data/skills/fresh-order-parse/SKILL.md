# 生鲜订单识别技能

主流程一句话：**用户上传「订单图片 + SKU 清单」→ 用文件空间相对路径调用 `fresh_order_parse` → 三张表展示 → 对异常/存疑行用 `read_file` 查 SKU 清单，给出推荐与证据 → 用一张最终推荐表收口，推荐的品种与 SKU 编码标红。**

## 一、前置条件（两个文件缺一不可）

| 输入 | 必需 | 说明 |
|---|---|---|
| 待解析订单图片 | 是 | 单次一张（`.png` / `.jpg` / `.jpeg`），必须是用户上传到文件空间的原图 |
| SKU 清单 | 是 | `.xlsx`，含「SKU清单」工作表，列为：SKU编码、商品名称、别名（多个别名由竖线分隔）、品类、规格、单位、是否启用 |

硬规则：

1. 任一文件缺失（用户只给了图片、只给了 SKU 表，或只在对话里口头念了商品名），**先向用户索取，不得调用工具，也不得凭对话内容编造解析结果**。
2. 提示用户把文件上传到「数据准备」空间下的对应目录（订单图片：`数据准备/生鲜订单图片`；SKU 清单：`数据准备/生鲜sku表`）。
3. 文件名不确定时先用 `list_dir` 列出目录，拿到真实文件名再调用，**不要猜测文件名**（例如凭常识写 `订单1.png`）。

## 二、调用工具

工具名：`fresh_order_parse`（在 MCP 服务 `fresh-parse` 下）。

| 参数 | 必填 | 填什么 |
|---|---|---|
| `image_path` | 是 | 订单图片的**文件空间相对路径**，如 `数据准备/生鲜订单图片/订单1.png` |
| `sku_path` | 是 | SKU 清单的**文件空间相对路径**，如 `数据准备/生鲜sku表/SKU清单.xlsx` |
| `noise_path` | 否 | 留空，使用服务内置默认噪声词表 |
| `synonyms_path` | 否 | 留空，使用服务内置默认映射表 |

调用规则：

- 四个参数一律写**文件空间相对路径**（`数据准备/...`、`共享空间/...`、`临时空间/...`）；**禁止填 http/https 地址、本地盘符绝对路径**——平台会把相对路径自动铸造成签名下载直链。
- **一次调用只处理一张图片**。用户给多张图 → 逐张调用，先按图片分别成表，再给合计。
- 一次调用即返回三张表，不要为了"再确认一下"重复调用同一张图。

## 三、结果展示（必须用表格）

工具返回 JSON：`auto_rows`/`auto_count`、`review_rows`/`review_count`、`error_rows`/`error_count`。

先给一句总览：「共识别 N 行：自动匹配 a 行、待审核 b 行、异常 c 行。」

**表一 · 自动匹配（`auto_rows`）**

| 原始行 | 标准化名称 | 数量 | 匹配商品 | SKU编码 | 置信度 |
|---|---|---|---|---|---|

**表二 · 待审核（`review_rows`）**

| 原始行 | 标准化名称 | 数量 | 最高分 | 候选列表 |
|---|---|---|---|---|

候选列表取 `candidates`，按「名称（分数）」用 ` / ` 连接，最多列前 3 个。

**表三 · 异常（`error_rows`）**

| 原始行 | 标准化名称 | 数量 | 异常类型 | 最高候选 | 最高分 | 说明 |
|---|---|---|---|---|---|---|

展示规则：

1. 三张表**都要出现**；某张为空就写「无」，并保留计数 0，不要省略整张表。
2. 置信度 / 最高分统一取整显示。
3. 保持工具返回的行序，不要自行排序、合并或去重。
4. **不要丢「原始行」列**——它是后续复核与人工修正的唯一锚点。
5. 多图/多单时保留 `order_no`（订单编号）与 `source`（来源）；单图可在总览里说明一次。
6. 不要把工具返回的原始 JSON 整段贴给用户。

## 四、异常与存疑品类的求证（`read_file`）

触发条件（满足任一即触发）：

- `error_rows` 非空；
- `review_rows` 的候选分数偏中低，或前两名分数接近、同名不同规格，无法一眼判断；
- 数量或单位缺失、明显不合理（如数量为空）；
- 自动匹配结果与用户描述的业务常识明显不符。

步骤：

1. 用 `read_file` 读取 SKU 清单：`path` 传与 `sku_path` 相同的相对路径（xlsx 会自动转成 CSV 文本）。
2. 以「原始行 / 标准化名称 / 候选名称」中的关键词逐个检索：商品名称、别名、品类、规格；一次没命中就换更短的核心词（如去掉规格、单位、修饰词）再查。
3. 每条异常给出**推荐 + 证据**，证据三要素缺一不可：
   - 订单侧：原始行原文、标准化名称、数量；
   - SKU 侧：命中的 SKU编码、商品名称、别名/规格、单位、是否启用；
   - 判断依据：为什么是这条（名称或别名完全一致、规格吻合、仅差噪声词等）。
4. SKU 清单里确实找不到 → 明确写「SKU 清单中未找到」，列出已检索过的关键词，请用户确认，**不得臆造 SKU 编码或商品名称**。
5. `read_file` 返回内容被截断时，按提示用 `offset` / `limit` 续读，直到确认或排除为止。

推荐输出格式：

```
【异常复核】
订单行：<原始行>（标准化：<standardized_name>，数量 <数量>）
工具结论：<异常类型 / 候选与分数>
推荐：<商品名称>（SKU编码 xxx）
证据：SKU清单 —— SKU编码 / 商品名称 / 别名 / 规格 / 单位 / 是否启用
待确认：<仍有歧义时，需要用户拍板的具体问题>
```

## 五、最终推荐表（异常/待审核处理完必给）

触发条件：`review_count > 0` 或 `error_count > 0`，且第四节复核已做完 —— **必须**再给一张最终推荐表收口。两个计数都为 0 时不给此表，只写一句「全部自动匹配，无需人工推荐」。

表结构（一张表收口，不再拆）：

| 序号 | 原始行 | 数量 | 最终商品 | SKU编码 | 判定 | 依据 |
|---|---|---|---|---|---|---|
| 1 | 洋芋2斤 | 2斤 | 土豆 | VEG-002 | 直接匹配 | 分数 100 |
| 2 | 蕃茄3斤 | 3斤 | ==番茄== | ==VEG-001== | 模型推荐 | 别名/惯用称呼一致，SKU 清单启用 |

- 行覆盖：表一、表二、表三的**全部行**都进最终表，序号从 1 连续编号（多单时按 `order_no` 顺序接排）。
- 「判定」只有三种取值：`直接匹配`（取 `auto_rows` 工具结果）、`模型推荐`（取第四节复核结论）、`待确认`（清单查无或仍有歧义）。
- **标红规则（重点）**：`模型推荐` 与 `待确认` 两行的「最终商品」「SKU编码」两列，MUST 用 `==内容==` 包裹，例如 `==番茄==`、`==VEG-001==`；`直接匹配` 行与表头**不标红**。
  - `==` 内侧不要留空格（`== 番茄 ==` 不识别），也不要改用 HTML 标签、颜色词或其它符号——界面只认 `==...==` 这一种标红写法。
  - `待确认` 行：最终商品写 `==待确认：<最可能品种>==`，SKU编码写 `==—==`，依据里列出已检索过的关键词。
- 表尾补一行汇总（不标红）：`合计 N 行：直接匹配 a、模型推荐 b、待确认 c`。
- 「数量」取工具返回的 `quantity`（含单位），缺失写 `—`；「依据」一句话，写清是别名命中、规格吻合还是仅差噪声词。

硬规则：

1. 最终表 MUST 与第四节的逐条复核结论一一对应，不得出现第四节没推荐过的品种或臆造的 SKU 编码。
2. 前面三张表必须保留（用户要核对过程），最终表另起一张，不要用「同上」「见上表」省略。
3. 标红只用于最终表的推荐单元格；三张原始表、总览、合计行都保持默认颜色。

## 六、边界与禁止事项

- 缺订单图片或缺 SKU 清单时，**不调用工具、不输出解析结果**。
- 本技能只读：不修改 SKU 清单、不写回订单数据、不生成新的 SKU。
- `read_file` 读到的 SKU 信息只用于「异常复核」的推荐与证据，**不得用它替换工具给出的匹配结果**。
- 工具报错时（如参数未铸造成合法直链、OCR 失败、文件不存在），如实说明错误要点并给出下一步（检查文件是否已上传、是否为空白/模糊图片），**不得假装解析成功**。
- 一次一张图；未拿到图片前不要用「假设有一张订单」的方式演示解析。
